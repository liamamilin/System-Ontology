28  Appendix B — Entity Dictionary

This appendix defines the canonical entity vocabulary used in System Ontology v0.1. The purpose of the entity dictionary is to provide precise definitions for every entity type introduced in the ontology.

Each entry specifies:

  • the conceptual meaning of the entity

  • its role within system architecture

  • typical attributes associated with the entity

  • its relationship to other ontology elements

The definitions in this dictionary form the semantic reference layer for blueprint construction, extraction, and analysis.

28.1 System

Definition

A System is a bounded set of components, interfaces, workflows, and data structures organized to achieve a defined goal through interaction with external actors and environments.

Role in the Ontology

The system entity represents the root node of an ontology instance. All architectural elements exist either inside the system boundary or within its surrounding context.

Typical Attributes

  • id

  • name

  • goal

  • system_type

  • architecture_style

  • boundary

28.2 Actor

Definition

An Actor represents a human or automated participant that interacts with the system through defined interfaces.

Actors exist outside the system boundary but influence system behavior through requests, commands, or other interactions.

Role in the Ontology

Actors appear primarily within system context definitions and are associated with interface interactions.

Typical Attributes

  • id

  • name

  • role

Examples of actor roles include user, administrator, operator, and external client system.

28.3 External System

Definition

An External System represents a system outside the architectural boundary that interacts with the system through defined interfaces.

External systems may provide services, consume outputs, or participate in event exchanges.

Role in the Ontology

External systems appear in the context layer of architectural descriptions and establish integration boundaries.

Typical Attributes

  • id

  • name

  • description

  • interaction_interfaces

28.4 Capability

Definition

A Capability represents a functional ability of the system.

Capabilities describe what the system can accomplish from a behavioral perspective without specifying how that ability is implemented.

Role in the Ontology

Capabilities connect system goals with architectural structure. They are often realized through workflows and implemented by components.

Capabilities may be organized into hierarchical capability trees.

Typical Attributes

  • id

  • name

  • description

  • parent_capability

28.5 Component

Definition

A Component represents a structural unit of the system responsible for performing specific computational or operational responsibilities.

Components encapsulate behavior and interact with other components through defined interfaces.

Role in the Ontology

Components form the core structural elements of system architecture.

Typical Attributes

  • id

  • name

  • component_type

  • responsibility

  • inputs

  • outputs

  • statefulness

28.6 Interface

Definition

An Interface represents a defined interaction point through which components or external actors communicate with the system.

Interfaces expose operations and data exchange mechanisms.

Role in the Ontology

Interfaces define architectural boundaries and enable communication between system elements.

Typical Attributes

  • id

  • name

  • interface_type

  • protocol

  • version

28.7 Contract

Definition

A Contract defines the formal agreement governing interactions through an interface.

Contracts specify data formats, behavioral guarantees, and interaction semantics.

Role in the Ontology

Contracts ensure that interface interactions remain consistent even as component implementations evolve.

Typical Attributes

  • id

  • name

  • contract_type

  • data_contract

  • behavior_contract

28.8 Data Entity

Definition

A Data Entity represents a structured unit of information managed by the system.

Data entities may correspond to domain concepts or internal technical artifacts.

Role in the Ontology

Data entities capture the informational structures that components read, write, or transform.

Typical Attributes

  • id

  • name

  • data_kind (business or technical)

  • persistence

  • owner

28.9 Workflow

Definition

A Workflow represents an ordered or conditional structure of tasks coordinated to accomplish a system capability.

Workflows define how system activities are orchestrated over time.

Role in the Ontology

Workflows represent the execution coordination layer of the architecture.

Typical Attributes

  • id

  • name

  • description

  • trigger_reference

28.10 Task

Definition

A Task represents a discrete unit of execution performed by a component.

Tasks typically correspond to computational operations, service invocations, or processing steps within workflows.

Role in the Ontology

Tasks define the operational units executed within workflows.

Typical Attributes

  • id

  • name

  • component_reference

28.11 Job

Definition

A Job represents a runtime execution instance composed of one or more tasks.

Jobs typically correspond to scheduled processes, batch executions, or long-running background operations.

Role in the Ontology

Jobs represent operational executions rather than structural elements.

Typical Attributes

  • id

  • name

  • workflow_reference

28.12 Step

Definition

A Step represents an ordered stage within a workflow.

Steps define execution sequencing and determine how tasks are coordinated during workflow execution.

Role in the Ontology

Steps establish the internal structure of workflows.

Typical Attributes

  • id

  • name

  • workflow_reference

  • order

28.13 Trigger

Definition

A Trigger represents the condition that initiates workflow or task execution.

Triggers connect system execution with time-based schedules, events, or external requests.

Role in the Ontology

Triggers link system behavior to environmental stimuli.

Typical Attributes

  • id

  • name

  • trigger_type

Common trigger types include:

  • time

  • event

  • request

28.14 Constraint

Definition

A Constraint represents a requirement or limitation that governs system behavior.

Constraints typically encode non-functional requirements such as performance targets, reliability requirements, or security policies.

Role in the Ontology

Constraints attach quality attributes and operational requirements to architectural entities.

Typical Attributes

  • id

  • name

  • metric

  • threshold

  • scope

28.15 Failure Mode

Definition

A Failure Mode represents a specific way in which a system component or workflow may fail.

Failure modes capture potential system vulnerabilities and operational risks.

Role in the Ontology

Failure modes connect system structure with reliability analysis.

Typical Attributes

  • id

  • name

  • affected_entity

  • mitigation_reference

28.16 Reliability Mechanism

Definition

A Reliability Mechanism represents a structural mechanism designed to mitigate system failures.

Examples include retry policies, idempotent operations, circuit breakers, and isolation strategies.

Role in the Ontology

Reliability mechanisms link architectural structure with resilience strategies.

Typical Attributes

  • id

  • name

  • mechanism_type

28.17 Trust Boundary

Definition

A Trust Boundary represents a transition point between parts of the system that operate under different trust assumptions.

Trust boundaries typically occur between internal systems and external actors or between components with different privilege levels.

Role in the Ontology

Trust boundaries identify locations where authentication, authorization, or data protection mechanisms must be applied.

Typical Attributes

  • id

  • name

  • boundary_type

  • protected_resources

28.18 Summary

The entity dictionary establishes the semantic vocabulary used across blueprint representations. These entities capture the essential structural, behavioral, and operational elements required to describe complex software systems.

Together with the relation definitions and type taxonomies defined earlier in the ontology, this vocabulary forms the foundation for representing software architecture as structured and computable knowledge.
