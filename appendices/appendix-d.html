30  Appendix D — System Type Decision Tree

This appendix defines the decision procedure used to classify systems into canonical system types within System Ontology v0.1.

System type classification serves several purposes:

  • enabling consistent tagging of blueprint instances

  • supporting architectural retrieval and clustering

  • enabling pattern discovery across architecture datasets

  • guiding automated blueprint extraction pipelines

A system type is not determined by implementation technology or domain. Instead, classification is based on structural characteristics, including component composition, interaction models, and execution patterns.

The decision tree defined here provides a deterministic method for assigning a system type based on observable architectural features.

30.1 Classification Principles

System type classification follows several principles.

Structural basis

Classification is based on architectural structure rather than application domain or programming language.

For example, a data pipeline implemented in Python and one implemented in Java are classified identically if they share the same structural workflow architecture.

Dominant architecture

Some systems combine multiple architectural styles. In such cases, the classification should identify the dominant operational structure of the system.

Finite type set

The ontology maintains a limited and stable set of system types. This constraint ensures that blueprint repositories remain searchable and comparable across large datasets.

30.2 Decision Tree Overview

The following decision procedure determines the system type.

START

Is the system primarily used as a reusable code package
consumed by other software through imports or linking?

YES → Library / SDK
NO  → continue


Does the system expose interactive user interfaces
for human users through web or graphical interfaces?

YES → Web Application
NO  → continue


Is the primary interaction model a command-line interface
invoked by users or scripts?

YES → CLI Tool
NO  → continue


Does the system primarily expose network APIs
for consumption by other systems?

YES → API / Service
NO  → continue


Is the core structure a scheduled or event-triggered
workflow engine coordinating multiple tasks?

YES → Workflow Engine
NO  → continue


Is the primary architecture a multi-stage data
processing pipeline with transformation stages?

YES → Data Pipeline
NO  → continue


Does the system consist of autonomous agents
interacting with tools, environments, or other agents?

YES → Agent System
NO  → continue


Does the system provide infrastructure or capabilities
used as a foundation for multiple external applications?

YES → Platform
NO  → continue


If none of the above apply,
classify as Hybrid Architecture.

30.3 System Type Definitions

30.3.1 CLI Tool

A CLI Tool is a system whose primary interface is a command-line interface. Users or scripts invoke commands that execute tasks and produce outputs.

Typical characteristics:

  • command-line interface entry point

  • short-lived execution model

  • input through arguments or configuration files

  • output through console, files, or structured data

Typical components:

  • CLI interface

  • command dispatcher

  • task execution modules

30.3.2 Web Application

A Web Application is a system that provides interactive functionality through a web-based user interface.

Typical characteristics:

  • browser-based user interface

  • HTTP-based API services

  • server-side business logic

  • persistent data storage

Typical components:

  • web UI

  • API services

  • storage components

  • authentication systems

30.3.3 API / Service

An API / Service system exposes functionality primarily through network APIs consumed by other systems.

Typical characteristics:

  • REST or RPC interfaces

  • stateless request processing

  • service-level scaling

  • integration with other services

Typical components:

  • API gateway

  • service handlers

  • storage systems

  • authentication components

30.3.4 Workflow Engine

A Workflow Engine coordinates execution of multi-step processes through explicit workflow definitions.

Typical characteristics:

  • workflow definitions

  • task orchestration

  • scheduling and retry mechanisms

  • long-running process management

Typical components:

  • workflow orchestrator

  • scheduler

  • task workers

  • persistence storage

30.3.5 Data Pipeline

A Data Pipeline processes data through sequential or streaming transformation stages.

Typical characteristics:

  • batch or streaming ingestion

  • transformation stages

  • data movement across storage systems

  • analytical processing

Typical components:

  • ingestion components

  • transformation workers

  • message queues or streaming systems

  • storage systems

30.3.6 Agent System

An Agent System consists of autonomous or semi-autonomous agents interacting with tools, environments, or other agents.

Typical characteristics:

  • decision-making agents

  • tool invocation

  • environment interaction

  • iterative reasoning cycles

Typical components:

  • agent controller

  • tool interface layer

  • memory systems

  • model inference engines

30.3.7 Platform

A Platform provides foundational infrastructure or services used by multiple external applications or systems.

Typical characteristics:

  • extensible infrastructure services

  • multi-tenant capability

  • plugin or extension systems

  • shared data and service layers

Typical components:

  • platform core services

  • extension frameworks

  • identity and access management

  • service APIs

30.3.8 Library / SDK

A Library or SDK is a reusable code package designed to be integrated into other software systems.

Typical characteristics:

  • distributed as a package dependency

  • invoked through function or class interfaces

  • does not operate as a standalone system

Typical components:

  • public APIs

  • internal modules

  • configuration structures

30.3.9 Hybrid Architecture

A Hybrid Architecture represents systems that combine multiple architectural types without a single dominant operational structure.

Examples include:

  • platforms that also expose APIs and agent workflows

  • web applications with integrated data pipeline engines

  • agent systems embedded within larger service architectures

Hybrid classification indicates that the system requires multi-type architectural representation.

30.4 Signature Components

Each system type typically includes identifiable signature components that signal its architectural structure.

Examples include:

System Type Signature Components
CLI Tool CLI interface, command dispatcher
Web App Web UI, API service, storage
API Service API gateway, service handlers
Workflow Engine workflow orchestrator, scheduler
Data Pipeline ingestion worker, transformation stages
Agent System agent controller, tool interface
Platform extension framework, service APIs
Library / SDK public API modules

These signatures provide strong signals for automated blueprint extraction from repositories.

30.5 Role in Blueprint Extraction

The system type decision tree plays an important role in automated blueprint extraction.

During extraction, signals such as:

  • entry points

  • dependency patterns

  • directory structures

  • runtime configurations

can be analyzed to infer the likely system type.

Once the system type is determined, the extraction pipeline can apply type-specific heuristics to identify components, workflows, and interaction models.

This approach significantly improves the accuracy of architecture inference.

30.6 Summary

The System Type Decision Tree provides a deterministic mechanism for classifying systems according to their architectural structure.

By constraining system classification to a stable and finite set of types, the ontology enables large blueprint repositories to remain searchable, comparable, and analyzable.

This classification framework also forms a key foundation for later volumes addressing architecture datasets and automated blueprint extraction.
