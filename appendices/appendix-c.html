29  Appendix C — Relation Dictionary

This appendix defines the canonical relation vocabulary used in System Ontology v0.1. While entities describe the elements that exist within a system, relations describe how those elements interact, depend on one another, and form architectural structure.

Relations transform the ontology from a collection of objects into a connected architectural graph. Each relation type defines a specific semantic meaning that must remain consistent across blueprint representations.

The relations defined in this dictionary represent the minimal set required to capture structural composition, execution flow, data movement, dependency relationships, governance responsibilities, and contractual compliance.

29.1 contains

Definition

The contains relation represents structural composition. It indicates that one entity structurally includes another entity as part of its internal structure.

Semantic Meaning

If entity A contains entity B, then B exists as a structural element within A.

Typical Usage

  • a system contains components

  • a workflow contains steps

  • a module contains subcomponents

Direction

A → B
(container → contained entity)

Inverse Relation

part_of

29.2 part_of

Definition

The part_of relation represents the inverse of structural containment.

Semantic Meaning

If entity A is part_of entity B, then A exists within the structural scope of B.

Typical Usage

  • a component is part_of a system

  • a workflow step is part_of a workflow

Direction

A → B
(contained entity → container)

Inverse Relation

contains

29.3 depends_on

Definition

The depends_on relation represents a dependency relationship in which one entity requires another entity in order to operate correctly.

Semantic Meaning

If entity A depends_on entity B, the behavior or availability of A relies on B.

Typical Usage

  • a service depends_on a database

  • a worker depends_on a message queue

  • a pipeline stage depends_on upstream processing

Direction

A → B
(dependent → dependency)

Architectural Significance

Dependency relations define the coupling structure of the system.

29.4 calls

Definition

The calls relation represents synchronous invocation between components or through interfaces.

Semantic Meaning

If entity A calls entity B, A sends a request to B and waits for a response before continuing execution.

Typical Usage

  • a frontend service calls an API service

  • a workflow engine calls a processing component

Direction

A → B
(caller → callee)

Interaction Model

Request–response communication.

29.5 invokes

Definition

The invokes relation represents a directed operational request between components or tasks. It is semantically similar to calls but may apply to workflow execution rather than service APIs.

Semantic Meaning

If entity A invokes entity B, A triggers the execution of B as part of a workflow or processing sequence.

Typical Usage

  • a workflow step invokes a processing task

  • an orchestration engine invokes a worker

Direction

A → B

Architectural Significance

Invocation relations help represent execution paths within workflows.

29.6 emits

Definition

The emits relation represents the production of an event or message.

Semantic Meaning

If entity A emits an event, the event is published to a communication channel or event stream.

Typical Usage

  • a service emits a domain event

  • a component emits log or telemetry events

Direction

A → Event or Channel

Interaction Model

Event-driven communication.

29.7 consumes

Definition

The consumes relation represents the reception and processing of an event or message.

Semantic Meaning

If entity A consumes an event, A reacts to or processes an event produced by another entity.

Typical Usage

  • a worker consumes queue messages

  • an analytics component consumes event streams

Direction

Consumer → Event Source

Architectural Significance

Event consumption enables asynchronous system interaction.

29.8 reads

Definition

The reads relation represents data retrieval from a data entity or storage component.

Semantic Meaning

If entity A reads entity B, A accesses data stored in B without modifying it.

Typical Usage

  • a service reads user records

  • a data pipeline stage reads input datasets

Direction

Reader → Data Entity

Architectural Significance

Read relations represent data dependency flows.

29.9 writes

Definition

The writes relation represents data modification or persistence.

Semantic Meaning

If entity A writes to entity B, A stores or updates data within B.

Typical Usage

  • a service writes transaction records to storage

  • a processing engine writes results to a database

Direction

Writer → Data Entity

Architectural Significance

Write relations represent data production flows.

29.10 owns

Definition

The owns relation represents responsibility or stewardship over an architectural entity.

Semantic Meaning

If entity A owns entity B, A is responsible for maintaining, operating, or governing B.

Typical Usage

  • a team owns a service component

  • an organization owns a platform

Direction

Owner → Owned Entity

Architectural Significance

Ownership relations connect organizational structure with system architecture.

29.11 governs

Definition

The governs relation represents policy or control authority applied to architectural elements.

Semantic Meaning

If entity A governs entity B, A defines rules, policies, or constraints affecting B.

Typical Usage

  • a policy engine governs API access

  • a security authority governs data access rules

Direction

Authority → Governed Entity

Architectural Significance

Governance relations represent control and policy enforcement structures.

29.12 implements

Definition

The implements relation indicates that a component provides the functionality defined by an interface.

Semantic Meaning

If component A implements interface B, A provides the operational behavior described by B.

Typical Usage

  • a service implements an API interface

  • a component implements a command interface

Direction

Component → Interface

Architectural Significance

Implementation relations connect structural elements with interaction boundaries.

29.13 conforms_to

Definition

The conforms_to relation indicates that an entity satisfies a defined contract, schema, or policy.

Semantic Meaning

If entity A conforms_to contract B, A adheres to the rules defined by B.

Typical Usage

  • an API conforms_to a schema definition

  • an event conforms_to an event specification

  • a component conforms_to a security policy

Direction

Entity → Contract

Architectural Significance

Conformance relations enforce compatibility and compliance within system interactions.

29.14 Relation Summary

The relation set defined in Ontology v0.1 is intentionally minimal but expressive enough to capture the essential structural and behavioral interactions within software systems.

These relations fall into several functional categories:

Structural relations

  • contains

  • part_of

Dependency relations

  • depends_on

Invocation relations

  • calls

  • invokes

Event relations

  • emits

  • consumes

Data relations

  • reads

  • writes

Governance relations

  • owns

  • governs

Contract relations

  • implements

  • conforms_to

Together, these relations form the semantic connective tissue of the ontology, enabling architectural structures to be represented as coherent graphs rather than isolated entities.
