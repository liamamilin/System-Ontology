33  Appendix G — Projection Mapping Cheat Sheet

33.0.1 Ontology → Blueprint Slots → Views

This appendix summarizes the projection mapping rules that connect the ontology layer to blueprint representations and stakeholder views.

Within the Blueprint Architecture framework, three conceptual layers must remain clearly separated:

  1. Ontology — the canonical semantic model of systems

  2. Blueprint Kernel — the minimal architectural representation

  3. Views / Projections — stakeholder-specific perspectives derived from the blueprint

The ontology provides the full semantic vocabulary, while the Blueprint Kernel provides a minimal structural representation. Views are then derived from the kernel depending on the needs of different readers.

This layered mapping ensures that architecture can be represented once and projected into multiple perspectives without duplicating information.

34 1. Ontology → Blueprint Kernel Mapping

The Blueprint Kernel defines six fundamental structural slots:

Goal
Capabilities
Components
Interfaces
Data
Workflows

Ontology entities map into these slots through projection rules.

34.0.1 Mapping Table

Ontology Entity Blueprint Kernel Slot Purpose
System Goal Defines the system objective
Capability Capabilities Describes functional abilities
Component Components Defines structural building blocks
Interface Interfaces Defines interaction boundaries
Contract Interfaces Specifies interface semantics
Data Entity Data Represents system information structures
Workflow Workflows Represents execution orchestration
Step / Task / Job Workflows Defines workflow structure
Trigger Workflows Defines execution initiation
Constraint Goal / Components / Interfaces Defines quality requirements

This mapping ensures that complex ontology structures can always be reduced into the minimal blueprint kernel representation.

35 2. Kernel → View Projections

Once the blueprint kernel is constructed, different views can be generated automatically.

Views are not separate models. They are filtered projections of the blueprint.

Three primary projections are defined in v0.1.

35.1 Architecture View

The Architecture View focuses on structural organization.

It highlights system composition and interaction patterns.

35.1.1 Primary Focus

  • components

  • interfaces

  • dependencies

  • data flows

35.1.2 Typical Visualization

Architecture views are typically rendered as:

  • component diagrams

  • dependency graphs

  • service interaction maps

35.1.3 Derived From

Components
Interfaces
Data
Workflows
Relations

This view is primarily used by system architects and engineers.

35.2 Specification View

The Specification View focuses on system capabilities and behavioral requirements.

It emphasizes what the system is expected to do and what constraints govern its behavior.

35.2.1 Primary Focus

  • goals

  • capabilities

  • interfaces

  • contracts

  • constraints

35.2.2 Typical Representation

Specification views often resemble:

  • capability trees

  • API specifications

  • requirement structures

35.2.3 Derived From

Goal
Capabilities
Interfaces
Contracts
Constraints

This view is primarily used by product designers and system planners.

35.3 Operations View

The Operations View focuses on runtime behavior and operational reliability.

It describes how the system executes tasks, manages workflows, and maintains system health.

35.3.1 Primary Focus

  • workflows

  • triggers

  • runtime dependencies

  • reliability mechanisms

  • failure modes

35.3.2 Typical Representation

Operations views often appear as:

  • workflow diagrams

  • runtime topology diagrams

  • operational monitoring structures

35.3.3 Derived From

Workflows
Triggers
Components
Constraints
Failure mechanisms

This view is primarily used by operators and reliability engineers.

37 4. Projection Pipeline

The full projection pipeline can be summarized as:

Ontology
   ↓
Blueprint Kernel
   ↓
View Projections

More explicitly:

Ontology Graph
   ↓ (mapping rules)
Blueprint Kernel
   ↓ (projection filters)
Architecture View
Specification View
Operations View

This architecture enables blueprint representations to function as a single source of architectural truth.

38 5. Role in the Blueprint Architecture Framework

The projection mapping layer plays a critical role in the broader framework.

It ensures that:

  • ontology definitions remain stable

  • blueprint representations remain minimal

  • multiple stakeholder views can be generated automatically

Without projection mapping, architecture documentation typically fragments into separate artifacts such as diagrams, specifications, and operational documents.

Within the Blueprint framework, these artifacts become projections of a single architectural representation.

39 6. Practical Usage

In practice, projection mappings are implemented in blueprint tooling.

Typical workflows include:

ontology instance
      ↓
blueprint generation
      ↓
architecture diagram
spec documentation
ops workflow

This allows blueprint repositories to support automated documentation generation, architectural visualization, and system analysis.

40 Summary

Projection mapping connects three layers of architectural representation:

Ontology (semantic language)
      ↓
Blueprint Kernel (minimal architecture structure)
      ↓
Views (stakeholder projections)

This structure enables software architecture to function as structured, reusable, and computable knowledge.

The projection model therefore forms the bridge between the ontology defined in this volume and the blueprint construction and analysis processes developed in later volumes of the Blueprint Architecture Series.
