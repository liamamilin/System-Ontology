19  Component Type Taxonomy (v0.1)

While system types classify entire architectures, component types classify the structural elements that compose those systems. A stable taxonomy of component types enables architectural descriptions to remain consistent across domains, technologies, and implementation environments.

Component types describe the functional role of a component within the architecture, rather than its implementation details. For example, a database component may be implemented using many different technologies, but its architectural role as a storage component remains constant.

The component taxonomy defined in Ontology v0.1 focuses on a small set of structural roles that appear across most software systems. These roles capture the primary responsibilities that components perform within system architectures.

19.0.1 Frontend and Interface Components

Frontend and interface components represent the points of interaction between the system and external actors. These actors may be human users, external systems, or automated processes.

Frontend components provide user-facing interaction mechanisms. Examples include graphical web interfaces, desktop interfaces, and mobile interfaces. These components focus on presenting information and collecting user input.

Interface components provide programmatic access to system capabilities. These interfaces often appear as APIs, command-line interfaces, or event endpoints.

The architectural role of these components is to expose system capabilities while maintaining a controlled boundary between internal components and external actors.

Frontend Examples:

React Web Application:
  - Provides browser-based user interface
  - Manages client-side state
  - Communicates with backend APIs
  
Mobile Application:
  - Provides mobile user interface
  - Accesses device capabilities
  - Offline functionality support
  
Desktop Application:
  - Provides desktop user interface
  - Integrates with operating system
  - Native performance

CLI Tool:
  - Provides command-line interface
  - Accepts command-line arguments
  - Returns structured output

Interface Examples:

REST API:
  - HTTP/HTTPS protocol
  - JSON/XML data format
  - Standard HTTP methods
  
GraphQL API:
  - Single endpoint
  - Query language for data
  - Flexible data retrieval
  
gRPC API:
  - Protocol Buffers
  - High-performance RPC
  - Streaming support
  
Event Stream:
  - Publish-subscribe model
  - Real-time events
  - Multiple consumers
  
Command Interface:
  - Programmatic commands
  - Scriptable interface
  - Batch processing support

19.0.2 Compute Components

Compute components perform the core processing logic of the system. They implement the computational behavior required to fulfill system capabilities.

Several structural roles commonly appear within this category.

Service components process incoming requests and apply business logic. They often expose APIs and coordinate interactions with other components.

Worker components execute background processing tasks such as data transformations, asynchronous jobs, or long-running computations.

Engine components implement specialized execution logic. Examples include workflow engines, rule engines, recommendation engines, or model inference engines.

Compute components therefore represent the active processing layer of the system architecture.

Service Examples:

API Service:
  - Handles HTTP requests
  - Implements business logic
  - Coordinates with other services
  
Business Logic Service:
  - Implements domain rules
  - Processes business operations
  - Maintains domain state
  
Integration Service:
  - Integrates with external systems
  - Handles data transformation
  - Manages external API calls

Worker Examples:

Background Job Worker:
  - Processes scheduled jobs
  - Executes long-running tasks
  - Handles batch operations
  
Data Processing Worker:
  - Transforms data
  - Applies business rules
  - Generates reports
  
Notification Worker:
  - Sends notifications
  - Handles email/SMS
  - Manages delivery retries

Engine Examples:

Workflow Engine:
  - Orchestrates workflows
  - Manages task execution
  - Handles retries and errors
  
Rule Engine:
  - Evaluates business rules
  - Makes decisions
  - Applies policies
  
ML Inference Engine:
  - Runs machine learning models
  - Makes predictions
  - Processes inference requests
  
Search Engine:
  - Executes searches
  - Ranks results
  - Handles queries

19.0.3 Storage Components

Storage components manage the persistence and retrieval of system data.

These components maintain data across system operations and ensure that information remains available beyond the execution of individual tasks.

Typical storage components include:

  • relational or document databases

  • distributed key–value stores

  • caching systems

  • vector databases used for embedding storage and similarity search

Storage components are often associated with specific data entities within the ontology. They define where system data resides and how it is accessed.

Because storage components manage durable state, they often represent critical architectural dependencies.

Storage Examples:

Relational Database:
  - Structured data storage
  - ACID transactions
  - SQL queries
  - Examples: PostgreSQL, MySQL
  
Document Database:
  - Flexible schema
  - JSON documents
  - Nested data structures
  - Examples: MongoDB, CouchDB
  
Key-Value Store:
  - High-performance access
  - Simple data model
  - Low latency
  - Examples: Redis, DynamoDB
  
Object Storage:
  - Large file storage
  - Scalable
  - Cost-effective
  - Examples: S3, Azure Blob
  
Vector Database:
  - Embedding storage
  - Similarity search
  - ML applications
  - Examples: Pinecone, Weaviate

Cache Examples:

In-Memory Cache:
  - Fast access
  - Volatile storage
  - Session data
  - Examples: Redis, Memcached
  
CDN Cache:
  - Content delivery
  - Geographic distribution
  - Static assets
  - Examples: Cloudflare, Akamai
  
Application Cache:
  - Response caching
  - Computed results
  - Performance optimization
  - Examples: Built-in caches

19.0.4 Coordination Components

Coordination components manage the temporal and structural coordination of system activities.

These components regulate how tasks are scheduled, how components communicate asynchronously, and how workflows are executed.

Common coordination roles include:

Queue components buffer tasks or messages between producers and consumers. They decouple components and allow asynchronous communication.

Scheduler components initiate tasks according to time-based or conditional triggers.

Orchestrator components manage multi-step workflows and coordinate execution across multiple services or tasks.

Coordination components are particularly important in distributed systems, where many components must interact without direct synchronous dependencies.

Queue Examples:

Message Queue:
  - Message buffering
  - FIFO ordering
  - At-least-once delivery
  - Examples: RabbitMQ, SQS
  
Task Queue:
  - Job scheduling
  - Worker coordination
  - Priority support
  - Examples: Celery, Sidekiq
  
Event Queue:
  - Event streaming
  - Publish-subscribe
  - Multiple consumers
  - Examples: Kafka, Pulsar

Scheduler Examples:

Cron Scheduler:
  - Time-based triggers
  - Recurring jobs
  - Cron expressions
  - Examples: Quartz, Sidekiq-Scheduler
  
Event Scheduler:
  - Event-based triggers
  - Conditional execution
  - Complex schedules
  - Examples: Temporal, Cadence
  
Resource Scheduler:
  - Resource allocation
  - Load balancing
  - Priority scheduling
  - Examples: Kubernetes Scheduler

Orchestrator Examples:

Workflow Orchestrator:
  - Workflow coordination
  - Step execution
  - Error handling
  - Examples: Airflow, Temporal
  
Service Orchestrator:
  - Service coordination
  - Dependency management
  - Service discovery
  - Examples: Kubernetes, Nomad
  
Process Orchestrator:
  - Process management
  - Lifecycle control
  - Scaling operations
  - Examples: Docker Swarm, ECS

19.0.5 Observability Components

Observability components provide visibility into the behavior and performance of the system.

These components collect and analyze operational information, allowing engineers to understand system behavior, detect failures, and diagnose performance issues.

Typical observability roles include:

Log systems that record operational events and system messages.

Metrics systems that collect quantitative measurements such as request latency, throughput, and resource usage.

Tracing systems that record the execution path of requests as they propagate across components.

Observability components do not directly implement business functionality, but they play a critical role in maintaining system reliability and operational transparency.

Logging Examples:

Application Logger:
  - Application events
  - Structured logs
  - Log levels (debug, info, warn, error)
  - Examples: Log4j, Winston
  
Access Logger:
  - HTTP access logs
  - Request tracking
  - Security auditing
  - Examples: Nginx logs, Apache logs
  
Audit Logger:
  - Compliance logging
  - Security events
  - Immutable records
  - Examples: CloudTrail, Audit Logs

Metrics Examples:

Application Metrics:
  - Request rate
  - Response time
  - Error rate
  - Examples: Prometheus, StatsD
  
System Metrics:
  - CPU usage
  - Memory usage
  - Disk I/O
  - Examples: Node Exporter, Collectd
  
Business Metrics:
  - Order count
  - Revenue
  - User engagement
  - Examples: Custom metrics, Datadog

Tracing Examples:

Distributed Tracing:
  - Request tracing
  - Service dependencies
  - Performance analysis
  - Examples: Jaeger, Zipkin, OpenTelemetry
  
Transaction Tracing:
  - Database queries
  - External API calls
  - Transaction performance
  - Examples: APM tools, New Relic
  
User Journey Tracing:
  - User interactions
  - Session tracking
  - UX analysis
  - Examples: Session replay tools

Together, these component types form a minimal taxonomy capable of describing the primary structural roles present in most system architectures.

By categorizing components according to their architectural function, the ontology enables blueprint representations to remain consistent across different technologies while preserving the essential structural characteristics of the system.

19.1 Summary

Component types classify the functional role of a component within the architecture, not its implementation details. The ontology v0.1 taxonomy covers five primary categories: Frontend/Interface, Compute (Services, Workers, Engines), Storage/Cache, Coordination (Queues, Schedulers, Orchestrators), and Observability (Logging, Metrics, Tracing).

19.1.1 Core Knowledge — Must Remember

Category Role Examples Key Characteristic
Frontend / Interface Points of interaction with external actors Web UI, REST API, CLI, Event Stream, Mobile App Expose system capabilities while maintaining controlled boundaries
Compute: Service Request processing with business logic API Service, Business Logic Service, Integration Service Active request processing, often stateless
Compute: Worker Background asynchronous processing Job Worker, Data Processing Worker, Notification Worker Event-driven or scheduled, fault-tolerant
Compute: Engine Specialized execution logic Workflow Engine, Rule Engine, ML Inference Engine Encapsulated domain-specific computation
Storage / Cache Persistence and retrieval of data Relational DB, Document DB, Key-Value Store, CDN Durable state — often critical architectural dependencies
Coordination: Queue Async message buffering between components Message Queue (RabbitMQ), Task Queue (Celery), Event Queue (Kafka) Decouple producers and consumers
Coordination: Scheduler Time/event-based task initiation Cron Scheduler (Quartz), Event Scheduler (Temporal) Trigger execution based on conditions
Coordination: Orchestrator Multi-step workflow management Workflow Orchestrator (Airflow), Service Orchestrator (Kubernetes) Centralized coordination
Observability Visibility into system behavior Logger, Metrics Collector (Prometheus), Distributed Tracing (Jaeger) No business logic — critical for reliability

Key insight: The same component type can be implemented with many different technologies (e.g., PostgreSQL, MongoDB, or S3 are all “Storage”). The architectural role remains constant even as implementation technology evolves.
