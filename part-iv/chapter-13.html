18  System Type Taxonomy (v0.1)

Architectural representations benefit from a stable classification of system types. While individual systems vary widely in implementation, many share recognizable structural patterns. A taxonomy of system types enables architectural descriptions to be compared, indexed, and analyzed across large collections of systems.

Within the ontology, system types provide a high-level categorization of architectural structures. They describe the dominant operational model of a system rather than its specific implementation details.

The taxonomy defined in Ontology v0.1 focuses on a small set of system categories that appear consistently across software ecosystems.

18.0.1 Why System Types Must Be Finite and Stable

A system type taxonomy must remain limited and stable.

If the number of types grows without constraint, classification becomes inconsistent. Different architects may assign different type labels to similar systems, preventing meaningful comparison across blueprint datasets.

A small and stable set of system types ensures that:

  • blueprint repositories remain searchable

  • architectural datasets remain analyzable

  • pattern mining becomes feasible

  • architecture intelligence systems can operate on predictable categories

System types therefore function as structural anchors rather than descriptive labels. Each type represents a recurring architectural organization that appears across many systems.

Because architectural styles evolve slowly compared to implementation technologies, the number of system types should remain relatively constant across ontology versions.

18.0.2 Primary System Types

Ontology v0.1 defines a set of common system types that capture the majority of contemporary software architectures.

CLI Tools

Command-line tools provide functionality through terminal interfaces. They typically execute short-lived processes initiated by user commands or scripts.

CLI systems often consist of:

  • a command interface

  • argument parsing components

  • execution logic modules

  • optional integration with external systems

These systems emphasize simplicity and direct user interaction.

Example: git command-line tool for version control

Components:
  - CLI Interface (parses git commands)
  - Repository Manager (handles git operations)
  - File System (accesses .git directory)
  
Characteristics:
  - Command-line interaction
  - Short-lived execution
  - Direct file system access
  - Optional remote integration

Web Applications

Web applications provide user-facing functionality through graphical interfaces delivered over web protocols.

Typical components include:

  • web front-end interfaces

  • application services

  • session management systems

  • data persistence layers

Web applications emphasize user interaction and request-driven workflows.

Example: E-commerce web application

Components:
  - Web UI (React frontend)
  - API Service (Node.js backend)
  - Database (PostgreSQL)
  - Redis Cache (session storage)
  
Characteristics:
  - Browser-based UI
  - HTTP API services
  - Session management
  - Data persistence

APIs and Services

API systems expose programmable interfaces for external clients or other services.

These systems typically include:

  • API gateway components

  • service implementations

  • authentication and authorization layers

  • data access components

API-based architectures often serve as integration layers within larger system ecosystems.

Example: Payment processing API

Components:
  - API Gateway (request routing)
  - Auth Service (authentication)
  - Payment Service (payment processing)
  - Database (transaction storage)
  
Characteristics:
  - Network-accessible interfaces
  - Stateless request processing
  - Independent scaling
  - Integration-focused

Workflow Engines

Workflow engines coordinate the execution of complex processes composed of multiple tasks or services.

Typical architectural elements include:

  • workflow definition engines

  • task execution services

  • scheduling systems

  • state persistence mechanisms

These systems emphasize orchestration and process coordination.

Example: Business process automation platform

Components:
  - Workflow Orchestrator (coordinates processes)
  - Scheduler (triggers workflows)
  - Task Workers (execute tasks)
  - Database (workflow state)
  
Characteristics:
  - Process definitions
  - Task orchestration
  - Scheduling and retry
  - Long-running processes

Data Pipelines

Data pipeline systems process large volumes of data through staged transformations.

Common components include:

  • data ingestion systems

  • transformation engines

  • streaming or batch processing frameworks

  • storage and analytics components

Data pipelines organize system behavior around data flow rather than request-response interactions.

Example: Real-time analytics pipeline

Components:
  - Ingestion Workers (collect data)
  - Stream Processor (transform data)
  - Message Broker (coordinate flow)
  - Data Warehouse (store results)
  
Characteristics:
  - Data ingestion
  - Transformation stages
  - Streaming or batch processing
  - Analytics focus

Agent Systems

Agent systems rely on autonomous or semi-autonomous agents that interpret goals, plan actions, and interact with tools or services.

Typical elements include:

  • agent controllers

  • tool interfaces

  • memory or context stores

  • reasoning or planning modules

Agent architectures emphasize dynamic decision-making and adaptive workflows.

Example: AI-powered task assistant

Components:
  - Agent Controller (coordinates reasoning)
  - LLM Engine (generates plans)
  - Tool Executor (invokes tools)
  - Memory Store (maintains context)
  
Characteristics:
  - Autonomous decision-making
  - Tool invocation
  - Iterative reasoning
  - Adaptive workflows

Platforms

Platforms provide infrastructure or shared services upon which other applications are built.

Platform systems typically include:

  • service registries

  • resource management systems

  • extensibility mechanisms

  • developer-facing interfaces

Platforms act as foundational layers within larger software ecosystems.

Example: Cloud platform as a service

Components:
  - Resource Manager (provisions infrastructure)
  - Service Registry (discovers services)
  - API Gateway (exposes platform APIs)
  - Monitoring Service (tracks resources)
  
Characteristics:
  - Infrastructure services
  - Multi-tenant support
  - Extension mechanisms
  - Developer tools

Libraries and SDKs

Libraries and software development kits provide reusable functionality for other systems.

These systems typically consist of:

  • packaged modules

  • public APIs

  • configuration interfaces

  • integration documentation

Libraries do not operate as independent systems but instead extend the capabilities of host applications.

Example: Machine learning library

Components:
  - Model Definitions (ML architectures)
  - Training Functions (model training)
  - Inference Functions (model prediction)
  - Utilities (data processing)
  
Characteristics:
  - Packaged modules
  - Public APIs
  - No standalone execution
  - Integration-focused

18.0.3 Signature Components

Each system type is typically associated with a set of signature components. These components represent the structural patterns that characterize that type of system.

For example:

  • web applications often contain UI components, application services, and persistence layers

  • data pipelines typically include ingestion components, transformation engines, and storage components

  • workflow engines contain orchestration components and task execution units

Signature components allow system types to be identified through the presence of particular structural patterns.

These patterns also enable automated analysis of blueprint datasets. By detecting recurring component configurations, architecture intelligence systems can infer likely system types.

18.0.4 Type Classification Rules

Determining the type of a system requires explicit classification rules.

A common approach is to represent system classification as a decision tree based on structural signals.

These signals may include:

  • the presence of user interfaces

  • dominant interaction models

  • workflow coordination mechanisms

  • data processing pipelines

  • agent decision loops

For example:

  • if the primary interaction model involves terminal commands, the system is likely a CLI tool

  • if the system primarily exposes programmable interfaces for other systems, it may be classified as an API service

  • if system behavior is organized around continuous data transformation stages, the system likely belongs to the data pipeline category

Classification rules allow system types to be inferred automatically when analyzing blueprint repositories or extracting architectures from existing codebases.

By combining a stable taxonomy with explicit classification rules, the ontology enables architectural structures to be organized into meaningful system categories that support large-scale analysis and reuse.

│                                                                                         │
│   Note: Can be classified as both WEB APPLICATION (user-facing) and API SERVICE       │
│         (backend), depending on perspective.                                            │
│                                                                                         │
│ EXAMPLE 5: Apache Airflow                                                              │
│                                                                                         │
│   Step 1: Primary interaction → Web Admin / Workflow Defs                               │
│   Step 2C: API Calls (workflow definitions)                                             │
│   Step 2C2: Coordinates workflows? → Yes                                                │
│   Result: WORKFLOW ENGINE                                                               │
│                                                                                         │
│   Verification:                                                                         │
│     ✓ Workflow definition (DAGs)                                                       │

│     ✓ Retry logic (task retries)                                                         │

│ EXAMPLE 6: AutoGPT                                                                     │
│                                                                                         │
│   Step 1: Primary interaction → No direct interaction (autonomous)                     │
│   Step 2D: Makes autonomous decisions? → Yes                                             │
│   Step 2D1: Uses external tools? → Yes                                                  │
│   Result: AGENT SYSTEM                                                                  │
│                                                                                         │
│   Verification:                                                                         │
│     ✓ Decision-making component (LLM)                                                   │
│     ✓ Autonomous choices without human intervention                                    │
│     ✓ Uses external tools (file system, web search, etc.)                              │
│     ✓ Has goals/objectives                                                              │
│     ✓ Handles multi-step tasks                                                          │
│                                                                                         │
│ EXAMPLE 7: Vercel                                                                      │
│                                                                                         │
│   Step 1: Primary interaction → Web Browser                                            │
│   Step 2B: Web interface primary? → Yes                                                  │
│   Step 2B1: Platform for building apps? → Yes                                           │
│   Result: PLATFORM                                                                      │
│                                                                                         │
│   Verification:                                                                         │
│     ✓ Multi-tenant architecture                                                         │
│     ✓ Developer tools and APIs                                                          │
│     ✓ Application hosting                                                              │
│     ✓ User management                                                                  │
│                                                                                         │
│ EXAMPLE 8: React Library                                                              │
│                                                                                         │
│   Step 1: Primary interaction → No direct interaction                                   │
│   Step 2D: Makes autonomous decisions? → No                                              │
│   Step 2D2: Imported/used by other systems? → Yes                                       │
│   Result: LIBRARY/SDK                                                                   │
│                                                                                         │
│   Verification:                                                                         │
│     ✓ Public API (React components, hooks)                                              │
│     ✓ No standalone execution                                                          │
│     ✓ Reusable components                                                              │
│     ✓ Documentation                                                                    │
│                                                                                         │
│ EXAMPLE 9: Apache Spark                                                                │
│                                                                                         │
│   Step 1: Primary interaction → API Calls (Spark Context)                               │
│   Step 2C: Data processing? → Yes                                                       │
│   Step 2C1: Multi-stage? → Yes (map, reduce, etc.)                                      │
│   Result: DATA PIPELINE                                                                 │
│                                                                                         │
│   Verification:                                                                         │
│     ✓ Ingestion components (data sources)                                              │

18.1.5 Edge Cases and Hybrid Types

┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                      EDGE CASES AND HYBRID TYPES                                          │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                         │
│ HYBRID TYPE 1: Web Application + API Service                                            │
│                                                                                         │
│   Example: Content Management System (WordPress)                                        │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Primary purpose = End-user application → WEB APPLICATION                          │
│     • Secondary purpose = Programmatic access → API SERVICE                             │
│                                                                                         │
│   Recommendation: Classify as WEB APPLICATION (primary),                                │
│                   note API SERVICE capabilities                                           │
│                                                                                         │
│ HYBRID TYPE 2: API Service + Workflow Engine                                           │
│                                                                                         │
│   Example: Jenkins CI/CD Pipeline                                                       │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Primary purpose = Execute workflows → WORKFLOW ENGINE                             │
│     • Secondary purpose = Expose APIs → API SERVICE                                    │
│                                                                                         │
│   Recommendation: Classify as WORKFLOW ENGINE (primary),                                │
│                   note API SERVICE capabilities                                           │
│                                                                                         │
│ HYBRID TYPE 3: Data Pipeline + Agent System                                            │
│                                                                                         │
│   Example: Intelligent Data Processing System                                           │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Primary purpose = Process data in stages → DATA PIPELINE                          │
│     • Secondary purpose = Make autonomous decisions → AGENT SYSTEM                      │
│                                                                                         │
│   Recommendation: Classify as DATA PIPELINE (primary),                                  │
│                   note AGENT SYSTEM capabilities                                         │
│                                                                                         │
│ HYBRID TYPE 4: Platform + Workflow Engine                                              │
│                                                                                         │
│   Example: GitHub Actions Platform                                                      │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Primary purpose = Enable app building → PLATFORM                                  │
│     • Secondary purpose = Execute workflows → WORKFLOW ENGINE                           │
│                                                                                         │
│   Recommendation: Classify as PLATFORM (primary),                                       │
│                   note WORKFLOW ENGINE capabilities                                      │
│                                                                                         │
│ EDGE CASE 1: Microservices Architecture                                                 │
│                                                                                         │
│   Example: E-commerce microservices platform                                            │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Overall system = PLATFORM (enables multiple services)                             │
│     • Individual services = API SERVICES                                                │
│                                                                                         │
│   Recommendation: Classify each component independently based on its primary purpose   │
│                                                                                         │
│ EDGE CASE 2: Serverless Functions                                                      │
│                                                                                         │
│   Example: AWS Lambda function                                                         │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Single function = API SERVICE (exposed via HTTP)                                 │
│     • Function collection = WORKFLOW ENGINE (orchestrated)                              │
│                                                                                         │
│   Recommendation: Classify based on deployment and orchestration model                 │
│                                                                                         │
│ EDGE CASE 3: Mobile Applications                                                       │
│                                                                                         │
│   Example: iOS/Android mobile app                                                       │
│                                                                                         │
│   Classification Approach:                                                               │
│     • Frontend = CLIENT (not in ontology v0.1, treated as component)                  │
│     • Backend = API SERVICE                                                             │
│                                                                                         │
│   Recommendation: Focus on backend classification, note frontend separately            │
│                                                                                         │
│ EDGE CASE 4: Desktop Applications                                                      │
│                                                                                         │
│   Example: Electron desktop app                                                        │
│                                                                                         │
│   Classification Approach:                                                               │
│     • If desktop-only → Not covered in v0.1 (treat as WEB APPLICATION equivalent)       │
│     • If syncs with web → WEB APPLICATION (primary interface)                           │
│                                                                                         │
│   Recommendation: Classify based on primary interaction model                           │

18.1.6 Classification Best Practices

┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                        CLASSIFICATION BEST PRACTICES                                     │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                         │
│ PRACTICE 1: Focus on Primary Purpose                                                    │
│                                                                                         │
│   ✓ Identify the system's primary purpose and interaction model                        │
│   ✓ Classify based on dominant characteristics                                        │
│   ✗ Don't over-engineer classification for minor features                            │
│                                                                                         │
│   Example: A web app with an API is still a WEB APPLICATION (primary)                 │
│                                                                                         │
│ PRACTICE 2: Use Decision Tree Systematically                                            │
│                                                                                         │
│   ✓ Follow the decision tree step by step                                              │
│   ✓ Answer questions based on actual system behavior                                   │
│   ✗ Don't skip steps or make assumptions                                              │
│                                                                                         │
│   Example: Start with "Primary Interaction Model", not with system architecture       │
│                                                                                         │
│ PRACTICE 3: Verify with Characteristics                                                 │
│                                                                                         │
│   ✓ Check that the system has the key characteristics of its type                     │
│   ✓ Verify at least 3-4 characteristics are present                                  │
│   ✗ Don't classify based on single characteristic                                     │
│                                                                                         │
│   Example: A system with API endpoints isn't necessarily an API SERVICE              │
│                                                                                         │
│ PRACTICE 4: Handle Hybrid Systems Appropriately                                         │
│                                                                                         │
│   ✓ Identify primary vs secondary purposes                                             │
│   ✓ Classify based on primary purpose                                                  │
│   ✓ Note secondary capabilities in documentation                                      │
│   ✗ Don't create new hybrid types without justification                               │
│                                                                                         │
│   Example: A platform with workflow capabilities is still a PLATFORM (primary)        │
│                                                                                         │
│ PRACTICE 5: Document Classification Rationale                                           │
│                                                                                         │
│   ✓ Record the decision path taken                                                     │
│   ✓ Note any ambiguous characteristics                                                 │
│   ✓ Provide justification for edge cases                                               │
│   ✗ Don't classify without documentation                                               │
│                                                                                         │
│   Example: Document why a system was classified as X vs Y                             │
│                                                                                         │
│ PRACTICE 6: Re-evaluate When System Evolves                                            │
│                                                                                         │
│   ✓ Review classification when system architecture changes                              │
│   ✓ Update classification if primary purpose changes                                   │
│   ✗ Don't assume classification is permanent                                           │
│                                                                                         │
│   Example: A CLI tool that gains a web UI may become a WEB APPLICATION               │
│                                                                                         │
│ PRACTICE 7: Use Consistent Terminology                                                 │
│                                                                                         │
│   ✓ Use the same terms as the ontology                                                 │
│   ✓ Avoid local terminology or abbreviations                                            │
│   ✗ Don't create custom type names without justification                              │
│                                                                                         │
│   Example: Use "API SERVICE" not "REST API" or "Microservice"                         │
│                                                                                         │
│ PRACTICE 8: Consider Multiple Perspectives                                             │
│                                                                                         │
│   ✓ Consider how different users interact with the system                              │
│   ✓ Classify based on overall system, not individual components                        │
│   ✗ Don't let component diversity drive system classification                         │
│                                                                                         │
│   Example: A web app with worker processes is still a WEB APPLICATION                 │
