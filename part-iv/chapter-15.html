20  Architecture Style Taxonomy (v0.1)

While system types classify what kind of system exists, architectural styles describe how the internal structure of that system is organized. An architecture style represents a recurring structural arrangement of components, interfaces, and interaction patterns.

Architectural styles capture higher-level design strategies that shape the organization of software systems. These strategies influence how responsibilities are distributed, how components interact, and how systems evolve over time.

Within the ontology, architecture styles function as structural descriptors that characterize the dominant organization pattern of a system.

20.0.1 Layered Architecture

Layered architecture organizes components into hierarchical layers, where each layer performs a specific responsibility and interacts primarily with adjacent layers.

Typical layers include:

  • presentation or interface layer

  • application or service layer

  • domain logic layer

  • data persistence layer

In layered systems, dependencies typically flow in one direction—from higher layers toward lower layers. This structure promotes separation of concerns and simplifies reasoning about system organization.

Layered architectures are commonly found in enterprise applications, web services, and traditional backend systems.

Example: E-commerce Layered Architecture

┌─────────────────────────────────────────┐
│  Presentation Layer                     │
│  (Web UI, Mobile App)                   │
└────────────┬────────────────────────────┘
             │ HTTP calls
┌────────────▼────────────────────────────┐
│  Application Layer                       │
│  (Order Service, User Service)           │
└────────────┬────────────────────────────┘
             │ Business logic
┌────────────▼────────────────────────────┐
│  Domain Layer                           │
│  (Order Domain, User Domain)            │
└────────────┬────────────────────────────┘
             │ Domain models
┌────────────▼────────────────────────────┐
│  Data Layer                             │
│  (Database, Cache, File Storage)       │
└─────────────────────────────────────────┘

Benefits:
  - Clear separation of concerns
  - Easy to understand
  - Testable layers
  - Reusable components

Challenges:
  - Can become rigid
  - Performance overhead
  - Changes ripple across layers
  - May not fit all systems

20.0.2 Modular Monolith

A modular monolith is a system that runs as a single deployable unit while maintaining strong internal modular boundaries.

In this architecture style, components are organized into modules that encapsulate distinct responsibilities. These modules interact through well-defined interfaces but are packaged and deployed as a single application.

The modular monolith balances two objectives:

  • strong internal structure and separation of responsibilities

  • operational simplicity through single-unit deployment

This style is often used in systems that require clear modularity but do not yet require distributed deployment.

Example: Modular Monolith E-commerce System

Single Application:
  ├── Module: User Management
  │   ├── User API
  │   ├── User Logic
  │   └── User Storage
  │
  ├── Module: Order Processing
  │   ├── Order API
  │   ├── Order Logic
  │   └── Order Storage
  │
  ├── Module: Payment Processing
  │   ├── Payment API
  │   ├── Payment Logic
  │   └── Payment Storage
  │
  └── Module: Inventory Management
      ├── Inventory API
      ├── Inventory Logic
      └── Inventory Storage

Benefits:
  - Simpler deployment
  - Easier testing
  - Clear module boundaries
  - Good starting point

Challenges:
  - Scaling limitations
  - Single point of failure
  - Module independence
  - Technology constraints

When to use:
  - Small to medium teams
  - Simple deployment needs
  - Rapid development
  - Monolithic simplicity needed

20.0.3 Microservices

Microservice architectures decompose systems into independently deployable services that communicate through network interfaces.

Each service typically encapsulates a specific capability and maintains control over its own data and runtime environment.

Key characteristics of microservice architectures include:

  • service-level deployment boundaries

  • network-based communication between components

  • independent scaling of services

  • decentralized data ownership

Microservice architectures increase system flexibility and scalability but introduce additional operational complexity.

Example: E-commerce Microservices

Service A: User Service
  - Manages user accounts
  - Exposes user API
  - Owns user database

Service B: Order Service
  - Processes orders
  - Exposes order API
  - Owns order database

Service C: Inventory Service
  - Manages inventory
  - Exposes inventory API
  - Owns inventory database

Service D: Payment Service
  - Processes payments
  - Exposes payment API
  - Owns transaction database

Communication:
  - HTTP/gRPC APIs
  - Event-driven messaging
  - Service discovery
  - API gateway routing

Benefits:
  - Independent scaling
  - Technology diversity
  - Fault isolation
  - Team autonomy

Challenges:
  - Operational complexity
  - Distributed systems challenges
  - Network overhead
  - Data consistency

When to use:
  - Large systems
  - Multiple teams
  - Independent scaling needs
  - Technology diversity

20.0.4 Event-Driven Architecture

Event-driven architectures organize system behavior around asynchronous event propagation.

In this style, components emit events that describe state changes or completed operations. Other components react to these events without requiring direct invocation relationships.

Event-driven systems often include components such as event producers, message brokers, and event consumers.

This architectural style enables temporal decoupling between components and supports high scalability in distributed environments.

Example: Event-Driven Order System

Event Producers:
  - Order Service emits: OrderCreated, OrderCancelled
  - Payment Service emits: PaymentCompleted, PaymentFailed
  - Shipping Service emits: OrderShipped, OrderDelivered

Message Broker:
  - Kafka topic: orders
  - Kafka topic: payments
  - Kafka topic: shipments

Event Consumers:
  - Inventory Service consumes OrderCreated
  - Email Service consumes OrderCreated, OrderShipped
  - Analytics Service consumes all events
  - Notification Service consumes OrderDelivered

Benefits:
  - Loose coupling
  - Temporal decoupling
  - Scalability
  - Flexibility

Challenges:
  - Eventual consistency
  - Debugging complexity
  - Event ordering
  - Consumer failure handling

When to use:
  - High throughput needed
  - Loose coupling desired
  - Multiple consumers
  - Async processing needed

20.0.5 Pipeline Architecture

Pipeline architectures organize computation as a sequence of processing stages through which data flows.

Each stage performs a transformation on the incoming data before passing it to the next stage. Pipelines may operate on batch datasets or continuous data streams.

This style is commonly used in:

  • data processing systems

  • analytics pipelines

  • machine learning workflows

  • media processing systems

Pipeline architectures emphasize data flow as the organizing principle of the system.

Example: Data Analytics Pipeline

Stage 1: Ingestion
  - Collects data from sources
  - Validates data format
  - Writes to staging area

Stage 2: Transformation
  - Cleans data
  - Applies business rules
  - Enriches data

Stage 3: Aggregation
  - Aggregates metrics
  - Computes summaries
  - Generates insights

Stage 4: Storage
  - Writes to warehouse
  - Updates indexes
  - Creates reports

Data Flow:
  Source → Ingestion → Transformation → Aggregation → Storage

Benefits:
  - Clear data flow
  - Modular stages
  - Easy to monitor
  - Scalable stages

Challenges:
  - Sequential bottlenecks
  - Error handling
  - Backpressure
  - Stage compatibility

When to use:
  - Data processing
  - Analytics workflows
  - ETL processes
  - ML pipelines

20.0.6 Plugin-Based Architecture

Plugin-based architectures support extensibility through dynamically loadable components.

The core system defines extension points that allow external modules or plugins to introduce additional functionality without modifying the core system.

This style is commonly found in:

  • development tools and editors

  • platform ecosystems

  • extensible frameworks

Plugin architectures enable flexible extension mechanisms and support ecosystem-driven development models.

Example: IDE Plugin System

Core IDE:
  - Editor component
  - Syntax highlighting
  - File management
  - UI framework

Extension Points:
  - Language support plugins
  - Build system plugins
  - Version control plugins
  - Code analysis plugins

Plugin Examples:
  - Python Language Plugin
  - Maven Build Plugin
  - Git Integration Plugin
  - Linting Plugin

Plugin Interface:
  - Plugin lifecycle (load, initialize, activate)
  - Extension point registration
  - Service provision
  - UI integration

Benefits:
  - Extensibility
  - Third-party ecosystem
  - Customization
  - Modularity

Challenges:
  - Plugin compatibility
  - Security concerns
  - Version management
  - Quality control

When to use:
  - Extensibility needed
  - Third-party developers
  - Platform products
  - Tool frameworks

20.0.7 Hybrid Architectures

In practice, many systems combine elements from multiple architectural styles.

A system may, for example, combine microservices with event-driven communication, or embed pipeline processing stages within a layered application structure.

These systems are referred to as hybrid architectures.

Hybrid architectures arise because architectural styles represent design patterns rather than strict constraints. Systems often adopt multiple patterns to address different operational requirements.

Recognizing hybrid architectures is therefore essential for accurate architectural representation.

Example: Hybrid E-commerce Platform

Primary Style: Microservices
  - Independent services for different domains
  - Network-based communication
  - Independent deployment

Secondary Style: Event-Driven
  - Services communicate via events
  - Asynchronous processing
  - Loose coupling between services

Tertiary Style: Layered (within services)
  - Each service has layered structure
  - Presentation, application, data layers
  - Internal modularity

Result: System combines multiple architectural styles to address different needs:
  - Microservices for independent scaling
  - Event-driven for loose coupling
  - Layered for internal structure

20.0.8 Identifying Architecture Styles

Architecture styles can often be inferred from structural signals present in code repositories, configuration files, and system entry points.

Several types of signals are particularly useful for this purpose.

Repository structure

The organization of directories and modules can indicate architectural style. For example, layered directory structures may indicate layered architectures, while service-based repository structures may suggest microservices.

Dependency patterns

The dependency graph between modules or packages may reveal architectural boundaries and interaction structures.

Entry points

The presence of multiple independent service entry points may indicate a microservice architecture, while a single primary entry point may indicate a monolithic system.

Messaging infrastructure

Configuration files referencing message brokers or event streams may indicate event-driven architectures.

These structural signals form the basis for automated architecture detection methods introduced in later volumes of the series, particularly in the context of Blueprint Extraction.

By identifying architectural styles through observable structural patterns, blueprint representations can classify and analyze large collections of systems with greater consistency and accuracy.

20.1 Summary

Architecture styles describe how the internal structure of a system is organized — they are recurring structural arrangements of components, interfaces, and interaction patterns. Unlike system types (which classify what kind of system), styles describe how it is organized internally. In practice, many systems are hybrid architectures that combine elements from multiple styles.

20.1.1 Core Knowledge — Must Remember

Style Organization Principle Benefits Challenges
Layered Components organized into hierarchical layers; dependencies flow downward Separation of concerns, testability, reusability Can become rigid; performance overhead across layers
Modular Monolith Single deployable unit with strong internal module boundaries Simple deployment, clear boundaries, good starting point Scaling limitations, single point of failure
Microservices Independently deployable services with network-based communication Independent scaling, team autonomy, fault isolation Operational complexity, distributed systems challenges, data consistency
Event-Driven Behavior organized around asynchronous event propagation Loose coupling, temporal decoupling, high scalability Eventual consistency, debugging complexity, event ordering
Pipeline Sequential processing stages through which data flows Clear data flow, modular stages, easy to monitor Sequential bottlenecks, backpressure management
Plugin-Based Core system with dynamically loadable extension modules Extensibility, third-party ecosystem, customization Plugin compatibility, version management, security
