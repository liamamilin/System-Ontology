21  Pattern Hooks: Making Ontology Pattern-Aware

Architectural patterns represent reusable structural solutions that appear repeatedly across software systems. While the ontology defines the fundamental entities and relations used to describe systems, patterns capture recurring arrangements of those entities and relations.

For the Blueprint Architecture framework to support pattern discovery, pattern reuse, and architecture intelligence, the ontology must be pattern-aware. This means that the ontology should not only represent system structures but also provide the structural anchors necessary for identifying and describing recurring architectural patterns.

Pattern hooks serve this role. They connect the ontology representation of systems with the pattern catalog introduced in later volumes of the series.

21.0.1 Patterns as Reusable Structural Fragments

A pattern can be understood as a reusable fragment of system structure that solves a recurring architectural problem.

Patterns do not represent entire systems. Instead, they capture partial configurations of components, interfaces, workflows, and relations that appear repeatedly in many systems.

Examples include structures such as:

  • API gateway routing patterns

  • event producer–consumer pipelines

  • background worker processing loops

  • cache-aside data access patterns

  • workflow orchestration structures

Patterns are therefore structural templates that can be embedded into larger system architectures.

Within the ontology, patterns are not treated as primitive entities. Instead, they are expressed as subgraphs of the ontology structure.

21.0.2 Pattern Hooks

For patterns to be identifiable within system architectures, the ontology must define pattern hooks.

A pattern hook is an entity or relation type that frequently serves as the anchor point of a pattern structure. Hooks provide stable structural signals that indicate where a pattern may exist within a system.

Typical pattern hooks include:

  • component types such as API gateways, workers, or schedulers

  • relation types such as invocation, event emission, or data access

  • workflow entities that coordinate task execution

  • interface entities representing interaction boundaries

For example, the presence of an API gateway component combined with routing interfaces and service dependencies may indicate a gateway pattern. Similarly, the combination of event emission and event consumption relations may indicate an event-driven processing pattern.

By defining these hooks explicitly, the ontology allows pattern detection mechanisms to operate on architectural graphs.

21.1 Pattern Hook Examples

21.1.1 Gateway Pattern Hook

Pattern: API Gateway

Ontology Hook:
  - Component type: api_gateway
  
Structural Signature:
  System contains:
    - Component: API Gateway
    - Multiple Services behind gateway
    - Relations: Gateway routes to services
  
Example Detection:
  1. Identify api_gateway component
  2. Check if it has routing configuration
  3. Identify services behind gateway
  4. Verify gateway implements interface

Ontology Representation:
  comp.api_gateway (api_gateway)
    implements int.api_public
    routes_to comp.service_a
    routes_to comp.service_b
    routes_to comp.service_c

Use Case:
  - Unified API entry point
  - Request routing
  - Cross-cutting concerns (auth, rate limiting)

21.1.2 CQRS Pattern Hook

Pattern: Command Query Responsibility Segregation

Ontology Hooks:
  - Component types: read_service, write_service
  - Data access relations: reads, writes
  
Structural Signature:
  - Separate read and write components
  - Different data stores for read/write
  - Interface separation for commands/queries
  
Example Detection:
  1. Identify read_service and write_service components
  2. Check if they access different data stores
  3. Verify command/query interface separation
  4. Confirm eventual consistency model

Ontology Representation:
  comp.order_read_service (read_service)
    reads data.order_read_db
  
  comp.order_write_service (write_service)
    writes data.order_write_db
  
  int.command_interface (interface)
  int.query_interface (interface)

Use Case:
  - High-read systems
  - Complex business logic
  - Performance optimization

21.1.3 Event Sourcing Pattern Hook

Pattern: Event Sourcing

Ontology Hooks:
  - Event entities and relations
  - Event store component
  - Event replay capability
  
Structural Signature:
  - Components emit events for all state changes
  - Event store persists event stream
  - State reconstructed from events
  - Event replay for debugging/analysis
  
Example Detection:
  1. Identify event store component
  2. Check for comprehensive event emission
  3. Verify state reconstruction capability
  4. Confirm event replay functionality

Ontology Representation:
  comp.event_store (storage)
    stores events.domain_events
  
  comp.order_service (api_service)
    emits events.OrderCreated
    emits events.OrderUpdated
    emits events.OrderCancelled
  
  wf.state_reconstruction (workflow)
    replays events from event_store

Use Case:
  - Audit trails
  - Temporal queries
  - Event replay
  - Debugging

21.1.4 Circuit Breaker Pattern Hook

Pattern: Circuit Breaker

Ontology Hooks:
  - Circuit breaker component
  - Relation types: calls, fallback
  - Interface definitions
  
Structural Signature:
  - Circuit breaker between caller and callee
  - Fallback mechanism on failure
  - State tracking (open, closed, half-open)
  - Health monitoring
  
Example Detection:
  1. Identify circuit breaker component
  2. Check for fallback relations
  3. Verify state tracking
  4. Confirm health monitoring

Ontology Representation:
  comp.circuit_breaker (orchestrator)
    monitors comp.service_a
    calls comp.service_a (when closed)
    calls comp.fallback_service (when open)
    tracks state: [open, closed, half-open]

Use Case:
  - Failure isolation
  - Graceful degradation
  - System resilience
  - Cascading failure prevention

21.1.5 Saga Pattern Hook

Pattern: Saga (Distributed Transaction)

Ontology Hooks:
  - Workflow entities
  - Compensating actions
  - Transaction coordination
  
Structural Signature:
  - Multi-step workflow
  - Compensating actions for each step
  - Transaction coordinator
  - Event-based communication
  
Example Detection:
  1. Identify saga workflow
  2. Check for compensating actions
  3. Verify transaction coordinator
  4. Confirm event-based step coordination

Ontology Representation:
  wf.order_saga (workflow)
    contains step.charge_payment
    contains step.reserve_inventory
    contains step.update_order
  
  step.charge_payment
    succeeds: emit PaymentCompleted
    fails: emit PaymentFailed (triggers refund)
  
  step.reserve_inventory
    succeeds: emit InventoryReserved
    fails: emit InventoryFailed (triggers release)
  
  step.update_order
    succeeds: emit OrderCompleted
    fails: emit OrderCancelled

Use Case:
  - Distributed transactions
  - Long-running transactions
  - Compensation logic
  - Event-driven coordination

21.1.6 Repository Pattern Hook

Pattern: Repository

Ontology Hooks:
  - Repository components
  - Domain entity mapping
  - Data access encapsulation
  
Structural Signature:
  - Repository per domain entity
  - Encapsulates data access logic
  - Provides CRUD operations
  - Hides data source details
  
Example Detection:
  1. Identify repository components
  2. Check domain entity association
  3. Verify CRUD operation interfaces
  4. Confirm data source encapsulation

Ontology Representation:
  comp.user_repository (worker)
    manages data.user
    implements int.repository_interface
  
  int.repository_interface
    provides create(), read(), update(), delete()
    returns/accepts user entities

Use Case:
  - Data access abstraction
  - Testability
  - Data source independence
  - Domain model focus

21.1.7 Strategy Pattern Hook

Pattern: Strategy

Ontology Hooks:
  - Strategy components
  - Context component
  - Strategy selection logic
  
Structural Signature:
  - Context component uses strategy
  - Multiple strategy implementations
  - Runtime strategy selection
  - Common interface
  
Example Detection:
  1. Identify context component
  2. Check for multiple strategy implementations
  3. Verify common interface
  4. Confirm runtime selection

Ontology Representation:
  comp.payment_context (engine)
    uses int.payment_strategy
  
  comp.credit_card_strategy (policy)
    implements int.payment_strategy
  
  comp.paypal_strategy (policy)
    implements int.payment_strategy
  
  comp.bank_transfer_strategy (policy)
    implements int.payment_strategy

Use Case:
  - Algorithm variations
  - Runtime behavior selection
  - Policy implementation
  - Testability

21.1.8 Publish-Subscribe Pattern Hook

Pattern: Publish-Subscribe

Ontology Hooks:
  - Publisher components
  - Subscriber components
  - Topic/channel components
  - Event relations
  
Structural Signature:
  - Publishers emit events to topics
  - Subscribers consume from topics
  - Message broker coordinates
  - Multiple subscribers per topic
  
Example Detection:
  1. Identify message broker
  2. Check for event emission/consumption
  3. Verify topic/channel structure
  4. Confirm multiple subscribers

Ontology Representation:
  comp.message_broker (broker)
    manages topic.orders
    manages topic.payments
  
  comp.order_service (api_service)
    emits events.OrderCreated to topic.orders
  
  comp.inventory_service (worker)
    consumes from topic.orders
  
  comp.email_service (worker)
    consumes from topic.orders

Use Case:
  - Event distribution
  - Loose coupling
  - Multiple consumers
  - Scalability

21.1.9 Observer Pattern Hook

Pattern: Observer

Ontology Hooks:
  - Subject components
  - Observer components
  - Notification relations
  
Structural Signature:
  - Subject maintains observer list
  - Observers register with subject
  - Subject notifies observers of changes
  - Observers react to notifications
  
Example Detection:
  1. Identify subject component
  2. Check for observer registration
  3. Verify notification mechanism
  4. Confirm observer reactions

Ontology Representation:
  comp.user_account (component)
    maintains state: user_profile
    notifies observers on changes
  
  comp.profile_observer (worker)
    observes comp.user_account
    reacts to state changes
  
  comp.analytics_observer (worker)
    observes comp.user_account
    tracks metrics

Use Case:
  - State change notifications
  - Reactive systems
  - UI updates
  - Event handling

21.1.10 Pattern Signatures

To represent patterns within the ontology framework, each pattern can be described through a pattern signature.

A pattern signature defines the structural configuration that characterizes the pattern. It typically includes:

  • a set of entity types

  • a set of relations between those entities

  • optional constraints on interaction or data flow

In ontology terms, a pattern signature corresponds to a subgraph structure that can be matched against system architecture graphs.

For example, an event processing pattern might be expressed through the following structural signature:

  • a producer component

  • an event interface

  • a message broker component

  • one or more consumer components

  • emission and consumption relations connecting these entities

When such a subgraph appears in a system architecture, the pattern can be recognized and classified.

Pattern signatures therefore provide a formal representation of architectural patterns that can be analyzed computationally.

21.1.11 Bridging Ontology and the Pattern Catalog

While the ontology defines the language used to describe system structures, the pattern catalog defines the library of reusable architectural solutions.

Pattern hooks and pattern signatures provide the bridge between these two layers.

The process operates as follows.

First, the ontology provides a consistent representation of system architecture as a graph of entities and relations.

Second, pattern signatures define structural subgraphs that correspond to known architectural patterns.

Third, pattern detection mechanisms identify occurrences of these signatures within blueprint representations.

Once patterns are identified, they can be recorded in a pattern catalog, which documents the architectural problem addressed by the pattern, the structural configuration involved, and the trade-offs associated with its use.

This connection allows architectural knowledge to accumulate across systems. Instead of analyzing each architecture independently, blueprint datasets can reveal recurring structural patterns and design strategies.

By making the ontology pattern-aware, the Blueprint Architecture framework establishes the foundation for systematic pattern discovery, pattern reuse, and architecture intelligence.

21.2 Summary

Pattern hooks make the ontology pattern-aware — they provide the structural anchors necessary for identifying and describing recurring architectural patterns. A pattern is a reusable subgraph (components, interfaces, relations) within the ontology structure, not a separate entity type. A pattern signature defines the structural configuration that characterizes a pattern — a subgraph that can be matched against system architecture graphs.

21.2.1 Core Knowledge — Must Remember

Concept Key Insight
Pattern = reusable subgraph Patterns are not primitive entities in the ontology. They are expressed as subgraphs of the ontology structure — recurring configurations of components, interfaces, workflows, and relations.
Pattern hooks Specific entity or relation types that serve as anchor points for pattern detection (e.g., api_gateway component type for the Gateway pattern, emits/consumes relations for event-driven patterns).
Pattern signatures A formal description of the structural configuration that characterizes a pattern: a set of entity types, a set of relations between them, and optional constraints. Signatures can be matched computationally against architectural graphs.
Pattern catalog bridge Ontology → Pattern Signatures → Pattern Detection → Pattern Catalog. The ontology provides the language; signatures provide the detection mechanism; the catalog stores the documented solutions.
Examples of pattern hooks API Gateway (gateway pattern), CQRS (read_service + write_service + separate data stores), Event Sourcing (event store + comprehensive event emission), Circuit Breaker (circuit breaker component + fallback relations), Saga (workflow + compensating actions), Publish-Subscribe (broker + publishers + subscribers).

The connection between ontology and pattern catalog enables architectural knowledge to accumulate across systems — blueprint datasets reveal recurring structural patterns and design strategies that no single system analysis could discover.
