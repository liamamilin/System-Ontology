4  Notation & Conventions

This volume introduces a formal ontology for describing software systems. To ensure conceptual clarity and consistency across chapters, a small set of core notational conventions is used throughout the text.

These conventions define how system structures are expressed and how different levels of abstraction are represented. Understanding these conventions is essential for correctly interpreting the diagrams, examples, and formal definitions presented in this book.

4.1 Why Conventions Matter

In technical writing, especially in works introducing new conceptual frameworks, consistent notation serves several critical purposes:

  • Precision: Eliminates ambiguity in how concepts are described
  • Communication: Provides a shared language for discussing architectural structures
  • Analysis: Enables formal reasoning about architectural properties
  • Automation: Supports machine processing of architectural descriptions

Without these conventions, readers might interpret diagrams and definitions differently, leading to misunderstandings and inconsistent application of the ontology.

4.2 The Core Conceptual Framework

The ontology is built on four fundamental conceptual building blocks:

┌─────────────────────────────────────────────────────────┐
│              Ontology Conceptual Framework               │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Entities  →  The "things" that exist in systems        │
│  Relations  →  How entities connect and interact        │
│  Attributes →  Properties that describe entities        │
│  Constraints→  Rules that govern system behavior        │
│                                                         │
└─────────────────────────────────────────────────────────┘

In addition to these core elements, the ontology supports several structural concepts that help organize and present architectural knowledge: Views, Layers, Granularity, and Projections.

Let us examine each of these in detail.

4.3 Entity

An Entity represents a distinct conceptual element that exists within a system.

4.3.1 Definition

Entities correspond to identifiable architectural elements such as components, interfaces, data objects, workflows, or capabilities. Each entity represents something that can be described, referenced, and related to other entities within the ontology.

4.3.2 Role in the Ontology

Entities form the nodes of the system representation graph. They are the nouns of the architectural language—the things we can point to, name, and describe.

4.3.3 Examples

Common entities include:

  • System: The bounded architectural unit with a defined goal
  • Component: A structural building block that encapsulates responsibilities
  • Interface: An interaction boundary through which components communicate
  • Capability: A functional ability that the system provides
  • Data Entity: A structured unit of information managed by the system
  • Workflow: A coordinated sequence of execution steps
  • Constraint: A requirement or quality attribute

4.3.4 Properties

Every entity has the following inherent properties:

  • Identity: A unique identifier that distinguishes it from other entities
  • Type: The entity category (e.g., Component, Interface, Workflow)
  • Name: A human-readable label for the entity
  • Description: An explanation of the entity’s role and purpose

Entities may also have additional attributes specific to their type, discussed below.

4.3.5 Visual Representation

In architectural diagrams, entities are typically represented as:

┌─────────────────┐
│   Entity Name   │
│   (Type)        │
└─────────────────┘

For example:

┌─────────────────┐
│   Order Service │
│   (Component)   │
└─────────────────┘

4.4 Attribute

An Attribute describes a property of an entity.

4.4.1 Definition

Attributes provide structured metadata that characterizes an entity without introducing new structural elements into the system model. They capture information such as identifiers, responsibilities, configuration parameters, or descriptive properties.

4.4.2 Role in the Ontology

Attributes enable entities to be precisely described while keeping the ontology compact. They provide detail without complexity.

4.4.3 Key Principle

Attributes do not create new entities; they only describe existing ones.

This distinction is crucial. For example, “version” is an attribute of a component, not a separate entity. We don’t create a “Version” entity—we simply record the version number as an attribute of the component.

4.4.4 Examples

Typical attributes include:

  • name: The human-readable identifier
  • type: The entity category
  • description: A textual explanation
  • version: The current version number
  • owner: The team or individual responsible
  • lifecycle_status: The current state (e.g., active, deprecated)

4.4.5 Visual Representation

Attributes are typically shown as properties within an entity diagram:

┌─────────────────────────┐
│   Order Service         │
│   (Component)           │
│   ───────────────────   │
│   version: 2.1.0        │
│   owner: payments team  │
│   status: active        │
└─────────────────────────┘

Additional example with multiple attributes:

┌─────────────────────────────┐
│   User Authentication        │
│   (Component)               │
│   ───────────────────────   │
│   component_type: api_service│
│   responsibility: auth       │
│   statefulness: stateless    │
│   inputs: credentials       │
│   outputs: tokens           │
└─────────────────────────────┘

4.5 Relation

A Relation describes a structured connection between two or more entities.

4.5.1 Definition

Relations define how architectural elements interact, depend on each other, or form part of a larger structure. Unlike attributes, relations introduce explicit structural semantics into the system model.

4.5.2 Role in the Ontology

Relations form the edges of the system representation graph. They are the verbs of the architectural language—how entities act on and relate to each other.

4.5.3 Examples

Examples of relations include:

  • contains / part_of: Structural composition
  • depends_on: Dependency relationships
  • calls / invokes: Invocation relationships
  • emits / consumes: Event relationships
  • reads / writes: Data access relationships
  • implements / conforms_to: Contract compliance

4.5.4 Properties

Relations have the following properties:

  • Type: The kind of relationship (e.g., contains, depends_on)
  • Direction: Whether the relationship is directed (A→B) or undirected
  • Source: The entity initiating the relationship
  • Target: The entity receiving the relationship
  • Cardinality: How many instances can participate (one-to-one, one-to-many, etc.)

4.5.5 Visual Representation

Relations are typically shown as arrows connecting entities:

┌───────────┐          ┌───────────┐
│ Component │ ────>   │ Interface │
│    A      │  calls  │    B      │
└───────────┘          └───────────┘

Different relation types may use different arrow styles to distinguish them.

Additional examples:

Dependency relation:
┌─────────────┐         depends_on          ┌─────────────┐
│ Order       │ ───────────────────────>   │ Inventory   │
│ Service     │                            │ Service     │
└─────────────┘                            └─────────────┘

Event relation:
┌─────────────┐       emits       ┌─────────────┐
│ Order       │ ────────────────> │ Order Placed│
│ Service     │                   │   Event     │
└─────────────┘                   └─────────────┘
                                        │
                                        │ consumes
                                        ↓
                                ┌─────────────┐
                                │ Payment     │
                                │ Service     │
                                └─────────────┘

Data access relation:
┌─────────────┐       reads       ┌─────────────┐
│ Analytics   │ ────────────────> │ Orders DB   │
│ Engine      │                   └─────────────┘
└─────────────┘

4.6 Constraint

A Constraint represents a condition or requirement that restricts the behavior or structure of a system.

4.6.1 Definition

Constraints typically encode non-functional requirements or operational limitations. They define measurable conditions that must be satisfied by a system, component, or interface.

4.6.2 Role in the Ontology

By representing constraints as explicit ontology elements, system requirements become analyzable and attachable to architectural structures. This transforms quality attributes from narrative descriptions into formal, enforceable conditions.

4.6.3 Structure

A constraint typically contains three core elements:

  1. Metric: What is being measured
    • Examples: latency, availability, throughput, error rate
  2. Threshold: The acceptable limit or target value
    • Examples: ≤300ms, ≥99.9%, 1000 req/sec, <0.1%
  3. Scope: The entity to which the constraint applies
    • Can be system, component, interface, or workflow level

4.6.4 Examples

  • Performance: “API response time must be ≤300ms (p95)”
  • Reliability: “System availability must be ≥99.9%”
  • Security: “All data must be encrypted at rest”
  • Compliance: “User data must be retained for 7 years”

4.6.5 Visual Representation

Constraints are often shown attached to the entity they govern:

┌─────────────────┐
│   API Service   │
│                 │
│   ┌───────────┐ │
│   │ latency   │ │
│   │ ≤ 300ms   │ │
│   └───────────┘ │
└─────────────────┘

Additional examples:

│                         │

4.7 View

A View is a representation of a system that focuses on a particular concern or audience.

4.7.1 Definition

Different stakeholders require different perspectives on the same system. Views allow the same underlying ontology instance to be projected into representations optimized for different purposes.

4.7.2 Why Views Matter

No single representation can serve all needs:

  • Architects need to understand component dependencies and data flows
  • Product managers need to understand capabilities and user interactions
  • Operators need to understand deployment topology and monitoring
  • Security analysts need to understand trust boundaries and access controls

Views allow all these perspectives to be derived from the same underlying ontology.

4.7.3 Common Views

  • Architecture View: Focuses on structural relationships between components, interfaces, and data flows
  • Specification View: Focuses on system capabilities, interfaces, and behavioral requirements
  • Operations View: Focuses on runtime behavior, deployment topology, and operational concerns
  • Deployment View: Focuses on how components are instantiated and distributed across infrastructure
  • Security View: Focuses on trust boundaries, authentication, and authorization

4.7.4 Visual Representation

Views are often shown as filtered projections of the full ontology:

Full Ontology Graph
        ↓
    [Filter]
        ↓
Architecture View (components, interfaces, dependencies)
        ↓
Specification View (capabilities, contracts, constraints)
        ↓
Operations View (runtime, triggers, reliability)

4.8 Layer

A Layer represents a structural level within a system architecture.

4.8.1 Definition

Layers organize entities into hierarchical or conceptual strata that reflect responsibility boundaries. Layering is commonly used to separate concerns such as user interaction, application logic, data management, and infrastructure.

4.8.2 Typical Layers

Common architectural layers include:

  • Presentation Layer / Interface Layer: User interfaces and external interaction points
  • Application Layer / Service Layer: Business logic and application services
  • Domain Layer: Core business rules and domain models
  • Data Layer / Persistence Layer: Data storage and access mechanisms
  • Infrastructure Layer: External services, messaging systems, and platform services

4.8.3 Layering Principles

Effective layering follows these principles:

  1. Unidirectional dependencies: Dependencies typically flow downward (presentation → application → data)
  2. Clear boundaries: Each layer has a well-defined responsibility
  3. Minimal coupling: Layers interact through defined interfaces
  4. Independent evolution: Layers can evolve independently to some degree

4.8.4 Visual Representation

Layers are typically shown as horizontal bands:

┌─────────────────────────────────┐
│     Presentation Layer          │
│  (UI, CLI, API Gateway)         │
├─────────────────────────────────┤
│     Application Layer           │
│  (Services, Workflows)          │
├─────────────────────────────────┤
│     Domain Layer                │
│  (Business Logic, Models)       │
├─────────────────────────────────┤
│     Data Layer                  │
│  (Databases, Caches, Queues)    │
├─────────────────────────────────┤
│     Infrastructure Layer        │
│  (External Services, Platform)   │
└─────────────────────────────────┘

4.9 Granularity

Granularity describes the level of detail at which a system is represented.

4.9.1 Definition

The ontology supports multiple levels of granularity so that the same system can be described at different scales. Different tasks require different levels of detail.

4.9.2 Granularity Levels

Typical granularity levels include:

  • System level: The entire application or platform as a single unit
  • Subsystem level: Major functional areas or modules within the architecture
  • Component level: Deployable or logically independent units
  • Module level: Internal groupings within components
  • Function level: Individual routines or methods

4.9.3 Choosing the Right Level

The appropriate level of granularity depends on the purpose:

Purpose Recommended Level
Portfolio management System level
Integration planning Subsystem level
Architecture design Component level
Implementation Module level
Performance analysis Function level

4.9.4 Practical Boundary

Within the Blueprint Architecture framework, the component level serves as the typical boundary for architectural description.

Below this level, structural knowledge tends to become implementation-specific. Function-level representations often belong to source code analysis rather than architecture representation.

Maintaining this boundary preserves the purpose of the blueprint: representing system architecture, not program implementation.

4.9.5 Visual Representation

Granularity can be shown as a hierarchy of detail:

System (Level 1)
    ↓
    ├── Subsystem A (Level 2)
    │   ↓
    │   ├── Component A1 (Level 3)
    │   └── Component A2 (Level 3)
    │
    └── Subsystem B (Level 2)
        ↓
        └── Component B1 (Level 3)

4.10 Projection

A Projection is a derived representation generated from the underlying ontology model.

4.10.1 Definition

Projections reorganize entities and relations into formats suited for specific tasks such as documentation, specification, visualization, or operational analysis.

4.10.2 Projections vs. Views

While related, projections and views serve different purposes:

  • Views emphasize perspective—what aspects are shown to which audience
  • Projections emphasize format—how the information is transformed for a specific purpose

Think of it this way:

A view selects a subset of the ontology for a particular audience. A projection transforms that subset into a specific format.

4.10.3 Examples

Examples of projections include:

  • Blueprint kernel views: Mapping ontology entities to the six-slot blueprint structure
  • Architectural diagrams: Visual representations of component structures and relationships
  • Specification documents: Human-readable descriptions of capabilities and interfaces
  • Dependency graphs: Focused views showing only dependency relationships
  • Operational dashboards: Real-time views of system state and metrics
  • Code generation templates: Transforming ontology into implementation code

4.10.4 Projection Pipeline

Ontology Instance
        ↓
    [Mapping Rules]
        ↓
Blueprint Kernel
        ↓
    [Projection Filters]
        ↓
Multiple Projections
    ├── Architecture Diagram
    ├── Specification Document
    ├── Dependency Graph
    └── Operational Dashboard

4.10.5 Benefits

Projections provide several key benefits:

  1. Single source of truth: All representations derive from the same ontology
  2. Consistency: Different views are guaranteed to be consistent
  3. Automation: Projections can be generated automatically
  4. Flexibility: New projections can be added without modifying the ontology

4.11 Putting It All Together

  • An order service for processing orders
  • A payment service for handling transactions
  • A database for storing orders

4.11.1.9 Views

Architecture View: Shows component structure and dependencies
Specification View: Shows capabilities and API contracts
Operations View: Shows deployment topology and monitoring

Architecture View example: - Focuses on: Components, Interfaces, Relations, Data Flow - Shows: How components connect, depend on each other, and exchange data - Used by: System architects, developers

Operations View example: - Focuses on: Runtime, Triggers, Reliability, Dependencies - Shows: How the system is deployed, how it scales, and how failures are handled - Used by: DevOps engineers, SREs

4.12 Summary of Conventions

Concept Purpose Example
Entity Represents architectural elements Component, Interface, Workflow
Attribute Describes entity properties version, owner, status
Relation Connects entities contains, depends_on, calls
Constraint Governs behavior or structure latency ≤ 300ms
View Focuses on perspective Architecture View, Ops View
Layer Organizes by responsibility Presentation, Application, Data
Granularity Controls detail level System, Subsystem, Component
Projection Transforms for specific use Diagrams, Specifications, Dashboards

These conventions establish the basic language used throughout this volume. Entities and relations describe what exists in a system and how those elements connect, while attributes and constraints provide additional descriptive structure.

Views, layers, granularity levels, and projections determine how this structural knowledge is interpreted and presented for different purposes.

By understanding these conventions, you will be able to:

  • Interpret diagrams and examples consistently
  • Apply the ontology to real systems correctly
  • Communicate about architecture using precise terminology
  • Generate appropriate views for different stakeholders

The remainder of this volume builds on this foundation to define the complete System Ontology v0.1.
