15  Relation Types (v0.1)

Entities alone cannot describe system architecture. A collection of components, interfaces, and data entities becomes meaningful only when the relationships between them are explicitly defined.

Relations capture how architectural elements are connected. They describe structural containment, operational dependencies, communication paths, data access patterns, and responsibility boundaries. When entities are connected through well-defined relations, the ontology forms a system structure graph.

The relation set defined in Ontology v0.1 is intentionally minimal. It includes only the relations necessary to represent the structural and operational interactions commonly observed in software systems.

15.0.1 contains / part_of — Structural Composition

The contains and part_of relations describe structural composition.

These relations represent hierarchical relationships between architectural entities. They indicate that one entity is structurally included within another.

Typical examples include:

  • a system contains multiple components

  • a workflow contains multiple steps

  • a module contains internal subcomponents

  • a data structure contains nested fields or records

The relation contains expresses the forward direction of composition, while part_of expresses the inverse relationship.

Structural composition establishes the hierarchical organization of systems and allows complex architectures to be represented as nested structures.

15.1 Relation Examples

15.1.1 Composition Relations

System Composition:
  E-commerce System contains:
    - Web UI
    - API Service
    - Database
    - Payment Gateway
    - Email Service

Workflow Composition:
  Order Processing Workflow contains:
    - Step 1: Validate Order
    - Step 2: Process Payment
    - Step 3: Update Inventory
    - Step 4: Generate Confirmation
    - Step 5: Send Email

Data Composition:
  Order Data contains:
    - Order ID
    - User ID
    - Order Items (array)
    - Total Amount
    - Shipping Address
    - Billing Address

15.1.2 Dependency Relations

Service Dependencies:
  Order Service depends_on:
    - Database (for order persistence)
    - Payment Gateway (for payment processing)
    - Inventory Service (for stock verification)
    - Email Service (for confirmations)

Component Dependencies:
  Web UI depends_on:
    - API Service (for data retrieval)
    - CDN (for asset delivery)
    
Workflow Dependencies:
  Ingestion Pipeline depends_on:
    - Data Source (external system)
    - Transformation Engine (internal component)
    - Data Warehouse (storage destination)

15.1.3 Invocation Relations

Synchronous Invocation:
  Web UI calls API Service:
    - HTTP POST /api/orders
    - Waits for response
    - Handles result or error
    
Workflow Invocation:
  Workflow Engine invokes Task Worker:
    - Triggers task execution
    - Monitors completion
    - Handles success/failure
    
Internal Invocation:
  API Service calls Authentication Service:
    - Validates user token
    - Returns user permissions
    - Synchronous call

15.1.4 Event Relations

Event Emission:
  Order Service emits:
    - OrderCreated event
    - PaymentCompleted event
    - OrderShipped event

Event Consumption:
  Inventory Service consumes OrderCreated event:
    - Reserves inventory
    - Updates stock levels
    
Email Service consumes OrderShipped event:
    - Sends shipping notification
    - Updates customer communication log
    
Analytics Service consumes all events:
    - Aggregates metrics
    - Generates reports

15.1.5 Data Access Relations

Read Relations:
  Order Service reads:
    - User Data (from User Database)
    - Product Data (from Product Database)
    - Inventory Data (from Inventory Database)
    
Analytics Engine reads:
    - Transaction Records (from Data Warehouse)
    - User Behavior Logs (from Event Store)

Write Relations:
  Order Service writes:
    - Order Records (to Order Database)
    - Transaction Records (to Transaction Database)
    
Ingestion Worker writes:
    - Raw Data (to Data Lake)
    - Processed Data (to Data Warehouse)

15.1.6 Governance Relations

Ownership Relations:
  Payments Team owns:
    - Payment Service
    - Transaction Database
    - Fraud Detection System
    
Operations Team owns:
    - Monitoring Infrastructure
    - Alert Management System
    - Incident Response Tools

Governance Relations:
  Security Policy governs:
    - Authentication mechanisms
    - Access control rules
    - Data encryption requirements
    
Compliance Policy governs:
    - Data retention policies
    - Audit logging requirements
    - Privacy protection measures

15.1.7 Contract Relations

Implementation Relations:
  Order Service implements:
    - Order API Interface
    - Order Processing Interface
    
Payment Service implements:
    - Payment API Interface
    - Transaction Interface

Conformance Relations:
  Order API conforms_to:
    - REST API Specification
    - JSON Schema Definition
    - Rate Limiting Policy
    
Event Stream conforms_to:
    - Event Schema Definition
    - Serialization Format
    - Delivery Guarantees

15.2.4 depends_on — Dependency Relationships

The depends_on relation represents a dependency between entities.

A dependency indicates that one entity requires the presence or functionality of another entity in order to operate correctly.

Examples include:

  • a service component depends_on a database component

  • a worker process depends_on a message queue

  • a processing pipeline depends_on a configuration store

Dependency relations are directional. The source entity requires the target entity for correct operation.

Explicitly representing dependencies enables architectural analysis of coupling, reliability risks, and failure propagation paths.

15.2.5 calls / invokes — Invocation Relationships

The calls or invokes relation represents a direct execution request between components.

This relation captures synchronous or directed interactions in which one component requests an operation from another component through an interface.

Typical examples include:

  • a web service calls an internal API service

  • a workflow engine invokes a task processor

  • an application component invokes a computation engine

Invocation relations are typically associated with request-response interaction patterns.

Distinguishing invocation relations from general dependencies allows the ontology to capture dynamic execution paths within the system.

15.2.6 emits / consumes — Event Relationships

The emits and consumes relations represent asynchronous communication through events.

In event-driven architectures, components publish events that may be processed by other components. This interaction pattern differs from direct invocation because the producer does not necessarily know which consumers will process the event.

Examples include:

  • a transaction service emits an event when an order is created

  • a notification service consumes that event to generate alerts

  • an analytics pipeline consumes event streams for processing

Event relations represent loosely coupled communication structures and are fundamental to event-driven system architectures.

15.2.7 reads / writes — Data Access Relationships

The reads and writes relations represent interactions between components and data entities.

These relations capture how components access and modify system data.

Examples include:

  • a service component reads user profile data

  • a processing engine writes transaction records

  • an analytics pipeline reads historical data from storage

Data access relations are important for understanding data ownership, data flow patterns, and consistency constraints within system architectures.

15.2.8 owns / governs — Responsibility Relationships

Not all relations describe technical interactions. Some relations represent organizational or operational responsibility.

The owns and governs relations represent responsibility assignments between stakeholders and architectural entities.

Examples include:

  • a team owns a service component

  • an operations group governs infrastructure resources

  • a policy authority governs security constraints

Responsibility relations connect the technical architecture to the organizational structures that operate and maintain it.

These relations are particularly important for understanding operational accountability and system governance.

15.2.9 implements / conforms_to — Implementation and Contract Relationships

The implements and conforms_to relations describe how components satisfy defined interfaces or contracts.

A component implements an interface when it provides the operational behavior defined by that interface.

Similarly, a component conforms_to a contract when its behavior satisfies the rules defined by a data schema, protocol specification, or policy definition.

Examples include:

  • a service component implements an API interface

  • an event processor conforms_to an event schema

  • a system component conforms_to a security policy

These relations connect structural elements to the contracts that govern their behavior.

Together, these relation types form the minimal relational vocabulary required to represent system architecture. By combining entities with these relations, the ontology constructs a structured graph that captures the essential dependencies, interactions, and responsibilities of software systems.

│ reads / writes:                                                                         │
│   ✓ When components access data entities                                                │
│   ✓ For database operations                                                            │
│   ✓ For file system access                                                             │
│   Example: ProductService reads Product from ProductDatabase                             │
│                                                                                         │
│ owns:                                                                                  │
│   ✓ When a component has ownership of data                                             │
│   ✓ For data ownership and responsibility                                               │
│   ✓ For lifecycle management                                                           │
│   Example: ProductService owns Product data entity                                      │
│                                                                                         │
│ implements:                                                                            │
│   ✓ When a component provides a capability                                              │
│   ✓ When a component implements an interface                                            │
│   ✓ For capability realization                                                         │
│   Example: ProductService implements ProductCatalog capability                          │
│                                                                                         │
│ provides / exposes:                                                                    │
│   ✓ When a component provides an interface                                             │
│   ✓ When an interface exposes a capability                                             │
│   ✓ For API definitions                                                                │
│   Example: ProductService provides ProductAPI                                           │
│                                                                                         │
│ orchestrated_by / involves:                                                            │
│   ✓ For workflow definitions                                                           │
│   ✓ For workflow execution                                                            │
│   ✓ For process coordination                                                           │
│   Example: OrderWorkflow orchestrated_by OrderService                                   │
│                                                                                         │
│ applies_to:                                                                            │
│   ✓ When a constraint applies to an entity                                             │
│   ✓ For quality attribute constraints                                                   │
│   ✓ For policy enforcement                                                             │
│   Example: PerformanceConstraint applies_to OrderService                                │
│                                                                                         │
│ mitigates:                                                                             │
│   ✓ When a reliability hook addresses a failure mode                                  │
│   ✓ For fault tolerance mechanisms                                                     │
│   ✓ For resilience patterns                                                            │
│   Example: RetryHook mitigates NetworkFailure                                          │
│                                                                                         │
│ enforces:                                                                              │
│   ✓ When a security hook enforces a policy                                             │
│   ✓ For access control                                                                 │
│   ✓ For compliance enforcement                                                         │
│   Example: AuthenticationHook enforces AccessControl                                    │
│                                                                                         │
│ separates:                                                                             │
│   ✓ When a trust boundary separates security domains                                    │
│   ✓ For security zones                                                                │
│   ✓ For privilege boundaries                                                           │
│   Example: NetworkBoundary separates ExternalNetwork from InternalNetwork               │

15.3.5 Common Relation Patterns

┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                          COMMON RELATION PATTERNS                                         │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                         │
│ PATTERN 1: System-Component-Interface Chain                                            │
│                                                                                         │
│   System → contains → Component → provides → Interface → exposes → Capability          │
│                                                                                         │
│   Example:                                                                              │
│     EcommercePlatform contains ProductService                                          │
│     ProductService provides ProductAPI                                                  │
│     ProductAPI exposes ProductCatalog                                                   │
│                                                                                         │
│ PATTERN 2: Component-Dependency-Call Chain                                             │
│                                                                                         │
│   Component → depends_on → Component → calls → Component                                │
│                                                                                         │
│   Example:                                                                              │
│     OrderService depends_on PaymentService                                              │
│     OrderService calls PaymentService.processPayment()                                   │
│                                                                                         │
│ PATTERN 3: Component-Data-Access Chain                                                 │
│                                                                                         │
│   Component → owns → Data Entity ← reads/writes ← Component                             │
│                                                                                         │
│   Example:                                                                              │
│     ProductService owns Product                                                        │
│     ProductService reads Product from ProductDatabase                                   │
│     OrderService writes Order to OrderDatabase                                          │
│                                                                                         │
│ PATTERN 4: Event-Driven Chain                                                          │
│                                                                                         │
│   Component → emits → Interface ← consumes → Component                                   │
│                                                                                         │
│   Example:                                                                              │
│     DataIngestionService emits DataReceivedEvent                                        │
│     DataTransformationService consumes DataReceivedEvent                                 │
│                                                                                         │
│ PATTERN 5: Workflow-Orchestration Chain                                                 │
│                                                                                         │
│   Workflow → orchestrated_by → Component → involves → Component                          │
│                                                                                         │
│   Example:                                                                              │
│     OrderWorkflow orchestrated_by OrderService                                          │
│     OrderWorkflow involves [ProductService, PaymentService]                             │
│                                                                                         │
│ PATTERN 6: Constraint-Application Chain                                                 │
│                                                                                         │
│   Constraint → applies_to → Component → conforms_to → Constraint                         │
│                                                                                         │
│   Example:                                                                              │
│     PerformanceConstraint applies_to OrderService                                       │
│     OrderService conforms_to PerformanceConstraint                                      │
│                                                                                         │
│ PATTERN 7: Failure-Mitigation Chain                                                     │
│                                                                                         │
│   Failure Mode → affected_by → Component ← mitigates ← Reliability Hook                 │
│                                                                                         │
│   Example:                                                                              │
│     NetworkFailure affects OrderService                                                 │
│     RetryHook mitigates NetworkFailure                                                  │
│                                                                                         │
│ PATTERN 8: Security-Enforcement Chain                                                   │
│                                                                                         │
│   Security Hook → enforces → Policy → conforms_to → Component                            │
│                                                                                         │
│   Example:                                                                              │
│     AuthenticationHook enforces AccessPolicy                                            │
│     OrderService conforms_to AccessPolicy                                               │
│                                                                                         │
│ PATTERN 9: Trust Boundary Chain                                                         │
│                                                                                         │
│   Trust Boundary → separates → Component → protected_by → Security Hook                  │
│                                                                                         │
│   Example:                                                                              │
│     NetworkBoundary separates ExternalNetwork from InternalNetwork                       │
│     InternalNetwork protected_by AuthenticationHook                                     │
│                                                                                         │
│ PATTERN 10: Capability-Implementation Chain                                            │
│                                                                                         │
│   Capability → implemented_by → Component → implements → Capability                     │
│                                                                                         │
│   Example:                                                                              │
│     ProductCatalog implemented by ProductService                                        │
│     ProductService implements ProductCatalog                                             │

15.3.6 Relation Cardinality Guidelines

┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                         RELATION CARDINALITY GUIDELINES                                   │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                         │
│ Relation          │ Expected Cardinality │ Notes                                         │
├───────────────────┼───────────────────────┼─────────────────────────────────────────────┤
│ contains          │ 1:N                   │ One entity contains many entities            │
│ part_of           │ N:1                   │ Many entities are part of one entity        │
│ depends_on        │ 1:N or N:1            │ Can be one-to-many or many-to-one           │
│ calls             │ 1:N or N:1            │ Can be one-to-many or many-to-one           │
│ invokes           │ 1:N                   │ One entity invokes many operations           │
│ emits             │ 1:N                   │ One entity emits many events                 │
│ consumes          │ N:1                   │ Many entities consume one event              │
│ reads             │ 1:N                   │ One entity reads many data entities          │
│ writes            │ 1:N                   │ One entity writes many data entities         │
│ owns              │ 1:N                   │ One entity owns many data entities           │
│ implements        │ N:M                   │ Many components implement many capabilities   │
│ provides          │ 1:N                   │ One component provides many interfaces       │
│ exposes           │ 1:N                   │ One interface exposes many capabilities      │
│ orchestrated_by   │ N:1                   │ Many workflows orchestrated by one component │
│ involves          │ N:M                   │ Workflow involves many components            │
│ applies_to        │ N:M                   │ Constraint applies to many entities          │
│ mitigates         │ N:1                   │ Hook mitigates one failure mode              │
│ enforces          │ N:1                   │ Hook enforces one policy                     │
│ separates         │ N:N                   │ Boundary separates many entities              │
└───────────────────┴───────────────────────┴─────────────────────────────────────────────┘

Notes:
  • 1:N = One-to-many relationship
  • N:1 = Many-to-one relationship
  • N:M = Many-to-many relationship
  • Cardinality can vary based on specific use cases
  • Use appropriate cardinality for accurate modeling

15.3.7 Relation Validation Rules

┌─────────────────────────────────────────────────────────────────────────────────────────┐
│                          RELATION VALIDATION RULES                                        │
├─────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                         │
│ RULE 1: Type Compatibility                                                              │
│   ✓ Source entity type must support the relation                                        │
│   ✓ Target entity type must be compatible with the relation                             │
│   ✗ Example: System cannot "calls" another System (use depends_on instead)             │
│                                                                                         │
│ RULE 2: Bidirectional Consistency                                                       │
│   ✓ If A contains B, then B part_of A                                                   │
│   ✓ If A emits event, then event consumed by B                                           │
│   ✗ Example: A contains B but B does not have part_of A (inconsistent)                 │
│                                                                                         │
│ RULE 3: No Circular Composition                                                         │
│   ✓ Avoid circular contains/part_of relationships                                      │
│   ✗ Example: A contains B, B contains C, C contains A (circular)                       │
│                                                                                         │
│ RULE 4: Dependency Acyclicity                                                           │
│   ✓ Avoid circular depends_on relationships                                             │
│   ✗ Example: A depends_on B, B depends_on C, C depends_on A (circular)                 │
│                                                                                         │
│ RULE 5: Interface Implementation                                                         │
│   ✓ Component implements interface must provide interface operations                    │
│   ✗ Example: Component implements interface but missing operations                     │
│                                                                                         │
│ RULE 6: Data Ownership                                                                  │
│   ✓ Data entity should have at most one owner                                           │
│   ✗ Example: Data entity owned by multiple components (ambiguous)                      │
│                                                                                         │
│ RULE 7: Constraint Applicability                                                        │
│   ✓ Constraint must apply to compatible entity types                                     │
│   ✗ Example: Security constraint applies to data entity (type mismatch)                │
│                                                                                         │
│ RULE 8: Workflow Orchestration                                                          │
│   ✓ Workflow must have valid orchestrator component                                     │
│   ✗ Example: Workflow orchestrated_by non-existent component                            │
│                                                                                         │
│ RULE 9: Event Semantics                                                                │
│   ✓ Event interface must have defined events                                            │
│   ✗ Example: Component emits event from non-event interface                             │
│                                                                                         │
│ RULE 10: Trust Boundary Separation                                                      │
│   ✓ Trust boundary must separate distinct security domains                              │
│   ✗ Example: Trust boundary separates entities in same domain (no separation)         │

15.4 Summary

Relations are what transform a collection of entities into a system structure graph. The ontology defines a minimal set of relation types — each with precise semantics — covering composition (contains/part_of), dependency (depends_on), invocation (calls/invokes), events (emits/consumes), data access (reads/writes), responsibility (owns/governs), and contract (implements/conforms_to).

15.4.1 Core Knowledge — Must Remember

Relation Category Relation Types What It Captures
Composition contains, part_of Structural hierarchy — which entities contain which (e.g., system contains components). These define the nested organization of architectures.
Dependency depends_on Operational dependency — one entity requires another to function. Directional: the source depends on the target. Enables analysis of coupling, reliability risks, and failure propagation.
Invocation calls, invokes Direct execution request — one component invokes another through an interface. Represents dynamic execution paths.
Event emits, consumes Asynchronous communication — producers emit events to interfaces/channels, consumers subscribe. Represents loosely coupled interaction.
Data Access reads, writes Interaction between components and data entities — who creates, retrieves, updates, and deletes data. Essential for data ownership and flow analysis.
Responsibility owns, governs Organizational or operational accountability — connects technical architecture to teams, policies, and governance structures.
Contract implements, conforms_to How components satisfy interfaces or contracts — connects structural elements to the rules that govern their behavior.

Relations are directional: the direction of the arrow indicates the flow of dependency or interaction. The complete entity-relation matrix and validation rules (acyclicity, containment consistency, data ownership constraints) provide the structural integrity of the ontology graph.
