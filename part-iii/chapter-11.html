16  Boundaries and Coupling Relations

System architecture is not determined only by the components that exist within a system, but by how tightly those components are connected. The strength and nature of these connections determine how easily a system can evolve, scale, and tolerate failure.

Coupling is therefore one of the most important structural properties of an architecture. However, in many architectural discussions coupling is treated as a subjective concept—described informally as “tight” or “loose” without precise structural criteria.

Within the ontology framework, coupling must be defined structurally rather than intuitively. Coupling emerges from specific relations between entities and can therefore be represented and analyzed explicitly.

16.0.1 Structural Definition of Coupling

Coupling represents the degree of dependency between architectural entities.

Two entities are coupled when the behavior, availability, or structure of one entity directly affects another. In ontology terms, coupling arises from relations such as:

  • depends_on

  • calls or invokes

  • reads or writes

  • emits or consumes

The nature of these relations determines the type and strength of coupling.

For example:

  • a component that synchronously invokes another component exhibits strong operational coupling

  • a component that publishes events to a message broker exhibits weaker coupling, since producers and consumers are decoupled in time

By representing these relations explicitly, the ontology allows coupling to be analyzed as a property of the architectural graph rather than as an informal judgment.

16.0.2 Synchronous and Asynchronous Coupling

One important distinction in coupling arises from the temporal relationship between interacting components.

Synchronous coupling occurs when one component must wait for another component to complete an operation before continuing execution.

Typical examples include:

  • direct API calls

  • RPC invocations

  • synchronous database queries

In synchronous coupling, the availability and response time of the called component directly affect the caller. This creates tight temporal dependency between components.

Asynchronous coupling, by contrast, occurs when communication happens without requiring immediate response from the receiving component.

Examples include:

  • message queues

  • event streams

  • task scheduling systems

In asynchronous coupling, the producer and consumer operate independently. Messages or events may be buffered or processed later.

Asynchronous coupling reduces temporal dependency and often improves system resilience and scalability.

16.0.3 Data Coupling and Control Coupling

Coupling can also be categorized according to the type of dependency being introduced.

Data coupling occurs when components share or exchange structured data.

Examples include:

  • reading and writing shared databases

  • consuming events produced by other components

  • exchanging structured API payloads

Data coupling primarily affects the information dependencies between components.

Control coupling, on the other hand, occurs when one component directly influences the behavior of another component.

Examples include:

  • invoking specific operations through an API

  • issuing commands to trigger tasks

  • controlling execution flows in orchestration systems

Control coupling introduces behavioral dependency, since one component explicitly directs another component’s execution.

Understanding the distinction between these coupling types helps architects reason about system flexibility and failure propagation.

16.0.4 Interface as Boundary

System boundaries are not merely conceptual divisions; they are implemented through interfaces.

An interface defines the precise point at which one component interacts with another component or with the external environment. For this reason, interfaces function as the practical realization of architectural boundaries.

When a boundary is clearly defined through an interface:

  • internal implementation details remain hidden

  • interaction rules become explicit

  • coupling is controlled and observable

This principle is sometimes summarized as:

The boundary of a component is defined by its interfaces.

A well-designed interface therefore acts as a controlled gateway between architectural units.

16.1 Coupling Examples by Type

16.1.1 Synchronous Coupling Example

Tight Synchronous Coupling:
  Frontend Service → API Service → Database
  
Characteristics:
  - Frontend waits for API response
  - API waits for Database query
  - Total latency = sum of all latencies
  - Failure at any point breaks entire chain
  
Problems:
  - Cascading failures
  - Poor performance under load
  - Difficult to scale independently
  
When to use:
  - Request-response patterns where immediate response needed
  - Simple, small-scale systems
  - Strong consistency requirements

16.1.2 Asynchronous Coupling Example

Loose Asynchronous Coupling:
  Order Service → Message Queue → Inventory Service
                              → Email Service
                              → Analytics Service
  
Characteristics:
  - Order Service publishes event and continues
  - Consumers process independently
  - Failure of one consumer doesn't affect others
  - Each service scales independently
  
Benefits:
  - Improved resilience
  - Better scalability
  - Looser coupling
  
When to use:
  - Event-driven workflows
  - High-throughput systems
  - Loose coupling needed

16.1.3 Data Coupling Example

Data Coupling:
  Order Service reads Product Data
  Order Service reads User Data
  Order Service writes Order Data
  
Characteristics:
  - Shared data creates dependency
  - Changes to data structure affect all readers
  - Data ownership unclear
  
Implications:
  - Need for data versioning
  - Schema changes require coordination
  - Data consistency challenges

16.1.4 Control Coupling Example

Control Coupling:
  Orchestrator Service invokes Worker Service A
  Orchestrator Service invokes Worker Service B
  Orchestrator Service invokes Worker Service C
  
Characteristics:
  - Orchestrator controls execution flow
  - Workers depend on orchestrator
  - Central coordination point
  
Implications:
  - Orchestrator becomes bottleneck
  - Workers can't operate independently
  - Complex orchestration logic

16.2 Boundary Definition Examples

16.2.1 Well-Defined Boundary

Payment Service (Well-Defined Boundary)

Interface:
  POST /api/payments/process
  Request: PaymentRequest
  Response: PaymentResponse
  
Internal Implementation:
  - Payment validation logic
  - Fraud detection
  - Payment gateway integration
  - Transaction persistence
  
Boundary Characteristics:
  - Clear API contract
  - Internal details hidden
  - Can be replaced without affecting callers
  - Can be scaled independently
  - Can be tested in isolation
  
Benefits:
  - Easy to understand
  - Easy to maintain
  - Easy to evolve
  - Easy to test

16.2.2 Poorly Defined Boundary

Monolithic Order Processing (Poorly Defined Boundary)

Mixed Responsibilities:
  - Order validation
  - Payment processing
  - Inventory management
  - Email notifications
  - User authentication
  - Product catalog queries
  
Boundary Problems:
  - Multiple responsibilities mixed together
  - Difficult to separate concerns
  - Changes to one area affect others
  - Hard to test in isolation
  - Hard to scale independently
  
Consequences:
  - High coupling
  - Low cohesion
  - Difficult maintenance
  - Slow development
  - Fragile system

16.3 Interface Boundary Examples

16.3.1 API Interface Boundary

API Gateway Interface (External Boundary)

Purpose: External access to system services

Characteristics:
  - HTTP/HTTPS protocol
  - RESTful design
  - Authentication required
  - Rate limiting applied
  - Input validation

Benefits:
  - Single entry point
  - Consistent security
  - Controlled access
  - Monitoring and logging
  - API version management

Components Behind Interface:
  - Multiple internal services
  - Load balancer
  - Authentication service
  - Rate limiting service

16.3.2 Service Interface Boundary

Payment Service Interface (Internal Boundary)

Purpose: Service-to-service communication

Characteristics:
  - Internal protocol (gRPC, internal HTTP)
  - Service authentication (mTLS)
  - High performance
  - Service discovery
  - Circuit breaker patterns

Benefits:
  - Efficient communication
  - Secure internal traffic
  - Service isolation
  - Independent deployment
  - Technology diversity

16.3.3 Event Interface Boundary

Event Stream Interface (Asynchronous Boundary)

Purpose: Event-driven communication

Characteristics:
  - Publish-subscribe pattern
  - Message broker
  - Event schema definitions
  - Delivery guarantees
  - Consumer groups

Benefits:
  - Loose coupling
  - Temporal decoupling
  - Scalability
  - Resilience
  - Flexibility

16.4 Coupling Reduction Strategies

16.4.1 Strategy 1: Introduce Message Queue

Before (Tight Coupling):
  Service A → Service B → Service C
  
  Problem: Failure in B blocks entire chain

After (Loose Coupling with Queue):
  Service A → Message Queue → Service B
                              → Service C
  
  Benefits:
    - Service A doesn't wait for B or C
    - B and C can operate independently
    - Queue buffers load
    - Failure isolation

16.4.2 Strategy 2: Use API Gateway

Before (Multiple Direct Dependencies):
  Client → Service A
  Client → Service B
  Client → Service C
  
  Problem: Client knows about all services

After (API Gateway Pattern):
  Client → API Gateway → Service A
                    → Service B
                    → Service C
  
  Benefits:
    - Single entry point
    - Service discovery
    - Load balancing
    - Security enforcement
    - Protocol translation

16.4.3 Strategy 3: Implement Circuit Breaker

Before (Cascading Failures):
  Service A calls Service B
  Service B fails
  Service A fails
  Client fails

After (Circuit Breaker Pattern):
  Service A calls Service B (with circuit breaker)
  Service B fails
  Circuit breaker opens
  Service A returns fallback response
  System continues operating

Benefits:
    - Failure isolation
    - Fallback behavior
    - System resilience
    - Graceful degradation

16.4.4 Strategy 4: Event Sourcing

Before (Shared Database Coupling):
  Service A and Service B both write to Database
  Database schema becomes coupling point
  Changes affect both services

After (Event Sourcing):
  Service A emits events
  Service B emits events
  Event store persists events
  Each service rebuilds state from events

Benefits:
    - Decoupled data access
    - Audit trail
    - Event replay
    - Temporal queries

16.4.5 Directionality and Visualization of Relations

Relations between entities are typically directional.

Directionality indicates the direction of dependency or interaction between architectural elements. For example:

  • if component A calls component B, the relation is directed from A to B

  • if component A depends on component B, the dependency flows from A toward B

Representing direction explicitly is essential for analyzing execution paths, dependency chains, and failure propagation.

When visualizing architectural graphs, several conventions help maintain clarity.

First, directional relations are typically represented using arrows that indicate dependency or invocation flow.

Second, containment relations are often represented through hierarchical structures rather than arrows.

Third, different relation types may be distinguished using visual styles such as line types or colors, allowing invocation paths, data flows, and event streams to be visually separated.

These visualization conventions allow the ontology graph to function not only as a formal representation of architecture but also as a clear visual model of system structure and interaction.
