17  Interaction Models as Relation Patterns

Relations describe individual connections between entities, but real system behavior emerges from recurring structures of relations rather than isolated links. When certain relation configurations appear repeatedly across systems, they form recognizable interaction models.

An interaction model is therefore a pattern of relations that defines how components coordinate behavior, exchange information, and produce system outcomes. These models capture the operational structure of a system beyond simple dependency graphs.

Within the ontology, interaction models are not treated as separate entity types. Instead, they are understood as relation patterns that can be recognized within the architectural graph.

17.0.1 Request–Response

The request–response model represents the most common interaction pattern in software systems.

In this model, one component sends a request to another component through a defined interface. The receiving component processes the request and returns a response.

The interaction structure typically involves the following relations:

  • a component calls or invokes an interface

  • the interface is implemented by another component

  • the responding component returns data through the same interaction channel

This model is usually associated with synchronous communication mechanisms such as HTTP APIs, RPC calls, or internal service invocations.

Request–response interactions create strong temporal coupling, because the requesting component must wait for the responding component to complete its operation.

Despite this coupling, the model remains widely used because it provides clear control flow and predictable response semantics.

17.1 Interaction Model Examples

17.1.1 Request-Response Example

Example: User Profile Lookup

Components:
  - Web Frontend (client)
  - User Service (server)
  - Database (storage)

Interaction Flow:
  1. Frontend calls User Service
     Request: GET /api/users/{id}
  
  2. User Service implements interface
     Receives request
     Validates user ID
     Queries database
  
  3. User Service reads from Database
     Query: SELECT * FROM users WHERE id = ?
  
  4. Database returns user data
     Response: { id, name, email, ... }
  
  5. User Service returns response to Frontend
     Response: { id, name, email, ... }

Characteristics:
  - Synchronous interaction
  - Client waits for response
  - Single request-response cycle
  - Temporal coupling between components

Use Cases:
  - API requests where immediate response needed
  - Simple queries and operations
  - Strong consistency required
  - Low-latency interactions

Benefits:
  - Simple to understand and implement
  - Predictable behavior
  - Clear error handling
  - Easy to debug

Challenges:
  - Cascading failures
  - Poor performance under load
  - Tight coupling between components
  - Difficult to scale independently

17.1.2 Event-Driven Example

Example: Order Processing Event Flow

Components:
  - Order Service (producer)
  - Inventory Service (consumer)
  - Email Service (consumer)
  - Analytics Service (consumer)
  - Message Broker (coordination)

Interaction Flow:
  1. Order Service creates order
     Processes order locally
     Emits OrderCreated event
  
  2. Order Service emits event to Message Broker
     Event: { order_id, user_id, items, total, timestamp }
     Topic: orders.created
  
  3. Message Broker distributes event
     Publishes to all subscribers
     Ensures delivery
  
  4. Inventory Service consumes event
     Receives OrderCreated event
     Reserves inventory
     Updates stock levels
  
  5. Email Service consumes event
     Receives OrderCreated event
     Sends confirmation email
     Updates customer communication
  
  6. Analytics Service consumes event
     Receives OrderCreated event
     Updates analytics metrics
     Generates reports

Characteristics:
  - Asynchronous interaction
  - Producer doesn't know consumers
  - Multiple consumers possible
  - Temporal decoupling

Use Cases:
  - Notifications and alerts
  - Data synchronization
  - Loose coupling needed
  - High-throughput systems

Benefits:
  - Loose coupling
  - Scalability
  - Resilience
  - Flexibility

Challenges:
  - Eventual consistency
  - Complex debugging
  - Event ordering challenges
  - Consumer failure handling

17.1.3 Pipeline Example

Example: Data Processing Pipeline

Components:
  - Ingestion Worker (stage 1)
  - Transformation Engine (stage 2)
  - Validation Engine (stage 3)
  - Storage Component (stage 4)

Interaction Flow:
  1. Ingestion Worker reads raw data
     Input: Raw data files
     Output: Structured records
  
  2. Ingestion Worker writes to Transformation Engine
     Passes structured records
     Triggers next stage
  
  3. Transformation Engine processes data
     Applies business rules
     Normalizes formats
     Enriches data
  
  4. Transformation Engine writes to Validation Engine
     Passes transformed data
     Triggers next stage
  
  5. Validation Engine validates data
     Checks data quality
     Validates schemas
     Filters invalid records
  
  6. Validation Engine writes to Storage
     Passes validated data
     Completes pipeline

Characteristics:
  - Sequential data flow
  - Each stage processes in order
  - Data transformation focus
  - Linear progression

Use Cases:
  - Data ETL processes
  - Analytics pipelines
  - Machine learning workflows
  - Content processing

Benefits:
  - Clear data flow
  - Modular stages
  - Easy to add/remove stages
  - Process visibility

Challenges:
  - Sequential bottlenecks
  - Error handling complexity
  - Backpressure management
  - Data format compatibility

17.1.4 Orchestration Example

Example: Order Fulfillment Orchestration

Components:
  - Orchestrator Service (central controller)
  - Payment Service (payment processing)
  - Inventory Service (stock management)
  - Shipping Service (fulfillment)
  - Notification Service (communication)

Interaction Flow:
  1. Orchestrator receives order
     Starts orchestration workflow
  
  2. Orchestrator invokes Payment Service
     Command: Process payment for order
     Waits for completion
  
  3. Payment Service processes payment
     Charges payment method
     Returns success/failure
  
  4. Orchestrator invokes Inventory Service
     Command: Reserve items for order
     Waits for completion
  
  5. Inventory Service reserves inventory
     Checks stock availability
     Updates inventory levels
     Returns success/failure
  
  6. Orchestrator invokes Shipping Service
     Command: Create shipment for order
     Waits for completion
  
  7. Shipping Service creates shipment
     Generates shipping label
     Schedules pickup
     Returns tracking number
  
  8. Orchestrator invokes Notification Service
     Command: Send order confirmation
     Waits for completion
  
  9. Notification Service sends notification
     Emails customer
     SMS customer
     Returns success/failure
  
  10. Orchestrator completes workflow
      Marks order as fulfilled
      Returns final status

Characteristics:
  - Centralized control
  - Explicit workflow
  - Sequential execution
  - Strong coordination

Use Cases:
  - Complex business processes
  - Multi-step workflows
  - Transactional operations
  - Process automation

Benefits:
  - Centralized control
  - Clear workflow visibility
  - Easy error handling
  - Transaction management

Challenges:
  - Orchestrator bottleneck
  - Single point of failure
  - Complexity in orchestrator
  - Tight coupling to orchestrator

17.1.5 Choreography Example

Example: Order Processing Choreography

Components:
  - Order Service (initiator)
  - Inventory Service (participant)
  - Payment Service (participant)
  - Shipping Service (participant)
  - Notification Service (participant)
  - Event Broker (coordination)

Interaction Flow:
  1. Order Service creates order
     Emits OrderCreated event
  
  2. Inventory Service consumes OrderCreated
     Receives event
     Reserves inventory
     Emits InventoryReserved event
     Or emits InventoryUnavailable event if stock insufficient
  
  3. Payment Service consumes InventoryReserved
     Receives event
     Processes payment
     Emits PaymentCompleted event
     Or emits PaymentFailed event if payment declined
  
  4. Shipping Service consumes PaymentCompleted
     Receives event
     Creates shipment
     Emits OrderShipped event
  
  5. Notification Service consumes OrderShipped
     Receives event
     Sends notification
     Emits NotificationSent event
  
  6. Order Service consumes final events
     Updates order status
     Completes workflow

Characteristics:
  - Decentralized control
  - Event-driven coordination
  - Independent components
  - Loose coupling

Use Cases:
  - Event-driven architectures
  - High-scale systems
  - Loose coupling required
  - Independent evolution

Benefits:
  - Loose coupling
  - Independent scaling
  - Fault isolation
  - Flexibility

Challenges:
  - Complex event flows
  - Difficult debugging
  - Event ordering issues
  - No central coordinator

17.1.6 Agentic Tool-Calling Example

Example: Task Execution Agent

Components:
  - Agent Controller (reasoning engine)
  - LLM Engine (decision making)
  - Tool Executor (tool invocation)
  - Tool A (database query)
  - Tool B (web search)
  - Tool C (file operation)
  - Memory Store (context management)

Interaction Flow:
  1. User provides task
     Request: "Find recent sales data and analyze trends"
  
  2. Agent Controller calls LLM Engine
     Input: Task description
     Request: Generate execution plan
  
  3. LLM Engine generates plan
     Output: Multi-step plan
     Steps: Query database, Analyze data, Generate report
  
  4. Agent Controller executes Step 1
     Invokes Tool Executor with Tool A
     Command: Query sales data from last 30 days
  
  5. Tool Executor invokes Tool A
     Executes database query
     Returns sales data
  
  6. Agent Controller receives result
     Stores in Memory Store
     Proceeds to Step 2
  
  7. Agent Controller executes Step 2
     Calls LLM Engine with data
     Request: Analyze trends in sales data
  
  8. LLM Engine analyzes data
     Identifies trends
     Returns analysis results
  
  9. Agent Controller executes Step 3
     Invokes Tool Executor with Tool C
     Command: Save analysis report to file
  
  10. Tool Executor invokes Tool C
      Writes report to file
      Returns confirmation
  
  11. Agent Controller completes task
      Synthesizes results
      Returns final response to user

Characteristics:
  - Dynamic decision making
  - Runtime tool selection
  - Iterative reasoning
  - Adaptive execution

Use Cases:
  - AI-powered automation
  - Complex task execution
  - Dynamic workflows
  - Intelligent assistants

Benefits:
  - Flexibility
  - Adaptability
  - Intelligence
  - Automation

Challenges:
  - Unpredictable behavior
  - Tool failure handling
  - Reasoning complexity
  - Performance variability

17.2 Interaction Model Comparison

17.2.1 Temporal Coupling Comparison

Request-Response:
  Coupling: High (synchronous)
  Latency: High (sum of all latencies)
  Resilience: Low (cascading failures)
  Scalability: Low (tight coupling)

Event-Driven:
  Coupling: Low (asynchronous)
  Latency: Low (no waiting)
  Resilience: High (isolated failures)
  Scalability: High (independent scaling)

Pipeline:
  Coupling: Medium (sequential)
  Latency: Medium (stages add latency)
  Resilience: Medium (stage failures)
  Scalability: Medium (stage independence)

Orchestration:
  Coupling: High (centralized)
  Latency: High (sequential steps)
  Resilience: Low (orchestrator dependency)
  Scalability: Low (orchestrator bottleneck)

Choreography:
  Coupling: Low (event-based)
  Latency: Low (asynchronous)
  Resilience: High (isolated failures)
  Scalability: High (independent scaling)

Agentic:
  Coupling: Variable (dynamic)
  Latency: Variable (iterative)
  Resilience: Medium (depends on tools)
  Scalability: Medium (depends on reasoning)

17.2.2 Use Case Recommendations

Choose Request-Response when:
  - Immediate response required
  - Simple interactions
  - Strong consistency needed
  - Low latency acceptable

Choose Event-Driven when:
  - Loose coupling needed
  - Multiple consumers
  - High throughput required
  - Eventual consistency acceptable

Choose Pipeline when:
  - Data transformation focus
  - Sequential processing
  - Clear stages needed
  - Data flow visibility important

Choose Orchestration when:
  - Complex workflows
  - Central control needed
  - Transaction semantics required
  - Process visibility important

Choose Choreography when:
  - Independent components
  - Loose coupling preferred
  - High scalability needed
  - Independent evolution desired

Choose Agentic when:
  - Dynamic decision making
  - Complex, unstructured tasks
  - AI-powered automation
  - Adaptive execution needed

17.2.3 Event-Driven

The event-driven interaction model is based on asynchronous message propagation.

In this pattern, components emit events describing state changes or completed operations. Other components may subscribe to these events and react when they occur.

The relation structure typically includes:

  • a component emits an event

  • an event channel distributes the event

  • one or more components consume the event

Unlike request–response interactions, event-driven systems do not require producers to know which components will consume the event.

This model introduces temporal decoupling, allowing producers and consumers to operate independently. It is commonly used in distributed systems that require scalability and resilience.

Event-driven architectures often rely on message brokers, event streams, or publish–subscribe infrastructures.

17.2.4 Pipeline and Stream

The pipeline interaction model represents systems in which data flows through a sequence of processing stages.

In this structure, each component performs a transformation on incoming data and passes the result to the next stage of the pipeline.

The relation structure typically includes:

  • components that read input data

  • components that write transformed output

  • sequential data flows connecting stages

Pipelines are common in batch processing systems, data analytics workflows, and machine learning pipelines.

A closely related structure is the stream processing model, where data flows continuously rather than in discrete batches.

Both pipeline and stream architectures emphasize data flow as the primary organizing principle of the system.

17.2.5 Orchestration vs Choreography

Complex systems often involve multiple interacting components that must coordinate their behavior.

Two major coordination models exist.

Orchestration

In orchestration, a central component explicitly controls the execution of other components. The orchestrator determines the order of operations and directs tasks through explicit invocation relations.

The relation structure often includes:

  • an orchestration component that invokes multiple tasks

  • workflow definitions describing execution order

  • centralized control over execution logic

Orchestration provides strong control over process flow but may introduce central coordination dependencies.

Choreography

In choreography, coordination emerges from event interactions between components rather than from a central controller.

Each component reacts to events emitted by others and performs its own operations accordingly.

The relation structure includes:

  • components that emit events

  • other components that consume those events

  • decentralized control logic distributed across the system

Choreography reduces centralized dependencies and allows more flexible system evolution.

17.2.6 Agentic Tool-Calling

Recent architectures based on language models and autonomous agents introduce a new interaction model often described as tool-calling.

In this model, an agent component dynamically selects and invokes tools in order to accomplish a task.

The interaction structure typically includes:

  • an agent component that interprets goals or prompts

  • tool interfaces representing available operations

  • invocation relations between the agent and selected tools

  • feedback loops where tool outputs influence subsequent decisions

Unlike traditional workflow orchestration, tool-calling interactions are often dynamic and decision-driven. The agent determines which tools to invoke based on runtime reasoning rather than predetermined execution sequences.

From an ontology perspective, agentic tool-calling can be represented as a pattern combining:

  • invocation relations (calls)

  • workflow coordination

  • dynamic decision logic

This interaction model is increasingly relevant in systems that integrate AI agents, automated planning systems, and adaptive workflows.

By representing interaction models as relation patterns rather than fixed constructs, the ontology allows architectural structures to be described flexibly while still capturing the recurring coordination patterns that shape system behavior.
