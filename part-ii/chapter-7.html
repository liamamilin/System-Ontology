12  Interfaces and Contracts

Components do not exist in isolation. Systems emerge from the interactions between components, and these interactions must occur through well-defined structural points. In the ontology, these interaction points are represented as interfaces.

Interfaces define the boundaries through which components communicate. They expose capabilities, define data exchange structures, and regulate interaction behavior. Without explicit interfaces, component dependencies become implicit and architectural structures become difficult to analyze.

Closely associated with interfaces are contracts. While interfaces define the interaction point, contracts define the rules governing that interaction. Together, interfaces and contracts form the foundation of system interoperability and architectural stability.

12.0.1 Interface — Interaction Point Entity

An interface represents a point of interaction between components or between a system and its external context.

Interfaces define how requests, events, or commands enter and exit components. They represent the formal connection points through which architectural elements communicate.

Interfaces typically expose several structural properties:

  • the operation or interaction type

  • the input and output data structures

  • the communication protocol

  • the interaction semantics

Interfaces may take different concrete forms depending on the architectural style of the system. Common examples include:

  • HTTP endpoints

  • RPC methods

  • event streams

  • message queue topics

  • command-line interfaces

  • internal function entry points

In the ontology, interfaces are represented as distinct entities rather than attributes of components. This separation allows interfaces to be referenced, versioned, and governed independently of the components that implement them.

Interfaces therefore function as the structural connectors of the system architecture.

12.0.2 Contract — Data and Behavioral Agreements

While interfaces identify the interaction point, contracts define the expectations governing that interaction.

A contract specifies the rules that participants must follow when communicating through an interface. These rules ensure that interacting components remain compatible even as internal implementations evolve.

Two forms of contracts are particularly important.

Data contracts

Data contracts define the structure and format of information exchanged through an interface. They specify the schema of request and response data, including field definitions, data types, and validation rules.

Examples include API schemas, event payload structures, and message formats.

Behavioral contracts

Behavioral contracts define the expected behavior of an interaction. They describe how components should respond to requests, what side effects may occur, and what guarantees are provided.

Behavioral contracts may include elements such as:

  • idempotency guarantees

  • ordering constraints

  • retry behavior

  • error handling semantics

Together, data contracts and behavioral contracts ensure that interactions remain predictable and stable.

12.0.3 Unified Representation of API, Event, and Command

Modern systems employ multiple interaction models. Components may communicate through synchronous requests, asynchronous events, or command-based control signals.

Despite these differences, these interaction forms share a common conceptual structure. Each represents an invocation of behavior across a system boundary.

For this reason, the ontology represents APIs, events, and commands using a unified interface model.

An interface interaction can be characterized by three elements:

  • the interaction initiator

  • the target component

  • the contract governing the interaction

Different interaction styles correspond to different patterns of this structure.

An API interaction represents a synchronous request-response invocation.

Example: REST API Interface

Interface: User API
Type: api
Protocol: HTTPS
Version: v2

Data Contract:
  Request: { "user_id": "string", "include_preferences": "boolean" }
  Response: { "user_id": "string", "name": "string", "email": "string", "preferences": {...} }

Behavior Contract:
  - Synchronous request-response
  - Idempotent for GET requests
  - Requires authentication
  - Returns 404 if user not found

An event interaction represents an asynchronous publication where producers emit events that consumers may process.

Example: Event Interface

Interface: Order Created Event
Type: event
Protocol: Kafka Topic
Version: v1

Data Contract:
  Event Schema: { "order_id": "string", "user_id": "string", "items": [...], "total": "number", "timestamp": "datetime" }

Behavior Contract:
  - At-least-once delivery
  - Consumers must handle duplicate events
  - No ordering guarantee across consumers
  - Event persists for 7 days

A command interaction represents a directed instruction that requests a specific action from a target component.

Example: Command Interface

Interface: Shutdown Command
Type: command
Protocol: Internal Message Queue
Version: v1

Data Contract:
  Command Schema: { "component_id": "string", "grace_period_seconds": "number", "reason": "string" }

Behavior Contract:
  - Initiates graceful shutdown
  - Acknowledges command receipt
  - Reports completion status
  - Cannot be cancelled once initiated

By modeling these interaction types within a unified interface structure, the ontology can represent diverse communication models while maintaining a consistent architectural vocabulary.

12.1.4 Interface Versioning

Interfaces are among the most stable elements of a system architecture. While internal component implementations may evolve frequently, interfaces often persist over long periods because they define integration boundaries between systems.

For this reason, interface versioning becomes a key mechanism for managing architectural evolution.

When an interface changes in ways that may affect compatibility, a new version must be introduced. Version identifiers allow multiple interface definitions to coexist while clients gradually migrate to newer versions.

Interface versioning serves several architectural functions.

First, it provides a stable reference point for system integrations. External systems can depend on a specific interface version without being affected by internal system changes.

Second, versioning enables incremental evolution of system architecture. New capabilities can be introduced through new interface versions while maintaining compatibility with existing integrations.

Third, interface versions function as historical markers of system architecture. By examining interface evolution over time, it becomes possible to analyze how a system’s structure and capabilities have changed.

Within the ontology, interfaces therefore carry explicit version identifiers and version relationships. These relationships capture how interface definitions evolve across system releases.

Through this mechanism, interface versioning becomes a central index of architectural change.

12.2 Interface Versioning Strategies

12.2.1 Strategy 1: URI Versioning

Version is embedded in the interface URI:

Version 1: /api/v1/users
Version 2: /api/v2/users
Version 3: /api/v3/users

Advantages:
  - Clear separation between versions
  - Easy to route requests to appropriate handlers
  - Can deprecate old versions by removing endpoints

Disadvantages:
  - URI changes require client updates
  - Version is exposed in client code
  - Multiple versions increase API surface area

12.2.2 Strategy 2: Header Versioning

Version is specified in request headers:

Endpoint: /api/users
Header: API-Version: v1

Version 1 Request:
  GET /api/users
  API-Version: v1

Version 2 Request:
  GET /api/users
  API-Version: v2

Advantages:
  - Clean URIs without version information
  - Same endpoint can handle multiple versions
  - Version can be negotiated dynamically

Disadvantages:
  - Less discoverable
  - Requires header support in all clients
  - Harder to cache responses

12.2.3 Strategy 3: Content Negotiation

Version is specified via content negotiation:

Accept header specifies version:
  Accept: application/vnd.api.v1+json
  Accept: application/vnd.api.v2+json

Advantages:
  - HTTP-standard approach
  - Can negotiate other aspects simultaneously (format, language)
  - Clean separation of concerns

Disadvantages:
  - Complex to implement
  - Requires content negotiation support
  - Not all clients support this pattern

12.3 Interface Evolution Patterns

12.3.1 Additive Changes (Compatible)

Adding new fields or operations without breaking existing functionality:

Original Interface (v1):
  POST /api/users
  Request: { "name": "string", "email": "string" }
  Response: { "user_id": "string", "name": "string", "email": "string" }

Evolved Interface (v2):
  POST /api/users
  Request: { "name": "string", "email": "string", "phone": "string" }
  Response: { "user_id": "string", "name": "string", "email": "string", "phone": "string" }

Strategy:
  - Keep v1 interface unchanged
  - Introduce v2 with additional fields
  - v1 requests ignore new fields
  - Gradually migrate clients to v2

12.3.2 Non-Breaking Modifications (Compatible)

Changing interface semantics without breaking existing clients:

Original Interface (v1):
  POST /api/orders
  Behavior: Creates order synchronously

Evolved Interface (v2):
  POST /api/orders
  Behavior: Creates order asynchronously, returns job ID
  New Endpoint: GET /api/orders/{job_id}
  Purpose: Check order creation status

Strategy:
  - v2 provides enhanced async behavior
  - v1 clients continue to work with synchronous mode
  - New clients can use async mode for better performance

12.3.3 Breaking Changes (New Version Required)

Changes that require clients to be updated:

Original Interface (v1):
  GET /api/users/{id}
  Response: { "user_id": "string", "name": "string", "email": "string" }

Breaking Change (v2):
  GET /api/users/{id}
  Response: { "user_id": "string", "full_name": "string", "contact_email": "string" }

Strategy:
  - Maintain v1 interface alongside v2
  - Document migration path from v1 to v2
  - Set deprecation date for v1 (e.g., 6 months)
  - Monitor v1 usage before removal
  - Remove v1 after migration period

12.4 Interface Lifecycle Management

12.4.1 Version Introduction

  1. Design - Define new interface version with clear contract
  2. Implement - Deploy new version alongside existing versions
  3. Document - Provide migration guide and examples
  4. Announce - Notify users of new version availability
  5. Monitor - Track adoption and usage patterns

12.4.2 Version Deprecation

  1. Announce Deprecation - Publish deprecation notice with timeline
  2. Provide Migration Guide - Offer clear steps for migrating to newer version
  3. Add Warnings - Return deprecation warnings in responses
  4. Monitor Usage - Track remaining clients using deprecated version
  5. Schedule Removal - Set final removal date

12.4.3 Version Removal

  1. Verify Migration - Confirm no active clients using deprecated version
  2. Remove Endpoint - Delete deprecated interface implementation
  3. Update Documentation - Remove deprecated version from docs
  4. Clean Up Tests - Remove tests for deprecated version
  5. Archive Specifications - Keep record of removed versions for reference

12.5 Interface Versioning Best Practices

Use Semantic Versioning - MAJOR version: Breaking changes - MINOR version: Additive changes - PATCH version: Bug fixes, documentation updates

Maintain Backward Compatibility - Prefer additive changes over breaking changes - Use default values for new fields - Support both old and new request formats when possible

Document Version Changes - Maintain changelog for each version - Provide migration guides - Include example requests/responses - Document deprecation timelines

Monitor Version Usage - Track which versions clients are using - Set up alerts for deprecated version usage - Gather feedback on new versions - Analyze migration patterns

Plan Deprecation Carefully - Provide ample migration time (typically 6-12 months) - Offer direct support for migration - Consider grandfather clauses for long-term clients - Communicate deprecation early and frequently
