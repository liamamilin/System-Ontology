14  Workflow and Execution Units

While components define the structural elements of a system, workflows define how these elements cooperate to produce behavior. Workflows represent the orchestration logic that coordinates tasks, data flows, and component interactions over time.

In many modern systems, particularly distributed systems and data pipelines, behavior emerges not from isolated component operations but from structured sequences of execution. These sequences determine how work progresses through the system, which components participate in processing, and how results are produced.

The ontology therefore treats workflows and execution units as explicit entities within the architectural representation.

14.0.1 Workflow — Orchestration Structure

A Workflow represents a structured sequence of operations that collectively accomplish a system objective.

Workflows coordinate tasks across components, defining the order in which operations occur and the conditions under which they proceed. They often represent the operational realization of system capabilities.

A workflow may include several structural elements:

  • ordered or conditional execution steps

  • branching logic based on data or events

  • parallel task execution

  • error handling and retry policies

  • termination conditions

Workflows appear in many forms across system architectures. Examples include:

  • request-processing pipelines in web services

  • data transformation pipelines in analytics systems

  • job execution pipelines in workflow engines

  • orchestration flows in agent-based systems

Within the ontology, workflows capture the behavioral coordination layer of the system.

14.1 Workflow Examples

14.1.1 Example 1: Order Processing Workflow

Workflow: Order Processing
Trigger: OrderCreatedEvent

Steps:
  1. Validate Order
     - Checks inventory availability
     - Validates payment method
     - Branch: If inventory unavailable → OutOfStockError
             If payment invalid → PaymentError
  
  2. Process Payment
     - Charges payment method
     - Branch: If payment failed → PaymentError
             If payment succeeded → continue
  
  3. Update Inventory
     - Reserves ordered items
     - Updates stock levels
  
  4. Generate Confirmation
     - Creates order confirmation
     - Sends email to customer
  
  5. Schedule Fulfillment
     - Creates fulfillment task
     - Notifies warehouse

Error Handling:
  - OutOfStockError → Notify customer, cancel order
  - PaymentError → Retry payment (3 attempts), then cancel

Termination:
  - Success: Order completed, confirmation sent
  - Failure: Order cancelled, customer notified

14.1.2 Example 2: Data Ingestion Workflow

Workflow: Data Ingestion Pipeline
Trigger: Scheduled (daily at 2 AM)

Steps:
  1. Fetch Data
     - Connect to external data source
     - Download data files
  
  2. Validate Schema
     - Validate data structure
     - Branch: If invalid → SchemaError
             If valid → continue
  
  3. Transform Data
     - Apply business rules
     - Normalize formats
  
  4. Deduplicate
     - Remove duplicate records
     - Maintain data quality
  
  5. Load to Warehouse
     - Insert into data warehouse
     - Update indexes
  
  6. Generate Report
     - Create ingestion summary
     - Send to operations team

Error Handling:
  - SchemaError → Alert data team, pause ingestion
  - ConnectionError → Retry (5 attempts), then escalate

Termination:
  - Success: Data loaded, report generated
  - Failure: Partial load possible, report errors

14.1.3 Example 3: Agent Tool-Calling Workflow

Workflow: Task Execution
Trigger: User Task Request

Steps:
  1. Analyze Task
     - Parse user request
     - Identify required capabilities
  
  2. Plan Actions
     - Generate step-by-step plan
     - Select required tools
  
  3. Execute Step 1
     - Invoke Tool A
     - Capture result
  
  4. Evaluate Progress
     - Check if step completed successfully
     - Branch: If failed → Retry or adjust plan
             If succeeded → continue
  
  5. Execute Step 2 (if needed)
     - Invoke Tool B
     - Capture result
  
  6. Evaluate Progress
     - Check if step completed successfully
     - Branch: If failed → Retry or adjust plan
             If succeeded → continue
  
  7. Continue Steps 3-N
     - Repeat for remaining steps
  
  8. Synthesize Results
     - Combine all step results
     - Generate final response

Error Handling:
  - Tool failure → Retry (3 attempts), then skip or use alternative
  - Execution timeout → Terminate workflow, report partial results

Termination:
  - Success: All steps completed, final response generated
  - Failure: Partial completion, report what was achieved

14.1.4 Example 4: Image Processing Workflow

Workflow: Image Processing Pipeline
Trigger: ImageUploadEvent

Steps:
  1. Receive Image
     - Accept uploaded image file
     - Validate file format and size
  
  2. Generate Thumbnails
     - Create multiple thumbnail sizes
     - Parallel execution:
       - Small thumbnail (100x100)
       - Medium thumbnail (300x300)
       - Large thumbnail (600x600)
  
  3. Apply Watermark
     - Add branding watermark
     - Position in bottom-right corner
  
  4. Optimize for Web
     - Compress image
     - Adjust quality settings
  
  5. Store Variants
     - Save original image
     - Save all thumbnails
     - Store metadata
  
  6. Update Database
     - Record image details
     - Update user statistics

Error Handling:
  - Invalid file → Reject upload, notify user
  - Processing failure → Retry (2 attempts), then mark as failed

Termination:
  - Success: All variants created and stored
  - Failure: Original preserved, partial variants created

14.2 Trigger Examples

14.2.1 Time-Based Triggers

Scheduled Backup Workflow:
  - Trigger: Every day at 3:00 AM
  - Purpose: Backup database
  - Components: Backup Service, Storage Service

Periodic Data Cleanup:
  - Trigger: Every Sunday at 1:00 AM
  - Purpose: Clean up temporary data
  - Components: Cleanup Worker, Database

Hourly Metrics Collection:
  - Trigger: Every hour (e.g., 0:00, 1:00, 2:00...)
  - Purpose: Collect performance metrics
  - Components: Metrics Collector, Time-series Database

14.2.2 Event-Based Triggers

Order Creation Workflow:
  - Trigger: OrderCreatedEvent published
  - Purpose: Process new order
  - Components: Order Service, Inventory Service, Payment Service

User Registration Workflow:
  - Trigger: UserRegisteredEvent published
  - Purpose: Initialize user account
  - Components: User Service, Email Service, Welcome Bot

System Alert Workflow:
  - Trigger: SystemAlertEvent published
  - Purpose: Handle system alerts
  - Components: Alert Processor, Notification Service

14.2.3 Request-Based Triggers

API Request Workflow:
  - Trigger: HTTP POST /api/process
  - Purpose: Process user request
  - Components: API Service, Processing Engine, Storage

CLI Command Workflow:
  - Trigger: User executes command `analyze data.csv`
  - Purpose: Analyze data file
  - Components: CLI Interface, Analysis Engine, Report Generator

Webhook Callback Workflow:
  - Trigger: Webhook callback received
  - Purpose: Process external system callback
  - Components: Webhook Handler, Validation Service, Processor

14.3 Execution Granularity Hierarchy

Workflow (highest level)
  └── Represents complete business process
  └── Coordinates multiple jobs or steps
  └── Example: "Order Processing Workflow"

Job (execution instance)
  └── Represents single workflow execution
  └── Contains specific parameters and context
  └── Example: "Order #12345 Processing Job"

Task (functional operation)
  └── Represents discrete unit of work
  └── Performed by specific component
  └── Example: "Validate Payment Task"

Step (workflow stage)
  └── Represents ordered stage in workflow
  └── Defines execution sequence
  └── Example: "Step 3: Process Payment"

Function (lowest level)
  └── Represents code-level operation
  └── Implementation detail
  └── Example: "validatePaymentMethod()"

14.4 Runtime Topology Examples

14.4.1 Simple Web Application Runtime

Runtime Topology: Web Application

Deployment:
  - Web UI: 2 instances behind load balancer
  - API Service: 3 instances behind load balancer
  - Database: 1 primary + 2 read replicas

Scaling:
  - Web UI: Auto-scale 2-5 instances based on CPU
  - API Service: Auto-scale 3-8 instances based on request rate
  - Database: Read replicas scale based on query load

Distribution:
  - All components deployed in same region
  - Network latency between components <10ms
  - Shared network for internal communication

14.4.2 Distributed Data Pipeline Runtime

Runtime Topology: Data Pipeline

Deployment:
  - Ingestion Workers: 10 instances across availability zones
  - Transformation Engine: 5 instances with GPU acceleration
  - Storage Cluster: Distributed object storage
  - Analytics Engine: 3 instances for query processing

Scaling:
  - Ingestion: Scale based on incoming data volume
  - Transformation: Scale based on queue depth
  - Analytics: Scale based on query load

Distribution:
  - Components distributed across 3 availability zones
  - Data replicated for durability
  - Regional deployment for latency optimization

14.4.3 Multi-Region Service Runtime

Runtime Topology: Global API Service

Deployment:
  - Region US-East: 5 API instances, 2 database replicas
  - Region US-West: 4 API instances, 2 database replicas
  - Region EU-West: 4 API instances, 2 database replicas

Scaling:
  - Each region scales independently
  - Global load balancer routes requests
  - Automatic failover between regions

Distribution:
  - Database master in primary region
  - Read replicas in all regions
  - Cross-region replication for consistency
  - DNS-based traffic routing

14.4.4 Task, Job, and Step — Execution Granularity

Execution within a workflow occurs through smaller operational units. These units represent the granularity of work performed during system execution.

Three related concepts appear frequently in system architectures.

A Task represents a discrete unit of work performed by a component. Tasks correspond to specific operations such as processing a request, executing a computation, or transforming data.

A Job represents a larger execution instance composed of one or more tasks. Jobs often correspond to scheduled processes, batch computations, or background operations.

A Step represents an individual stage within a workflow. Steps define the order in which tasks are executed and often correspond to logical stages in a processing pipeline.

These execution units form a hierarchy of granularity:

  • workflows coordinate execution structures

  • jobs represent runtime execution instances

  • tasks perform functional operations

  • steps define ordered execution within workflows

The ontology allows these units to be represented explicitly so that system behavior can be described in terms of execution structure rather than only component relationships.

14.4.5 Trigger — Initiating Execution

Workflows and jobs do not execute continuously. Their execution is initiated by triggers.

A Trigger represents the condition that causes a workflow or task to begin execution. Triggers connect system behavior to external events, internal signals, or scheduled conditions.

Three categories of triggers commonly appear in system architectures.

Time-based triggers

Time-based triggers initiate workflows according to scheduled intervals or specific timestamps. These triggers are commonly used in batch processing systems, maintenance operations, and periodic data synchronization tasks.

Event-based triggers

Event-based triggers initiate execution when a specific event occurs. Events may originate from external systems, message brokers, or internal components. Event-driven architectures rely heavily on this form of trigger.

Request-based triggers

Request-based triggers originate from direct interactions with system interfaces. Examples include API calls, user actions, or command invocations.

Triggers therefore connect system workflows to the broader system environment.

14.4.6 Runtime — Execution Topology

While workflows describe the logical coordination of execution, systems ultimately operate within runtime environments.

The runtime topology represents how components, workflows, and execution units are arranged during system operation. It describes where execution occurs and how runtime resources are allocated.

Runtime topology may include elements such as:

  • service instances

  • worker pools

  • container deployments

  • distributed processing nodes

  • orchestration controllers

Understanding runtime topology is important because architectural behavior often depends on runtime structure. Performance characteristics, reliability properties, and scaling behavior all emerge from the runtime configuration of system components.

Within the ontology, runtime entities provide the foundation for later architectural projections such as deployment views, operations views, and runtime observability models.

By linking workflows, execution units, triggers, and runtime topology, the ontology captures the operational dimension of system architecture, complementing the structural representation defined by components and interfaces.

14.5 Summary

While components define what exists in a system, workflows and execution units define how those elements cooperate to produce behavior. Workflows represent the orchestration logic — the structured sequences of operations that accomplish system objectives. Triggers connect workflows to real-world conditions (time, events, requests), and runtime topology describes where execution actually occurs.

14.5.1 Core Knowledge — Must Remember

Concept Key Insight
Workflow A structured sequence of operations that collectively accomplish a system objective. Includes ordered/conditional steps, branching, parallel execution, error handling, and termination conditions. Every workflow needs a trigger to initiate execution.
Execution hierarchy Workflow (highest — complete business process) → Job (single execution instance) → Task (discrete unit of work by a component) → Step (ordered stage within a workflow) → Function (code-level operation, implementation detail).
Trigger types Time-based (scheduled intervals), Event-based (specific events from message brokers or components), Request-based (API calls, user actions, command invocations). The trigger connects system behavior to the external environment.
Runtime topology Represents how components, workflows, and execution units are actually arranged during operation — service instances, worker pools, container deployments, processing nodes. Performance, reliability, and scaling behavior all emerge from runtime structure.
Operational dimension Workflows and execution units capture the behavioral layer of architecture, complementing the structural layer (components, interfaces, data). Together they form a complete representation of both form and behavior.
