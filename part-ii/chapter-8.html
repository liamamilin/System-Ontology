13  Data Entities and State

Software systems exist not only to perform computation but also to create, transform, store, and transmit data. Data therefore occupies a central role in architectural representation. Components process data, workflows move data between components, and system behavior often depends on the state encoded in stored information.

For this reason, the ontology treats data entities and state as first-class elements of system architecture. Explicitly representing data structures and their lifecycle allows system architectures to be analyzed in terms of data ownership, flow patterns, and persistence boundaries.

13.0.1 Data Entity — Business Entities vs Technical Entities

A Data Entity represents a structured unit of information managed by a system.

Data entities capture the logical structures through which information is represented, stored, and exchanged. They may correspond to domain concepts, operational records, or technical artifacts used internally by the system.

Two categories of data entities are particularly important.

Business Entities

Business entities represent domain concepts that are meaningful within the problem domain of the system. These entities correspond to real-world objects, processes, or relationships that the system models.

Examples may include:

  • user accounts

  • orders

  • transactions

  • documents

  • events generated by business processes

Business entities typically form the conceptual core of the system’s data model. Their structure often remains stable even as implementation technologies change.

Technical Entities

Technical entities represent data structures created for operational or infrastructural purposes. These entities support system execution rather than representing domain concepts.

Examples may include:

  • session records

  • cache entries

  • job queues

  • log records

  • configuration objects

While business entities model domain reality, technical entities support system functionality.

Distinguishing between these categories helps clarify the role of different data structures within system architecture.

13.0.2 State — System, Component, and Session State

Data entities give rise to state, which represents the current condition of a system or one of its components.

State reflects the accumulation of information over time. It influences how the system behaves and determines the outcomes of future operations.

State may appear at several levels.

System State

System state represents the global condition of the entire system. It may include aggregated data structures or shared storage resources that influence system-wide behavior.

Examples include global configuration settings or shared datasets.

Component State

Component state represents the internal state maintained by individual components. Components may store intermediate results, operational metadata, or internal caches that influence their behavior.

Some components operate statelessly, meaning that they do not maintain persistent state between interactions. Stateless components are often easier to scale and replicate.

Session State

Session state represents temporary information associated with a particular user interaction or workflow execution. This type of state often persists only for the duration of a session or task.

Examples include authentication sessions, temporary workflow contexts, or transient request metadata.

Explicitly modeling these forms of state allows architectural analysis of system reliability, scalability, and failure behavior.

13.0.3 Persistence — Storage and Lifecycle

State becomes durable through persistence mechanisms.

Persistence refers to the storage of data beyond the immediate execution context of a component. Persisted data survives process restarts, system redeployments, and other runtime events.

Persistence introduces several architectural considerations.

First, persistence mechanisms determine where data resides. Data may be stored in relational databases, document stores, object storage systems, or distributed key-value stores.

Second, persistence determines data ownership boundaries. Different components may own different data entities, which affects system coupling and coordination.

Third, persistence defines the lifecycle of data. Data entities may have lifetimes ranging from temporary caches to long-term historical records.

Representing persistence explicitly in the ontology allows architectural descriptions to capture storage responsibilities and data durability requirements.

13.0.4 Data Flow — Data as a First-Class Architectural Element

Data does not remain static within a system. It moves through components, workflows, and interfaces as it is processed and transformed.

These movements form data flows.

A data flow represents the transfer of information between architectural elements. It may correspond to:

  • API requests carrying structured payloads

  • events propagating through messaging systems

  • batch data transfers in pipelines

  • streaming data flows in real-time processing systems

Treating data flow as a first-class architectural element allows the ontology to capture how information travels through the system.

This perspective provides several benefits.

First, it reveals dependency relationships between components. Components that consume the same data sources or produce downstream outputs often become structurally coupled.

Second, it exposes processing pipelines that define system behavior. Many modern architectures are fundamentally organized around data pipelines rather than control flows.

Third, explicit data flow modeling enables analysis of system performance, reliability, and scalability.

Within the ontology, data flows connect components, workflows, and interfaces, forming a graph that describes how information moves across the architecture.

By representing data entities, state, persistence, and data flow explicitly, the ontology captures the informational dimension of system architecture alongside its structural and behavioral aspects.

13.3 Data Flow Patterns

13.3.1 Request-Response Data Flow

Client Request → Component A (reads cache) → [cache miss] → Component B (reads database) → Response
                  ↓
              [writes to cache]

Characteristics:
  - Synchronous interaction
  - Client waits for response
  - Often includes caching layers
  - Used in web applications and APIs

13.3.2 Event-Driven Data Flow

Component A (emits event) → Message Broker → Component B (consumes event)
                                        ↓
                                   Component C (consumes event)
                                        ↓
                                   Component D (consumes event)

Characteristics:
  - Asynchronous interaction
  - Producers don't know consumers
  - Multiple consumers possible
  - Loose coupling between components

13.3.3 Pipeline Data Flow

Input Data → Stage 1 (transform) → Stage 2 (transform) → Stage 3 (transform) → Output Data

Characteristics:
  - Sequential data transformation
  - Each stage processes data in order
  - Often used in data processing systems
  - Can be batch or streaming

13.3.4 Fan-Out/Fan-In Data Flow

Component A → Component B → Component E (aggregates)
            → Component C →
            → Component D →

Characteristics:
  - Parallel processing of same data
  - Results aggregated later
  - Used for distributed computation
  - Improves performance for independent operations

13.3.5 Broadcast Data Flow

Component A (publishes) → Component B (subscribes)
                     → Component C (subscribes)
                     → Component D (subscribes)

Characteristics:
  - One producer, multiple consumers
  - Same data sent to all consumers
  - Used for notifications and events
  - Loose coupling between publisher and subscribers

13.4 State Management Patterns

13.4.1 Stateless Component Pattern

Component processes requests without maintaining internal state:
  - All state stored externally (database, cache)
  - Requests are independent
  - Easy to scale horizontally
  - No session affinity required

Example: Stateless API Service
  - Request contains all needed context
  - Database stores all persistent data
  - Redis stores temporary session data
  - Multiple instances can handle any request

13.4.2 Stateful Component Pattern

Component maintains internal state:
  - State persists across requests
  - Session affinity may be required
  - More complex to scale
  - Lower latency for state-dependent operations

Example: Stateful Workflow Engine
  - Maintains workflow execution state
  - Tracks progress across multiple steps
  - Coordinates complex business processes
  - May require sticky sessions

13.4.3 Caching Layer Pattern

Cache layer reduces load on persistent storage:
  - Frequently accessed data cached
  - Reduces latency
  - Improves throughput
  - Introduces consistency challenges

Example: Read-Through Cache
  - Component A requests data
  - Cache checked first
  - Cache miss → fetch from database
  - Result stored in cache
  - Subsequent requests served from cache

13.4.4 Event Sourcing Pattern

State derived from sequence of events:
  - All state changes recorded as events
  - Current state computed from event history
  - Enables audit trails and replay
  - Different from CRUD operations

Example: Order System with Event Sourcing
  - Events: OrderCreated, PaymentReceived, OrderShipped
  - Current order state computed from events
  - Can reconstruct state at any point in time
  - Supports event-driven architecture

13.5 Summary

Data entities, state, persistence, and data flow capture the informational dimension of system architecture. Data entities are classified as Business Entities (domain concepts — stable, technology-independent) or Technical Entities (operational artifacts — session records, cache entries, logs). State appears at three levels: system, component, and session.

13.5.1 Core Knowledge — Must Remember

Concept Key Insight
Business Entity vs Technical Entity Business entities model domain reality (Order, User, Product) and remain stable across implementation changes. Technical entities support system execution (Session, CacheEntry, JobQueue) and are operationally focused.
State levels System state: global condition (config, feature flags). Component state: internal data maintained by individual components. Session state: temporary context tied to a user interaction or workflow execution. Stateless components are easier to scale; stateful ones provide lower latency for state-dependent operations.
Persistence Determines where data resides, data ownership boundaries, and data lifecycle (from temporary cache to long-term archive). Persistence mechanisms (databases, object stores, caches) define the durability and availability properties of data.
Data flow patterns Data moves through systems via recurring patterns: Request-Response (synchronous), Event-Driven (asynchronous, loose coupling), Pipeline (sequential transformation), Fan-Out/Fan-In (parallel processing), and Broadcast (one-to-many notification).
State management patterns Stateless (all state external — easy to scale), Stateful (internal state — requires session affinity), Caching Layer (reduces load on storage — introduces consistency challenges), Event Sourcing (state derived from event history — enables audit and replay).
