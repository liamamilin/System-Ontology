10  Capability and Requirement Entities

Architectural descriptions must capture not only what a system is composed of, but also what the system is intended to do and under what conditions it must operate. Two classes of entities are therefore required: those that represent system abilities, and those that represent constraints placed upon those abilities.

Within the ontology, these concerns are modeled through Capability entities and Requirement/Constraint entities. Capabilities describe the functional potential of a system, while constraints specify the conditions under which those capabilities must operate.

Together, they connect architectural structure with system intent.

10.0.1 Capability — Functional Ability Units

A Capability represents something the system is able to perform.

Capabilities describe functional abilities at the level of system behavior rather than implementation structure. They answer the question:

What can this system do?

Examples of capabilities include:

  • process user requests

  • store and retrieve data

  • schedule background jobs

  • execute workflows

  • generate predictions

  • expose programmable interfaces

Capabilities differ from components. A component is a structural unit of the system, while a capability represents behavior that may be realized through one or more components and workflows.

This distinction is important because a capability can remain stable even when the internal implementation of the system changes.

For example, a system capability such as data ingestion may be implemented through different architectural mechanisms over time. The capability persists even as the underlying components evolve.

Capabilities therefore serve as stable functional anchors within blueprint representations.

10.0.2 Requirement and Constraint

While capabilities describe what the system can do, requirements and constraints describe the conditions under which the system must operate.

In the ontology, these elements are represented primarily as Constraint entities.

Constraints encode system limitations, quality expectations, or operational conditions that affect system behavior. They typically correspond to non-functional requirements such as:

  • performance requirements

  • reliability targets

  • security policies

  • compliance rules

  • resource limitations

Constraints attach to architectural entities and define measurable conditions that must be satisfied.

A constraint representation typically contains several elements:

  • the metric being evaluated

  • the threshold or acceptable range

  • the scope of the constraint

  • the evaluation context

For example, a latency constraint might specify that a particular interface must respond within a defined time limit. A reliability constraint might require that a workflow achieve a specified success rate.

By representing requirements as structured constraints rather than narrative descriptions, the ontology enables these conditions to be analyzed and evaluated systematically.

10.0.3 Use Case and User Story as Projections

Software development practices often rely on artifacts such as use cases or user stories to describe system behavior.

Within the Blueprint Architecture framework, these artifacts are not treated as primary ontology entities.

Instead, they are considered projections of the underlying system structure.

Use cases and user stories describe interactions from the perspective of users or stakeholders. They are narrative representations of how capabilities are exercised through system interfaces.

Because these artifacts focus on scenarios rather than structural relationships, they are best interpreted as views generated from the ontology, rather than as elements of the ontology itself.

For example, a user story describing how a user uploads a file may correspond to several ontology elements:

  • a capability for data ingestion

  • an interface receiving the request

  • a workflow processing the file

  • components responsible for storage

The narrative scenario is therefore derived from the structural representation rather than serving as its foundation.

This separation prevents scenario descriptions from fragmenting the ontology while still allowing them to be generated as documentation views.

10.0.4 Capability Decomposition and Capability Trees

Capabilities rarely exist in isolation. Complex systems typically provide multiple capabilities that can be decomposed into smaller functional units.

To support this decomposition, capabilities can be organized into capability trees.

A capability tree represents hierarchical relationships between capabilities. At higher levels, broad system abilities are defined. These abilities can then be decomposed into more specific sub-capabilities.

For example:

  • data processing

    • data ingestion

    • data transformation

    • data storage

    • data retrieval

Each level of the tree represents a finer level of functional detail.

Capability decomposition follows several principles.

First, each capability should represent a coherent functional responsibility. The capability should describe an ability that can be clearly understood without referencing implementation details.

Second, decomposition should proceed only until the capability can be reasonably mapped to system workflows or component responsibilities. Excessively granular capability definitions provide little architectural value.

Third, capabilities should remain independent of specific technologies. The purpose of capability representation is to capture functional intent rather than implementation mechanisms.

When structured in this way, capability trees provide a stable link between system goals, architectural structures, and user-facing functionality.

They allow blueprint representations to connect high-level system purpose with the components and workflows that realize that purpose.

10.2 Capabilities vs. Components: Practical Distinction

10.2.1 When to Use Capabilities

Capabilities describe what a system does. They are:

  • Stable across implementations: Different technical approaches can provide the same capability
  • User-facing: Capabilities correspond to features users can observe and use
  • High-level: Capabilities don’t specify how functionality is implemented

Example: “Process Payments” is a capability. It doesn’t specify whether payments are processed through a REST API, GraphQL, or event-driven architecture.

10.2.2 When to Use Components

Components describe how functionality is implemented. They are:

  • Technical structures: Components correspond to code modules, services, or deployable units
  • Implementation-specific: Different implementations may use different component structures
  • Low-level: Components specify the technical mechanisms for delivering capabilities

Example: “Payment Service” is a component. It specifies a service that handles payment processing through specific interfaces and implementation patterns.

10.2.3 Mapping Capabilities to Components

A single capability may be realized by multiple components working together:

Capability: Process Payments

Realized by components:
  - Payment Gateway (receives payment requests)
  - Payment Processor (processes transactions)
  - Transaction Store (persists transaction records)
  - Fraud Detection Service (validates transactions)
  - Notification Service (sends payment confirmations)

A single component may contribute to multiple capabilities:

Component: Order Service

Contributes to capabilities:
  - Create Order (primary responsibility)
  - Update Inventory (coordinates with inventory)
  - Generate Confirmation (triggers notifications)
  - Track Order Status (provides status updates)

10.3 Constraints in Practice

API Response Time:
  - Metric: p95_latency_ms
  - Threshold: ≤300
  - Scope: int.api.public

  - Metric: requests_per_second
  - Threshold: ≥1000
  - Scope: sys.main

  - Metric: availability_percentage

  - Threshold: <0.0001%

10.3.2 Constraint Conflicts and Trade-offs

Example 1: Performance vs. Security

System: E-commerce Platform

Constraints:
  - Performance: API response time ≤200ms
  - Security: All requests must undergo comprehensive security checks

Conflict: Comprehensive security checks add latency, potentially violating the performance constraint.

Trade-off decision:
  - Accept slightly higher latency (≤300ms) to maintain security requirements
  - Implement security checks efficiently (caching, parallel validation)
  - Document the trade-off in constraint metadata

Example 2: Availability vs. Cost

System: Data Storage Service

Constraints:
  - Availability: ≥99.99%
  - Cost: Monthly operational cost ≤$10,000

Conflict: Achieving 99.99% availability requires multi-region deployment, exceeding cost constraints.

Trade-off decision:
  - Accept lower availability (99.95%) to meet cost constraints
  - Implement disaster recovery procedures for critical data
  - Prioritize availability for high-value customers

Example 3: Consistency vs. Latency

System: Distributed Database

Constraints:
  - Consistency: Strong consistency required for financial transactions
  - Latency: Read latency ≤50ms

Conflict: Strong consistency requires synchronous replication, increasing read latency.

Trade-off decision:
  - Use strong consistency only for financial operations
  - Use eventual consistency for analytics queries
  - Implement different consistency levels per operation type
