11  Components: The Structural Building Blocks

Within system architecture, components represent the primary structural units from which systems are constructed. While capabilities describe what a system can do, components represent how those abilities are realized through concrete structural elements.

A component encapsulates a set of responsibilities and exposes defined interfaces through which other components interact with it. Components therefore form the nodes of the architectural structure, connected through interfaces, data flows, and workflows.

In the ontology, components serve as the central elements of the structural layer. Most architectural relations—dependencies, data access, invocation, and orchestration—are defined between components.

11.0.1 Component vs Module vs Service

In practice, terms such as component, module, and service are often used interchangeably. For architectural representation, however, these concepts must be distinguished.

A component is the general structural unit of the ontology. It represents a bounded element of a system that performs a defined responsibility and interacts with other components through interfaces.

A module refers to a logical grouping of implementation elements within a codebase. Modules are often defined by programming language constructs such as packages, namespaces, or libraries. Modules are therefore primarily organizational structures inside source code.

A service is a component that exposes functionality through a network-accessible interface and operates as an independently deployable runtime unit.

In this sense:

  • module describes code organization

  • service describes runtime deployment behavior

  • component describes architectural structure

Within the ontology, the component is the canonical entity. Modules and services can be interpreted as specialized forms or projections of components depending on the architectural view being generated.

11.0.2 Common Component Types (Type Set v0.1)

Although the ontology core remains minimal, a practical architectural vocabulary requires a small set of commonly occurring component types. These types help standardize architectural descriptions across systems.

The following component types represent a typical minimal set.

API Gateway / API Service

API gateways act as entry points for external requests. They route traffic, enforce authentication, and manage request flows into internal services.

API services implement business logic and expose programmable interfaces through HTTP, RPC, or similar protocols.

Examples: - An API Gateway routing requests to microservices - A REST API service handling user account management - A GraphQL API service providing flexible data querying

Characteristics: - Network-accessible interfaces - Stateless request processing - Horizontal scalability - Authentication and authorization enforcement

Worker / Scheduler

Workers execute background processing tasks such as data transformation, job execution, or asynchronous processing.

Schedulers coordinate the execution of jobs according to time-based triggers or dependency conditions.

Examples: - A background worker processing email notifications - A batch job aggregator computing daily analytics - A scheduler triggering nightly data backups

Characteristics: - Asynchronous execution - Event-driven or time-triggered - Queue-based task distribution - Fault-tolerant retry mechanisms

Storage / Cache

Storage components persist data for long-term access. Examples include relational databases, object stores, and document stores.

Cache components store temporary data in order to reduce latency or reduce load on persistent storage systems.

Examples: - PostgreSQL database storing user records - Redis cache storing session data - S3 object store storing uploaded files

Characteristics: - Data persistence across process restarts - ACID transactions (for databases) - High throughput read/write operations - Data backup and recovery capabilities

Queue / Broker

Queue components buffer tasks or messages between producers and consumers.

Message brokers coordinate asynchronous communication across components through publish–subscribe or event streaming models.

Examples: - RabbitMQ message queue buffering API requests - Apache Kafka broker streaming events between services - AWS SQS queue storing background jobs

Characteristics: - Asynchronous message passing - Message durability and ordering - Decoupling of producers and consumers - Support for multiple consumers

UI / CLI

User interface components provide interactive access to system functionality through graphical or textual interfaces.

Command-line interfaces expose system capabilities through terminal commands and scripts.

Examples: - React web application providing user interface - Command-line tool for system administration - Mobile application interface

Characteristics: - Human-computer interaction - Stateful user sessions - Responsive to user actions - Multiple interaction modes (mouse, keyboard, touch)

Model / Policy / Engine

Model components represent computational models such as machine learning predictors or rule engines.

Policy components encode decision logic such as authorization policies or routing policies.

Engine components execute domain-specific logic, such as workflow engines or processing engines.

Examples: - Machine learning model for recommendation predictions - Authorization policy engine evaluating access rules - Workflow engine orchestrating business processes

Characteristics: - Encapsulated domain logic - Pluggable or configurable behavior - Stateless or stateful depending on design - Often language-specific implementations

These component types serve as a baseline vocabulary for describing system architectures. They are intentionally broad so that they remain applicable across different technological environments.

11.1.6 Component Attributes

Each component in the ontology is described through a set of attributes that capture its architectural role.

Responsibility

The responsibility defines the primary function of the component. It describes what role the component plays within the system architecture.

Inputs and Outputs

Components consume inputs and produce outputs. These inputs and outputs may correspond to:

  • API requests

  • events or messages

  • data streams

  • command invocations

Explicitly describing inputs and outputs clarifies how components interact with one another.

Dependencies

Components rarely operate independently. Dependencies describe which other components a given component relies upon in order to perform its responsibilities.

Dependency relations may represent synchronous invocation, asynchronous messaging, or data access relationships.

State

Some components maintain internal state, while others operate statelessly. The state attribute describes whether the component stores persistent or transient information during operation.

State characteristics influence system properties such as scalability, fault tolerance, and recovery behavior.

Together, these attributes define the architectural identity of a component.

11.1.7 Component Boundaries

One of the most important architectural decisions concerns where component boundaries should be drawn.

Component boundaries determine responsibility allocation, coupling relationships, and system maintainability. Poorly chosen boundaries can lead to tightly coupled systems that are difficult to evolve.

Two opposing risks must be managed.

If components are too large, responsibilities become entangled and the component becomes difficult to maintain or reuse.

If components are too small, the architecture becomes fragmented and coordination overhead increases.

Several principles help guide boundary decisions.

A component should encapsulate a coherent responsibility. All internal logic should contribute to a single architectural purpose.

Components should expose interaction only through explicit interfaces. Internal details should remain hidden from other parts of the system.

Dependencies between components should remain minimized and directional. Excessive cross-dependencies indicate that boundaries may be incorrectly defined.

Finally, component boundaries should align with operational realities, such as deployment units, scaling boundaries, or ownership responsibilities.

Determining component boundaries is therefore both a structural and operational decision. The ontology provides the conceptual framework for representing these boundaries, while architectural judgment determines how they are applied in specific systems.

11.2 Component Boundary Decision Framework

11.2.1 Boundary Indicators

Strong indicators that separate components:

  1. Different scaling requirements: One component needs horizontal scaling while another scales vertically
  2. Different failure domains: Failure of one component shouldn’t cascade to others
  3. Different deployment cycles: Components need to be deployed independently
  4. Different ownership: Different teams are responsible for different functionality
  5. Different technology stacks: Components use different programming languages or frameworks
  6. Different data ownership: Components manage separate data domains with different access patterns

Weak indicators (should not alone justify separation):

  1. Code size: Large codebases don’t necessarily require multiple components
  2. Complexity alone: Internal complexity doesn’t always justify component separation
  3. Temporary optimization: Short-term performance needs shouldn’t dictate architecture

11.2.2 Component Boundary Patterns

Domain-Driven Components

Align components with business domains or bounded contexts:

E-commerce System:
  - Order Management (orders, order items, order history)
  - Inventory Management (products, stock levels, suppliers)
  - Customer Management (users, profiles, preferences)
  - Payment Processing (transactions, refunds, disputes)

Layer-Based Components

Align components with architectural layers:

Web Application:
  - Presentation Layer (web UI, API clients)
  - Application Layer (business logic, validation)
  - Data Layer (persistence, caching)

Capability-Based Components

Align components with system capabilities:

Analytics Platform:
  - Data Ingestion Component (collects data from sources)
  - Data Processing Component (transforms and cleans data)
  - Data Storage Component (manages data persistence)
  - Analytics Component (provides query and reporting)

11.2.3 Boundary Evaluation Checklist

Component cohesion: Does the component have a single, well-defined responsibility?

Interface clarity: Are the component’s interfaces well-defined and stable?

Dependency direction: Do dependencies flow in one clear direction?

Operational independence: Can the component be deployed and scaled independently?

Team ownership: Does a single team have clear ownership of the component?

Failure isolation: Does failure of this component minimize impact on other components?

Evolution potential: Can the component evolve without breaking other components?

11.2.4 Common Boundary Anti-Patterns

God Component: A single component that does everything - Symptoms: Thousands of lines of code, handles multiple domains - Problems: Difficult to test, deploy, and maintain - Solution: Split by domain or capability

Chatty Components: Components that make excessive calls to each other - Symptoms: High network traffic, tight coupling through frequent interactions - Problems: Poor performance, difficult to scale independently - Solution: Combine chatty components or redesign interaction patterns

Leaky Boundaries: Components that expose internal details through interfaces - Symptoms: APIs that expose data structures or implementation details - Problems: Tight coupling, difficult to evolve independently - Solution: Design abstract interfaces that hide implementation

Orphan Components: Components with unclear purpose or ownership - Symptoms: Unused code, unclear responsibilities - Problems: Maintenance burden, confusion for developers - Solution: Remove if unused, clarify purpose if needed

11.3 Component to Implementation Mapping

While the ontology defines components at the architectural level, implementations may map to various structures:

Component: User Service

Possible implementations:
  - Single monolithic service (Node.js, Express)
  - Microservice with multiple sub-services
  - Serverless functions (AWS Lambda)
  - Containerized application (Docker)
  - Kubernetes deployment

The architectural component remains the same regardless of implementation choice. The ontology captures the architectural concept, not the implementation details.
