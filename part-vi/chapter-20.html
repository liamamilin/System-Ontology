25  Ontology → Blueprint Extraction Signals & Mapping Rules

The ontology defines the conceptual language used to describe system architecture. However, for blueprint datasets to be constructed at scale, architectural representations must often be derived from existing software systems rather than written manually.

Blueprint extraction addresses this problem. It refers to the process of inferring ontology entities and relations from observable signals in software repositories and system artifacts.

Extraction does not attempt to perfectly reconstruct architecture from code. Instead, it produces a structured architectural hypothesis that can be refined through automated analysis and human review.

This section defines the signals used for extraction, the mapping rules that translate those signals into ontology structures, and the mechanisms used to handle uncertainty.

25.0.1 Repository Signals

Software repositories contain a variety of signals that reflect architectural structure. These signals can be analyzed to infer components, interfaces, workflows, and other ontology entities.

Several categories of repository signals are particularly informative.

Directory structure

The organization of directories often reflects architectural boundaries. For example, directories may correspond to modules, services, or subsystems.

Directories containing source code, configuration files, or build definitions frequently indicate component boundaries.

Dependency declarations

Dependency files describe the libraries and services used by a system. Examples include package manifests, build configurations, and module dependency definitions.

These declarations can reveal relationships between components and identify external dependencies.

Entry points

Executable entry points indicate where system execution begins. Examples include application start scripts, service launch commands, and workflow definitions.

Entry points often correspond to service components, worker processes, or command-line interfaces.

Configuration files

Configuration files frequently contain references to system infrastructure such as message queues, databases, or external services.

These references provide signals about storage components, messaging systems, and runtime dependencies.

Deployment descriptors

Deployment configurations, container definitions, or infrastructure manifests reveal how components are instantiated and connected in runtime environments.

These artifacts provide signals about service boundaries, runtime topology, and scaling units.

Together, these repository signals form the observable evidence from which blueprint extraction algorithms infer system structure.

25.2 Mapping Rule Examples

25.2.1 Component Entity Mapping

Rule 1: Service Component Detection

Signals Required:
  - Entry point file (e.g., Application.java, index.js, main.py)
  - HTTP server configuration (e.g., app.listen, @SpringBootApplication)
  - API endpoint definitions (e.g., app.get, @RequestMapping)

Confidence: High (0.9)

Evidence:
  - File: src/main/java/PaymentServiceApplication.java
  - Pattern: @SpringBootApplication
  - Pattern: SpringApplication.run()

Mapping:
  Entity: PaymentService
  Type: API Service
  Attributes:
    - identifier: "PaymentService"
    - language: "Java"
    - framework: "Spring Boot"
  Relations:
    - implements: ["PaymentProcessing"]
    - provides: ["PaymentAPI"]

Rule 2: Worker Component Detection

Signals Required:
  - Worker entry point (e.g., worker.py, Worker.java)
  - Queue/Message broker dependency (e.g., Celery, Kafka client)
  - Task/job definitions (e.g., @app.task, @Scheduled)

Confidence: High (0.85)

Evidence:
  - File: src/main/java/DataProcessorWorker.java
  - Dependency: spring-kafka
  - Pattern: @KafkaListener

Mapping:
  Entity: DataProcessorWorker
  Type: Worker
  Attributes:
    - identifier: "DataProcessorWorker"
    - language: "Java"
    - framework: "Spring Kafka"
  Relations:
    - consumes: ["DataEvents"]
    - processes: ["DataTransformation"]

Rule 3: Storage Component Detection

Signals Required:
  - Database driver dependency (e.g., postgresql, mongoose)
  - Database configuration (e.g., datasource, MONGODB_URI)
  - Repository/Data access classes (e.g., @Repository, .repository/)

Confidence: High (0.9)

Evidence:
  - Dependency: postgresql
  - Configuration: spring.datasource.url=jdbc:postgresql://...
  - Directory: src/main/java/com/myapp/repository/

Mapping:
  Entity: ProductDatabase
  Type: Storage
  Attributes:
    - identifier: "ProductDatabase"
    - databaseType: "PostgreSQL"
  Relations:
    - contains: ["Product", "ProductCategory"]
    - accessed_by: ["ProductService"]

Rule 4: Queue/Broker Component Detection

Signals Required:
  - Message broker dependency (e.g., kafka, redis-rabbitmq)
  - Queue/topic configuration (e.g., spring.kafka, QUEUE_URL)
  - Producer/consumer annotations (e.g., @KafkaListener, @RabbitListener)

Confidence: High (0.9)

Evidence:
  - Dependency: spring-kafka
  - Configuration: spring.kafka.bootstrap-servers=kafka:9092
  - Pattern: @KafkaListener(topics = "data-input")

Mapping:
  Entity: MessageQueue
  Type: Queue/Broker
  Attributes:
    - identifier: "MessageQueue"
    - brokerType: "Kafka"
  Relations:
    - contains: ["DataEvents", "TransformedEvents"]

25.2.6 Mapping Rules

Signals obtained from repositories must be translated into ontology entities and relations. This translation is performed through mapping rules.

A mapping rule defines how a particular signal corresponds to elements in the ontology.

For example:

  • a directory containing an executable entry point may map to a component entity

  • a configuration referencing a database may map to a storage component

  • a dependency on a messaging framework may map to a queue or broker component

  • an HTTP routing configuration may map to an interface entity

Mapping rules therefore connect observable artifacts to architectural structures.

In practice, these rules often rely on combinations of signals rather than single indicators. For example, identifying a service component may require the presence of both an executable entry point and a network interface configuration.

Through these mapping rules, repository signals are transformed into structured ontology graphs representing candidate blueprint architectures.

25.2.7 Representing Ambiguity

Extraction processes inevitably encounter ambiguity.

Source code structures may not clearly indicate architectural intent, and different architectural interpretations may be possible for the same repository structure.

For this reason, blueprint extraction must represent uncertainty explicitly.

Two mechanisms are used for this purpose.

Confidence

Each extracted entity or relation can be associated with a confidence score representing the likelihood that the inferred structure is correct.

Confidence scores are typically derived from the strength and consistency of the signals used during extraction.

Evidence

Evidence records the specific repository signals that led to the extraction of a particular entity or relation.

Examples of evidence include file paths, dependency declarations, or configuration references.

By recording evidence alongside extracted structures, the system provides traceability and enables human reviewers to understand how architectural inferences were made.

Although automated extraction can generate initial blueprint representations, architectural interpretation often requires human judgment.

For this reason, blueprint extraction systems incorporate human-in-the-loop review stages.

At these stages, extracted entities and relations are presented to human reviewers who validate, modify, or reject the inferred structures.

Effective review systems typically include:

  • visual representations of the extracted architecture graph

  • links to the repository artifacts used as evidence

  • interfaces for editing or confirming extracted entities and relations

Human review transforms automatically generated architectural hypotheses into verified blueprint representations.

This process enables blueprint extraction to scale across large collections of repositories while maintaining architectural accuracy.

Through repository signals, mapping rules, uncertainty representation, and human review mechanisms, blueprint extraction bridges the gap between existing software systems and structured architectural knowledge.

25.6 Summary

Blueprint extraction is the process of inferring ontology instances from existing software repositories by analyzing structural signals — directory layouts, dependency declarations, entry points, configuration files, and deployment descriptors. The extracted representation includes confidence scores for each entity and relation, enabling human reviewers to focus on uncertain elements.

25.6.1 Core Knowledge — Must Remember

Concept Key Insight
Repository signals The primary evidence for extraction: directory structure (reveals component boundaries), dependency declarations (reveals service dependencies), entry points (reveals service boundaries), configuration files (reveals infrastructure and middleware), deployment descriptors (reveals topology and scaling behavior).
Mapping rules Transform signals into ontology entities and relations. Rules map directory names to component types, dependency declarations to depends_on relations, entry points to interface definitions, and configuration patterns to architectural decisions.
Confidence scoring Not all extracted elements are equally certain. Each entity and relation receives a confidence score (0.0–1.0). High confidence (>0.85): directly observed. Medium (0.7–0.85): inferred from patterns. Low (<0.7): requires human review.
Human-in-the-loop review Automated extraction generates hypotheses; architectural interpretation requires human judgment. Reviewers validate, modify, or reject extracted structures using visual graphs, evidence links, and editing interfaces. This transforms hypotheses into verified blueprints.
Extraction workflow Repository Analysis → Signal Collection → Entity Extraction → Relation Extraction → Ambiguity Assessment → Human Review → Blueprint Generation → Validation → Publication. Each step is traceable with evidence links back to source repository files.

Blueprint extraction reduces manual documentation time by ~80% while producing more consistent and traceable architecture representations than traditional manual methods. It enables scaling architectural knowledge capture across large collections of repositories.
