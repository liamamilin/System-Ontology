24  Ontology → Blueprint Kernel Mapping

The ontology defined in this volume provides the semantic vocabulary for representing systems. However, architectural knowledge within the Blueprint Architecture framework is ultimately organized through the Blueprint Kernel, introduced in the Foundations volume.

The kernel provides a stable structural container consisting of six slots:

  • Goal

  • Capabilities

  • Components

  • Interfaces

  • Data

  • Workflows

The ontology and the kernel therefore operate at different layers. The kernel defines where information is organized, while the ontology defines what entities populate that structure.

This section describes how ontology entities map onto the blueprint kernel and how different architectural views can be generated from the same underlying representation.

24.0.1 Mapping the Kernel Slots to Ontology

Each kernel slot corresponds to a set of ontology entities and relations.

Goal

The goal slot represents the purpose of the system. It is typically associated with system-level capability entities and contextual descriptions of system objectives.

Within the ontology, the goal slot is represented through:

  • system entities

  • high-level capability entities

  • stakeholder context relationships

Capabilities

The capabilities slot contains entities representing the functional abilities of the system.

Within the ontology, these are represented directly by capability entities and their hierarchical relationships within capability trees.

These entities capture what the system is designed to accomplish independently of implementation details.

Components

The components slot contains the structural units that implement system capabilities.

Within the ontology, this slot is populated by component entities and their structural relationships such as containment, dependency, and invocation.

These entities define the architectural structure of the system.

Interfaces

The interfaces slot contains the interaction points between components or between the system and external actors.

Within the ontology, these are represented by interface entities and their associated contracts.

These interfaces define the communication boundaries that connect system elements.

Data

The data slot represents the information structures managed by the system.

In the ontology, this slot corresponds to data entities, along with relations describing data access, persistence, and data flow.

Workflows

The workflows slot represents execution structures that coordinate system behavior.

Within the ontology, workflows are represented through workflow entities and execution units such as tasks and steps.

These entities capture how system activities are orchestrated over time.

Through this mapping, the ontology provides the semantic elements that populate the blueprint kernel structure.

24.1.1 Example: E-commerce Platform

System: E-commerce Platform

GOAL SLOT:
  System Entity: E-commercePlatform
    - Type: Web Application
    - Description: Online retail platform for product sales
    - Context: B2C commerce domain

  High-Level Capability: OnlineShopping
    - Type: Capability
    - Description: Enable customers to browse and purchase products
    - Relation: part_of(E-commercePlatform)

  Stakeholder Context:
    - Customer: Wants to buy products easily
    - Merchant: Wants to sell products and manage inventory
    - Admin: Wants to monitor platform operations

    - Type: Capability
    - Description: Browse and search products

  Workflow: ProductSearchWorkflow
    - Type: Workflow
    - Description: Search for products
    - Steps:
      1. User enters search query

      1. Order Service requests payment
      2. Payment Service validates payment method
      3. Payment Service calls External Payment Gateway
      4. External Payment Gateway processes payment
      5. Payment Service receives result
      6. Payment Service updates Transaction Database
      7. Payment Service returns result to Order Service

24.1.4 Minimal Attribute Sets

For blueprint representations to remain consistent across systems, each ontology entity must include a minimal set of attributes.

These attributes provide the essential metadata required to describe architectural elements while avoiding unnecessary complexity.

Typical minimal attributes include:

  • identifier — a unique name for the entity

  • type — the ontology type of the entity

  • description — a concise explanation of the entity’s role

  • relations — references to related entities

  • scope — the architectural context in which the entity exists

Additional attributes may be added when necessary, but these minimal fields ensure that blueprint representations remain structurally comparable.

Minimal attribute sets enable blueprint datasets to be stored, indexed, and analyzed consistently.

24.3.4 Blueprint Projections

Different stakeholders require different representations of the same system architecture.

A system architect may focus on component relationships, while an operations engineer may focus on runtime behavior. A product designer may instead focus on system capabilities and user interactions.

To accommodate these perspectives, blueprint representations support projections.

A projection is a transformation of the ontology graph into a view tailored for a particular audience or purpose.

Three projections commonly appear within the Blueprint Architecture framework.

Architecture View

The architecture view focuses on structural relationships between components, interfaces, and data flows.

This view emphasizes component dependencies, communication paths, and system boundaries.

It is typically used by system architects and engineers responsible for system design.

Specification View

The specification view emphasizes system capabilities, interfaces, and constraints.

This view is often used for system documentation, integration contracts, and design specifications.

Specification views make it easier to understand what the system does and how it can be interacted with.

Operations View

The operations view focuses on runtime structure and operational concerns.

It includes deployment topology, scaling boundaries, monitoring structures, and reliability mechanisms.

This view supports system operators and infrastructure engineers.

All of these views originate from the same ontology representation but emphasize different subsets of entities and relations.

24.3.5 Generating Multiple Views from One System

Consider a system that processes incoming data streams, transforms the data, and exposes processed results through an API.

Within the ontology representation, this system might include:

  • a data ingestion component

  • a transformation engine

  • a storage component

  • an API interface

  • a workflow coordinating data processing steps

From this representation, different projections can be generated.

The architecture view highlights the structural arrangement of components and their dependencies.

The specification view focuses on the capabilities of the system, the interfaces it exposes, and the data structures it manages.

The operations view highlights runtime characteristics such as scaling workers, monitoring pipelines, and failure handling mechanisms.

Although these views appear different, they all originate from the same underlying ontology graph.

This ability to generate multiple representations from a single structural model is essential for making blueprint representations usable across diverse engineering roles.
