7  The Ontology Stack

A system ontology must balance two competing requirements. On one hand, it must remain abstract enough to apply across different types of systems and domains. On the other hand, it must be concrete enough to describe real architectures with operational precision.

To achieve this balance, the ontology used in the Blueprint Architecture framework is organized as a layered stack. Each layer describes systems at a different level of abstraction while remaining connected to the others.

This layered structure allows the ontology to capture both conceptual meaning and concrete architectural structure without collapsing these concerns into a single representation.

7.1 The Challenge of Abstraction vs. Concreteness

7.1.1 The Abstraction Problem

If an ontology is too abstract:

Too Abstract:
  Entity: "Thing"
  Relation: "Related to"

Problem: Too general to be useful

Everything becomes a “thing related to other things”—the ontology provides no discriminatory power for architectural analysis.

7.1.2 The Concreteness Problem

If an ontology is too concrete:

Too Concrete:
  Entity: "REST API v2.1.3 endpoint"
  Entity: "PostgreSQL 14.2 table"
  Relation: "JDBC connection pool"

Problem: Too specific, technology-dependent, rapidly obsolete

The ontology becomes tied to specific technologies and quickly becomes outdated as technology evolves.

7.1.3 The Balance

We need an ontology that is:

  • Abstract enough: To apply across different technologies and domains
  • Concrete enough: To represent real architectural structures precisely
  • Stable enough: To remain useful over time
  • Extensible enough: To accommodate new architectural concepts

The layered stack achieves this balance by separating different levels of abstraction while maintaining clear connections between them.

7.2 Three Layers of the Ontology Stack

The ontology stack consists of three interconnected layers:

┌─────────────────────────────────────────────────────────┐
│              Operational Ontology                        │
│              (How systems behave in execution)           │
├─────────────────────────────────────────────────────────┤
│              Structural Ontology                         │
│              (How systems are organized)                 │
├─────────────────────────────────────────────────────────┤
│              Concept Ontology                            │
│              (What exists in system architecture)         │
└─────────────────────────────────────────────────────────┘

Each layer serves a distinct purpose while building on the layers below it.

7.3.2 Layer Relationships and Flow

CONCEPT ONTOLOGY (Vocabulary)
          ↓ defines
STRUCTURAL ONTOLOGY (Architecture)
          ↓ describes
OPERATIONAL ONTOLOGY (Behavior)

Flow of Abstraction:
  1. Concept Layer: "What exists?"
     → Defines System, Component, Interface entities
     → Defines contains, calls, implements relations

  2. Structural Layer: "How is it organized?"
     → Instances: EcommercePlatform, ProductService, ProductAPI
     → Structure: Platform contains Service provides API

  3. Operational Layer: "How does it behave?"
     → Execution: Order placement workflow steps
     → Behavior: Service calls another service, retries on failure

Flow of Implementation:
  1. Concept Layer (Stable foundation)
     → Changes rarely (major versions only)
     → Provides shared vocabulary

  2. Structural Layer (System-specific)
     → Changes per system (different architectures)
     → Provides architecture descriptions

  3. Operational Layer (Runtime-specific)
     → Changes per deployment (different environments)
     → Provides runtime insights

7.3.3 Concrete Example: E-commerce Platform

CONCEPT LAYER (Vocabulary):
  Entity Types:
    - System: Bounded architectural unit with a goal
    - Component: Structural building block
    - Interface: Interaction boundary
    - Data Entity: Information structure

  Relation Types:
    - contains: Containment relationship
    - calls: Invocation relationship
    - provides: Interface provision

STRUCTURAL LAYER (Architecture):
  Entity Instances:
    - EcommercePlatform (System type)
    - ProductService (Component type: API Service)
    - OrderService (Component type: API Service)
    - ProductAPI (Interface type: REST API)
    - OrderAPI (Interface type: REST API)
    - Product (Data Entity type: Business Entity)
    - Order (Data Entity type: Business Entity)

  Structural Relationships:
    - EcommercePlatform contains [ProductService, OrderService]
    - ProductService provides ProductAPI
    - OrderService provides OrderAPI
    - OrderService calls ProductService
    - ProductService owns Product
    - OrderService owns Order

  Architecture Style:
    - Microservices (multiple independent services)
    - RESTful communication
    - Shared-nothing architecture

OPERATIONAL LAYER (Behavior):
  Workflows:
    - Product Search Workflow:
      1. User submits search query
      2. WebFrontend calls ProductAPI.search
      3. ProductService queries Product database
      4. ProductService returns results
      5. WebFrontend displays results

    - Order Placement Workflow:
      1. User adds items to cart
      2. User initiates checkout
      3. OrderService creates order
      4. OrderService calls ProductService (validate inventory)
      5. OrderService calls PaymentService (process payment)
      6. OrderService confirms order
      7. OrderService updates Order database

  Runtime Behavior:
    - ProductService: Handles 1000 req/s average
    - OrderService: Handles 500 req/s average
    - Latency: 95th percentile < 200ms
    - Availability: 99.9% uptime
    - Retry mechanism: 3 attempts with exponential backoff
    - Circuit breaker: Opens after 5 consecutive failures

  State Transitions:
    - Order states: pending → processing → shipped → delivered
    - Payment states: authorized → captured → settled
    - Product states: available → reserved → sold

7.3.4 Layer Stability and Evolution

Layer Stability Matrix:

Layer           | Stability | Change Frequency | Version Impact
----------------|-----------|------------------|----------------
Concept         | Very High | Rare (years)     | Major versions
Structural      | Medium    | Per system       | Minor versions
Operational     | Low       | Per deployment   | Continuous

Evolution Example:

v1.0 (Concept Layer):
  - Defines core entities: System, Component, Interface
  - Defines core relations: contains, calls, implements
  - Stable for 3+ years

v1.1-v1.5 (Structural Layer):
  - New component types added: API Gateway, Inference Server
  - New relation types added: optimizes, validates
  - Additive changes, backward compatible

v2.0 (Concept Layer - Breaking):
  - Renames "API Service" to "REST Service"
  - Adds transitivity to "depends_on" relation
  - Requires migration of existing blueprints

Operational Layer:
  - Continuous updates based on deployment
  - Performance metrics collected in real-time
  - Failure modes identified and addressed
  - No version control (runtime-specific)

7.3.5 Layer Mapping to Blueprint Elements

CONCEPT LAYER → Blueprint Schema:
  - Entity type definitions → Schema entity types
  - Relation type definitions → Schema relation types
  - Type taxonomies → Classification schemas
  - Constraint types → Constraint schemas

STRUCTURAL LAYER → Blueprint Instance:
  - System instance → Blueprint system entity
  - Component instances → Blueprint component entities
  - Interface instances → Blueprint interface entities
  - Structural relations → Blueprint relation entities

OPERATIONAL LAYER → Blueprint Views:
  - Workflows → Operations view
  - Runtime topology → Deployment view
  - Performance metrics → Monitoring dashboards
  - Failure modes → Reliability view

7.3.7 Layer 1: Concept Ontology

7.3.7.1 Definition

The concept layer defines the semantic primitives of systems. These primitives describe what kinds of things exist in system architectures.

7.3.7.2 What It Defines

The concept ontology defines:

  • Entity types: What kinds of things can exist
  • Basic properties: What attributes entities can have
  • Fundamental relationships: Basic ways entities can connect

7.3.7.3 Examples

Concept-level entities include:

  • System: A bounded architectural unit with a goal
  • Component: A structural building block
  • Interface: An interaction boundary
  • Capability: A functional ability
  • Data Entity: An information structure
  • Workflow: A coordinated sequence
  • Constraint: A requirement or limit

7.3.7.4 The Core Question

At this layer, the ontology answers a basic question:

What kinds of elements exist in software systems?

The concept ontology therefore establishes the vocabulary used across the entire blueprint ecosystem.

7.3.7.5 Stability

The concept ontology is the most stable layer. It changes slowly because:

  • The fundamental elements of software architecture are relatively stable
  • New technologies introduce new ways of doing things, not new kinds of architectural elements
  • Changing core concepts requires a major version update

Example:

v1.0: Core entities defined (System, Component, Interface, etc.)
v1.5: New attributes added to existing entities
v2.0: Core entity structure changed (rare)

7.3.8 Layer 2: Structural Ontology

7.3.8.1 Definition

The structural layer describes how the conceptual entities are organized within a specific system architecture.

7.3.8.2 What It Defines

While the concept ontology defines entity types, the structural ontology defines:

  • Entity instances: Specific instances of concept types
  • Specific relationships: How instances relate to each other
  • Architectural configurations: How entities are arranged

7.3.8.3 Examples

Structural ontology includes:

  • Component containment: System contains Component A, Component B
  • Service dependencies: Component A depends_on Component B
  • Interface connections: Component A calls Interface B
  • Data flows: Component A reads Data Entity X
  • Workflow structures: Workflow contains Step 1, Step 2, Step 3

7.3.8.4 The Core Question

At this layer, the ontology answers:

How are the conceptual elements organized in this specific system?

The structural ontology therefore represents the architecture of a particular system.

7.3.8.5 Variability

The structural ontology is the most variable layer. Every system has a different structural configuration, even when using the same concept types.

Example:

System A:
  - Contains 3 components
  - Has 2 interfaces
  - Uses 1 workflow

System B:
  - Contains 15 components
  - Has 8 interfaces
  - Uses 5 workflows

Both use the same concept types, but have different structures.

7.3.9 Layer 3: Operational Ontology

7.3.9.1 Definition

The operational layer describes how the system behaves in execution environments.

7.3.9.2 What It Defines

This layer includes concepts related to:

  • Runtime behavior: How components execute
  • Deployment structure: Where components run
  • Operational characteristics: Performance, reliability, scaling
  • Environmental context: External dependencies and conditions

7.3.9.3 Examples

Operational ontology elements include:

  • Runtime topology: How components are distributed
  • Deployment units: What gets deployed together
  • Scaling boundaries: Where components can scale independently
  • Scheduling triggers: When workflows execute
  • Failure modes: How systems can fail
  • Operational constraints: Performance requirements, SLAs

7.3.9.4 The Core Question

At this layer, the ontology answers:

How does the architecture behave in actual execution?

The operational ontology extends structural descriptions into the domain of system operation.

7.3.9.5 Evolution

The operational ontology evolves as:

  • New deployment models emerge (serverless, edge computing)
  • New operational requirements emerge (observability, chaos engineering)
  • New runtime patterns emerge (circuit breakers, rate limiting)

7.4 Layer Interconnections

The three layers are not independent—they form an integrated stack:

Concept Ontology (what exists)
    ↓ defines types for
Structural Ontology (how organized)
    ↓ provides structure for
Operational Ontology (how behaves)

7.4.1 Example: Web Application

Let’s trace a simple web application through the three layers:

7.4.1.1 Concept Layer

Entities available:
  - System, Component, Interface, DataEntity, Workflow
  - Relations: contains, depends_on, calls, reads, writes

7.4.1.2 Structural Layer

Specific system instance:
  - System: E-commerce Platform
    - contains: Web UI, API Service, Database
    - Web UI calls API Service
    - API Service depends_on Database
    - API Service reads Order Data
    - API Service writes Order Data

7.4.1.3 Operational Layer

Runtime configuration:
  - Web UI deployed to CDN
  - API Service deployed to 3 instances with load balancer
  - Database deployed to primary + replicas
  - Scaling: API Service auto-scales based on load
  - Failure: Database failover to replica
  - Constraint: API response time < 500ms

All three layers describe the same system from different perspectives.

7.4.2 Example: Data Pipeline

Let’s trace a data processing pipeline through the three layers:

7.4.2.1 Concept Layer

Entities available:
  - System, Component, Interface, DataEntity, Workflow, Trigger
  - Relations: contains, depends_on, reads, writes, invokes

7.4.2.2 Structural Layer

Specific system instance:
  - System: Analytics Pipeline
    - contains: Ingestion Worker, Transformation Engine, Storage Component
    - Workflow: Data Processing Pipeline
    - Workflow contains: Step 1 (Extract), Step 2 (Transform), Step 3 (Load)
    - Ingestion Worker reads from Source Data
    - Transformation Engine writes to Processed Data
    - Storage Component persists results

7.4.2.3 Operational Layer

Runtime configuration:
  - Trigger: Scheduled execution every hour
  - Ingestion Worker: 5 parallel instances
  - Transformation Engine: Spark cluster with 10 workers
  - Storage Component: S3 bucket with lifecycle policies
  - Scaling: Spark cluster scales based on data volume
  - Failure: Retry with exponential backoff
  - Constraint: Pipeline completion time < 4 hours

7.4.3 Example: Agent System

Let’s trace an AI agent system through the three layers:

7.4.3.1 Concept Layer

Entities available:
  - System, Component, Interface, DataEntity, Workflow, Trigger
  - Relations: contains, depends_on, calls, invokes, reads, writes

7.4.3.2 Structural Layer

Specific system instance:
  - System: Document Analysis Agent
    - contains: Agent Controller, LLM Engine, Tool Executor, Memory Store
    - Agent Controller calls LLM Engine
    - Agent Controller invokes Tool Executor
    - Tool Executor implements multiple tool interfaces
    - Agent Controller reads from Memory Store
    - Agent Controller writes to Memory Store

7.4.3.3 Operational Layer

Runtime configuration:
  - Trigger: User request via API
  - Agent Controller: Single instance with connection pooling
  - LLM Engine: External API with rate limiting
  - Tool Executor: 3 parallel workers for concurrent tool execution
  - Memory Store: Vector database with embedding search
  - Failure: Tool execution timeout with fallback to alternative tools
  - Constraint: Agent response time < 30 seconds

These examples demonstrate how the same three-layer structure can describe radically different systems while maintaining consistent conceptual frameworks.

7.4.4 Benefits of Layering

Separation of Concerns: - Concept layer: What things are - Structural layer: How they’re arranged - Operational layer: How they run

Stability vs. Flexibility: - Concept layer: Stable, changes slowly - Structural layer: Flexible, varies by system - Operational layer: Evolves with technology

Independent Evolution: - Can evolve operational concepts without changing concepts - Can add new structural patterns without redefining entities - Can extend concepts without breaking existing systems

7.5 Multiple Views of the Same System

A single system can be interpreted through different perspectives depending on the audience and the purpose of the representation.

7.5.1 Why Multiple Views Matter

Different stakeholders need different information:

Product Manager:
  - What the system does
  - What capabilities it provides
  - How users interact with it

System Architect:
  - How components are structured
  - How they depend on each other
  - What interfaces they expose

DevOps Engineer:
  - How the system is deployed
  - How it scales
  - How it's monitored

Security Analyst:
  - Where trust boundaries exist
  - How authentication works
  - What data is sensitive

A single monolithic description cannot optimally serve all these needs.

7.5.2 Four Common Views

7.5.2.1 1. Product View

Audience: Product managers, stakeholders, users

Focus: System capabilities and user-facing functions

Questions answered: - What the system does - Which capabilities it provides - How those capabilities support user goals - What the user experience is like

Key elements: - System goals - Capabilities - User interfaces - Stakeholder interactions

Example:

Product View:
  System: E-commerce Platform
  Goal: Enable online shopping
  Capabilities:
    - Browse products
    - Add to cart
    - Checkout
    - Track orders
  User Interface: Web application

7.5.2.2 2. Engineering View

Audience: Architects, developers, engineers

Focus: Internal architecture and implementation

Questions answered: - What components exist - How they’re connected - What interfaces they expose - What data they manage

Key elements: - Components and modules - Interfaces and dependencies - Data structures - Workflows

Example:

Engineering View:
  Components:
    - Web UI (React frontend)
    - API Service (Node.js backend)
    - Database (PostgreSQL)
  Interfaces:
    - REST API for product catalog
    - REST API for orders
  Dependencies:
    - API Service depends_on Database
    - Web UI depends_on API Service

7.5.2.3 3. Operations View

Audience: Operators, DevOps engineers, SREs

Focus: Runtime behavior and system management

Questions answered: - How is the system deployed - How does it scale - How is it monitored - What happens when things fail

Key elements: - Deployment topology - Runtime scaling - Monitoring and observability - Reliability mechanisms

Example:

Operations View:
  Deployment:
    - Web UI: CDN
    - API Service: 3 instances, load balanced
    - Database: Primary + 2 replicas
  Scaling:
    - API Service: Auto-scale 3-10 instances
    - Database: Read replicas for queries
  Monitoring:
    - Metrics: request latency, error rate
    - Logs: application logs, access logs
  Reliability:
    - Database failover to replica
    - API Service retries with backoff

7.5.2.4 4. Security View

Audience: Security analysts, auditors, compliance officers

Focus: Security boundaries and controls

Questions answered: - Where are the trust boundaries - How is authentication handled - What data is sensitive - How are access controls enforced

Key elements: - Trust boundaries - Authentication mechanisms - Authorization policies - Data classification

Example:

Security View:
  Trust Boundaries:
    - External users → Web UI
    - Web UI → API Service
    - API Service → Database
  Authentication:
    - Users authenticate via OAuth 2.0
    - Services authenticate via mTLS
  Authorization:
    - Role-based access control (RBAC)
  Data Protection:
    - PII encrypted at rest
    - TLS for data in transit

7.5.3 Views as Projections

These views are not separate models—they are projections of the same ontology instance:

Single Ontology Instance
        ↓
    [Projection Filters]
        ↓
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ Product View│Engineering  │Operations   │Security     │
│             │View         │View         │View         │
└─────────────┴─────────────┴─────────────┴─────────────┘

All views derive from the same underlying data, ensuring consistency.

7.6 Mapping Ontology to the Blueprint Kernel

The blueprint kernel introduced in the previous volume defines six structural slots:

┌─────────────────────────────────────────────┐
│           Blueprint Kernel                  │
├─────────────────────────────────────────────┤
│  Goal          → What the system achieves   │
│  Capabilities  → What the system can do     │
│  Components    → How it's structured        │
│  Interfaces    → How parts interact         │
│  Data          → What information flows     │
│  Workflows     → How behavior is coordinated │
└─────────────────────────────────────────────┘

The ontology provides the typed entities that populate these slots.

7.6.1 Mapping Table

Blueprint Kernel Slot Ontology Entities Examples
Goal System entity sys.ecommerce
Capabilities Capability entities cap.browse_products, cap.place_order
Components Component entities comp.web_ui, comp.api_service
Interfaces Interface entities int.api.products, int.api.orders
Data DataEntity entities data.product, data.order
Workflows Workflow entities wf.order_processing

7.6.2 The Mapping Process

1. Start with blueprint kernel
2. Populate each slot with ontology entities
3. Use ontology relations to connect entities
4. Result: Complete blueprint representation

7.6.3 Example

Blueprint Kernel:
  Goal: Enable online shopping
  Capabilities: [to be defined]
  Components: [to be defined]
  Interfaces: [to be defined]
  Data: [to be defined]
  Workflows: [to be defined]

Ontology Populated:
  Goal: System (sys.ecommerce)
  Capabilities:
    - Capability (cap.browse_products)
    - Capability (cap.place_order)
  Components:
    - Component (comp.web_ui)
    - Component (comp.api_service)
    - Component (comp.database)
  Interfaces:
    - Interface (int.api.products)
    - Interface (int.api.orders)
  Data:
    - DataEntity (data.product)
    - DataEntity (data.order)
  Workflows:
    - Workflow (wf.order_processing)

Relations connect everything:
  - comp.web_ui calls int.api.products
  - comp.api_service implements int.api.products
  - comp.api_service depends_on comp.database
  - comp.api_service reads data.product
  - comp.api_service writes data.order

This mapping is the primary integration point between the Foundations volume and the System Ontology volume.

7.7 Granularity: Choosing the Right Level of Detail

System architecture can be described at multiple levels of detail. The ontology must therefore support multiple levels of granularity.

7.7.1 Granularity Levels

Typical levels include:

1. System Level - The entire application or platform as a single unit - Focus: Overall goals, major capabilities - Example: “E-commerce platform”

2. Subsystem Level - Major functional areas or modules - Focus: Major components, their relationships - Example: “Order processing subsystem”, “Inventory management subsystem”

3. Component Level - Deployable or logically independent units - Focus: Component responsibilities, interfaces - Example: “Order service”, “Payment gateway”, “Inventory service”

4. Module Level - Internal groupings within components - Focus: Code organization, module boundaries - Example: “Order validation module”, “Payment processing module”

5. Function Level - Individual routines or methods - Focus: Algorithmic details, code implementation - Example: “validateOrder()”, “processPayment()”

7.7.2 Choosing the Right Level

The appropriate level of granularity depends on the purpose:

Purpose Recommended Level Why
Portfolio management System level Overview of all systems
Integration planning Subsystem level Understand major dependencies
Architecture design Component level Design component structure
Implementation Module level Organize code structure
Performance analysis Function level Identify bottlenecks

7.7.3 The Architectural Boundary

Within the Blueprint Architecture framework, the component level serves as the typical boundary for architectural description.

7.7.3.1 Why Component Level?

Above component level: Too coarse - System level doesn’t provide enough detail for design decisions - Can’t understand component interactions or data flows

Below component level: Too fine - Module level is implementation-specific - Function level belongs to code analysis, not architecture - Details change frequently, reducing stability

At component level: Just right - Captures essential architectural structure - Independent of implementation details - Stable enough for long-term analysis - Detailed enough for design decisions

7.7.3.2 When to Go Deeper

Sometimes, component-level detail is insufficient:

  • Performance optimization: Need to understand module-level behavior
  • Security analysis: Need to understand data access patterns
  • Refactoring: Need to understand code structure

In these cases, you can:

  1. Start with component-level architecture
  2. Drill down to module/function level for specific analysis
  3. Maintain component level as the primary representation

7.7.3.3 When to Stay Higher

Sometimes, component-level detail is unnecessary:

  • Portfolio overview: System level is sufficient
  • Integration contracts: Interface level is sufficient
  • Capability planning: Capability level is sufficient

The ontology supports multiple levels, allowing you to choose the appropriate granularity for each task.

7.8 Summary

The ontology stack provides a structured approach to representing systems:

Concept Ontology
  - Defines what kinds of things exist
  - Most stable layer
  - Foundation for all other layers

Structural Ontology
  - Defines how things are organized
  - Varies by system
  - Captures specific architectures

Operational Ontology
  - Defines how things behave
  - Evolves with technology
  - Describes runtime characteristics

Key principles:

  1. Layered separation: Different levels of abstraction for different purposes
  2. Multiple views: Single ontology can generate multiple stakeholder-specific views
  3. Kernel mapping: Ontology entities populate blueprint kernel slots
  4. Appropriate granularity: Component level as the typical architectural boundary
  5. Flexible depth: Can drill down or up as needed

This layered approach enables the ontology to be both abstract enough to apply broadly and concrete enough to represent real architectures precisely.
